# 项目描述

* **项目描述**：本项目基于泰山派开发板构建学习辅助系统，上位机运行用户界面并集成YOLOv11n模型实现实时学习状态检测；下位机以ESP32为主控单元，负责环境数据采集与设备控制。系统可智能监督用户学习行为、提供便捷的学习支持功能，有效提升专注度与学习氛围。

* 负责内容：

1. 基于QT框架开发上位机界面，使用QSS进行整体视觉美化；集成DeepSeek API实现智能问答模块，通过QNetworkAccessManager发送HTTP请求并解析JSON响应，结合QTextToSpeech实现语音播报功能。

4. 下位机基于ESP32平台，通过MQTT协议将传感器数据实时上传至服务器，支持手机客户端订阅并远程查看环境数据及设备状态；同时通过串口与泰山派通信，支持通过手机App或终端助手控制灯光与风扇。应用FreeRTOS队列与事件机制优化任务调度，提升系统实时性和多任务处理能力。

5. 独立完成ESP32主控板的PCB设计、手工焊接与系统级测试，保障硬件模块稳定可靠运行。

        我将整个系统分解为几个任务：

        * 一个高优先级任务：负责处理串口接收中断抛出的数据，并将其快速放入队列中。它的职责是尽快离开中断上下文，不让中断被长时间阻塞。

        * 一个中优先级任务：作为主逻辑任务，它阻塞在队列上，等待处理来自串口的数据包。解析后，它会将需要发送的数据通过另一个队列发送给...

# UART+DMA 不定长数据收发+环形缓冲区的实现

通过UART+DMA实现不定长数据收发，结合环形缓冲区来处理数据的接收和发送，可以有效地提高数据传输效率和系统响应速度。以下是一个简单的实现思路：

##### 1. 硬件配置

确保UART和DMA的硬件配置正确。通常需要设置以下参数：
- UART波特率
- 数据位、停止位、校验位
- DMA通道配置
- DMA传输方向（从外设到内存或从内存到外设）
##### 2. 环形缓冲区设计
环形缓冲区是一个固定大小的缓冲区，使用两个指针（头指针和尾指针）来管理数据的读写。以下是环形缓冲区的基本结构：

```c
#define BUFFER_SIZE 256 // 缓冲区大小
typedef struct {
    uint8_t buffer[BUFFER_SIZE]; // 数据缓冲区
    volatile uint32_t head;       // 头指针
    volatile uint32_t tail;       // 尾指针
} RingBuffer;
RingBuffer ringBuffer;
```
##### 3. 初始化环形缓冲区
```c
void RingBuffer_Init(RingBuffer *rb) {
    rb->head = 0;
    rb->tail = 0;
}
```
##### 4. DMA接收数据
使用DMA接收数据时，将接收到的数据存储到环形缓冲区中。可以在DMA传输完成中断中处理数据。

```c
void DMA_UART_Receive_IRQHandler(void) {
    // 假设DMA接收完成后会触发中断
    uint32_t receivedLength = DMA_GetReceivedDataLength(); // 获取接收到的数据长度
    for (uint32_t i = 0; i < receivedLength; i++) {
        ringBuffer.buffer[ringBuffer.head] = DMA_ReadData(); // 从DMA读取数据
        ringBuffer.head = (ringBuffer.head + 1) % BUFFER_SIZE; // 更新头指针
        if (ringBuffer.head == ringBuffer.tail) {
            // 缓冲区满，处理溢出（例如丢弃旧数据或覆盖）
            ringBuffer.tail = (ringBuffer.tail + 1) % BUFFER_SIZE; // 覆盖旧数据
        }
    }
}
```
##### 5. DMA发送数据
发送数据时，可以从环形缓冲区中读取数据，并通过DMA发送出去。

```c
void DMA_UART_Send(RingBuffer *rb) {
    while (rb->tail != rb->head) { // 当缓冲区不为空时
        uint8_t data = rb->buffer[rb->tail]; // 读取数据
        DMA_WriteData(data); // 通过DMA发送数据
        rb->tail = (rb->tail + 1) % BUFFER_SIZE; // 更新尾指针
    }
}
```
##### 6. 使用示例
```c
int main(void) {
    RingBuffer_Init(&ringBuffer); // 初始化环形缓冲区

    // 配置UART和DMA
    UART_Config();
    DMA_Config();

    // 启动DMA接收
    DMA_UART_StartReceive();

    while (1) {
        // 主循环中可以处理其他任务
        if (DataAvailable(&ringBuffer)) { // 检查是否有数据可用
            DMA_UART_Send(&ringBuffer); // 发送数据
        }
    }
}
```
##### 7. 注意事项
- 确保环形缓冲区的大小足够大，以容纳预期的最大数据量。
- 在多线程或中断环境中访问环形缓冲区时，需要使用适当的同步机制（如禁用中断）来防止数据竞争。
- 处理缓冲区满的情况时，可以选择丢弃旧数据或覆盖旧数据，具体取决于应用需求。
#####

##### 8. 总结
通过使用UART和DMA结合环形缓冲区，可以实现高效的不定长数据收发。这种方法能够减少CPU的负担，提高数据传输的实时性和可靠性。环形缓冲区的设计使得数据的读写操作更加灵活，适用于多种嵌入式应用场景。
   
### 简化过程

要实现UART+DMA不定长数据收发可以通过，UART触发空闲中断，然后通过DMA传输过半中断/DMA传输完成中断 来处理数据，将数据写入环形缓冲区。

#### 双缓冲机制：
将DMA缓冲区设定为二维数组buf[2][N],在DMA开始工作是会先将数据存放到buf[0]中，当触发DMA半传输中断时，即表示buf[0]已存满，系统会转到buf[1]中缓存，这时你就可以及时处理buf[0]中的数据了，当触发DMA全传输中断时，即表示buf[1]已存满，系统会转到buf[0]中缓存，这时你就可以及时处理buf[1]中的数据了。即实现无缝数据流采集和并行处理。



# 设备省电的方法

## 方法一：进入低功耗模式

ESP32调用esp_deep_sleep_start() 函数 开启ESP32Deep Sleep 模式，该模式下ESP32 的 CPU、大部分 RAM 以及所有数字外设都会断电，只保留RTC 控制器、RTC 外设（包括 ULP 协处理器）和 RTC 存储器（8KB）保持供电,RTC主要用于睡眠时的定时唤醒。

项目中采用了定时唤醒的方式，通过调用 esp_sleep_enable_timer_wakeup()来实现定时唤醒设别从而定时上报一次数据，同时设备支持中断唤醒通过使用esp_sleep_enable_ext0_wakeup()绑定到一个特定的 GPIO，当检测到电平变化时，RTC IO 直接唤醒系统。

如果下位机在睡眠时需要保持灯光或者风扇状态，可以调用gpio_deep_sleep_hold_en()，强制锁定 GPIO 的电平状态，防止 CPU 断电后引脚电平跳变。

示例：

### wifi的两种模式STA模式和AP模式

在 Wi-Fi 网络拓扑中，STA 指的是连接到无线接入点 (AP, Access Point) 的终端设备。简单来说，当你用笔记本电脑或手机连接家里的路由器时，你的电脑和手机就处于 STA 模式，而路由器处于 AP 模式。

在 STA 模式下，ESP32 就像一个普通的上网设备，它不提供 Wi-Fi 信号给别人连接，而是主动去搜索并连接已有的 Wi-Fi 网络，从中获取 IP 地址，进而访问局域网或互联网。

### wifi活跃的同时保持低功耗——使用Modem Sleep模式

在 ESP32 中，Modem Sleep（调制解调器睡眠） 是一种非常实用的低功耗模式。在这种模式下，ESP32 会保持 CPU 运行，但会根据路由器的 DTIM（数据分发间隔）周期性地关闭和打开 Wi-Fi 或蓝牙的射频（RF）模块，从而在保持网络连接的同时大幅降低功耗。此时ESP32 的 CPU 核心（如你的业务逻辑、PID 控制、MQTT 保持）一直在正常跑，只是 Wi-Fi 的射频模块在后台偷偷地根据路由器的信号间隔（DTIM）进行开关。

Wi-Fi 处于 DTIM 模式时，ESP32-S3 会在 DTIM 周期内关闭 Wi-Fi 调制解调器（Modem）并保持连接，显著降低功耗。

    DTIM (Delivery Traffic Indication Message)：
    DTIM 表示路由器向设备传递数据的时间间隔。更高的 DTIM 值可以降低功耗，但会增加数据延迟。

```c
esp_wifi_set_ps(WIFI_PS_MIN_MODEM); // 最小功耗
esp_wifi_set_ps(WIFI_PS_MAX_MODEM); // 最大省电
```
### 更深度省电并支持快速唤醒：Light Sleep

Light Sleep 适用于 Wi-Fi 保持连接时的深度省电模式，支持更低的功耗。当你调用进入 Light Sleep 的命令后，CPU 会停止执行下一行代码，电流瞬间掉到 1mA 以下。只有当定时器时间到或某个引脚电平变化时，CPU 才会“惊醒”并从刚才停止的地方继续运行。

✅ CPU、时钟、部分外设会暂停，但 Wi-Fi/蓝牙可在特定 DTIM 间隔内保持唤醒。

✅ 恢复速度较快（约1~2ms）。

|工作状态|	平均电流 (典型值)|
|-----|-----|
|CPU 暂停，无外设|	~0.8mA - 1.2mA|
|Wi-Fi DTIM = 10|	~1.5mA - 2mA|
|RTC 唤醒触发（短时）|	~1mA|


假设你的设备需要频繁采集数据，比如一个心率手环，每秒都要读一次传感器，但又不想一直满负荷运转。这时候你就需要一种“打盹式”的节能方式——这就是 Light Sleep 的主场。

它是怎么工作的？
进入 Light Sleep 后：

* ✅ CPU 停止执行
* ✅ 大部分外设时钟关闭
* ✅ RAM 和任务上下文保留
* ✅ RTC 控制器、ULP 协处理器继续运行
* ✅ 可通过 GPIO 中断、定时器、触摸感应等方式快速唤醒

最关键是： 唤醒后程序接着原来的地方继续跑，不需要重启系统 。
```c
#include "esp_sleep.h"
#include "nvs_flash.h"

void setup_light_sleep() {
    // 设置 5 秒后自动唤醒
    const uint64_t sleep_time_us = 5 * 1000 * 1000;
    esp_sleep_enable_timer_wakeup(sleep_time_us);

    // 配置 GPIO13 下降沿唤醒
    esp_sleep_enable_ext0_wakeup(GPIO_NUM_13, 0);

    printf("即将进入轻度睡眠...\n");

    // 开始睡觉
    esp_light_sleep_start();

    printf("已唤醒！当前时间：%llu\n", esp_timer_get_time());
}
```

### 若追求极致省电（无需 Wi-Fi/蓝牙实时响应）：Deep Sleep

Deep Sleep 是 ESP32-S3 的最低功耗模式，CPU 和大部分外设断电，仅 RTC 和 ULP 协处理器可运行。一旦进入 Deep Sleep，除了 RTC 控制器和少数 GPIO，整个芯片几乎全部断电。CPU 停了，RAM 清了，Wi-Fi 模组歇菜了，连内部参考电压都关掉了。

✅ 适用于周期性唤醒、数据采集或极限省电场景。

✅ 唤醒时间较长（约100ms）。

|状态|	平均电流 (典型值)|
|------|-----|
|RTC 定时器唤醒	|~5μA|
|外部触发 (GPIO)	|~5μA|
|ULP 协处理器运行	|~20μA|

```c
#include "esp_sleep.h"

// 这个变量会在睡眠中保留！
RTC_DATA_ATTR static int boot_count = 0;

void app_main() {
    boot_count++;
    printf("第 %d 次启动\n", boot_count);

    // 5 秒后自动唤醒，比如传感器数据并不需要时刻上报，每隔一段时间采集一次就好
    esp_sleep_enable_timer_wakeup(5 * 1000 * 1000);

    // 启用 EXT1：GPIO27 上升沿唤醒，比如用户想要控制灯光或者风扇，按一下按钮就能唤醒设备
    esp_sleep_enable_ext1_wakeup(BIT6(27), ESP_SLEEP_WAKEUP_EXT1_HIGH);

    printf("进入深度睡眠...\n");
    esp_deep_sleep_start();
}

```

# 项目中RTOS得使用

## 使用到的通信/同步机制

### 1. 队列（Queue）—— 核心数据通道
用途：所有模块之间数据传递都用它

* UART 接收不定长数据 → 入队列
* MQTT 上报数据 → 从队列取数据
* 控制指令（灯光 / 风扇）→ 队列传递
* 传感器数据 → 队列发给 MQTT
### 2. 事件组（Event Group）—— 多事件等待
你项目最适合的场景：
等待 WiFi 连接成功 + MQTT 连接成功 才开始上报数据
等待 串口收到指令 OR MQTT 收到指令 执行设备控制
低功耗：等待 定时器唤醒 OR 中断唤醒 事件
### 3. 信号量（Semaphore）—— 任务同步 & 资源互斥
二值信号量：串口接收完成、传感器采集完成、MQTT 收到指令，用来唤醒任务
互斥信号量：保护 UART 硬件、Flash 读写、OTA 写入，防止多任务同时操作
### 4. 通知（Task Notify）—— 轻量级同步
替代部分信号量，更省内存，用于：
唤醒低功耗任务
触发单次行为（拍照、采集、上报）

## 任务设计

### 1. 数据采集任务（Sensor_Task）
* 采集温湿度、光照、人体感应等环境数据
* 放入 数据队列
* 周期：1s/2s 一次
### 2. UART 串口通信任务（UART_Task）
* 使用 UART+DMA 不定长接收
* 解析来自 RK3566 的指令（灯光、风扇、学习状态）
* 接收数据后通过 队列 / 事件组 通知控制任务
### 3. MQTT & IoT 任务（MQTT_Task）
* AT 指令联网
* 订阅平台指令
* 上报环境数据、设备状态
* 从 数据队列 取数据上报
* 下发指令给 设备控制任务
### 4. 设备控制任务（Control_Task）
* 控制灯光、风扇
* 来源：
    * UART 来自 RK3566
    * MQTT 来自手机 / 云端
* 用 信号量 / 队列 同步执行
### 5. 低功耗管理任务（Power_Task）
* 管理 ESP32 深睡眠 DeepSleep
* RTC 定时器 + 中断唤醒
* 唤醒事件用 事件组 管理
### 6. OTA 升级任务（OTA_Task）
* 后台监听升级指令
* 双分区切换、固件校验
* 互斥信号量保护 Flash 写入


# 低功耗管理任务是怎么工作的？

一般来讲实现低功耗功能，我们只需要设置定时唤醒和中断唤醒，然后开启Deep Sleep深度睡眠模式即可。但是实际项目中，进入深睡眠之前，系统必须做一堆 “善后工作”。

## 1. 进入睡眠前，必须安全停止所有其他任务
ESP32 有以下任务：
* UART 正在收发数据
* MQTT 正在上传数据
* 传感器正在采集
* 风扇 / 灯光正在控制

## 2. 进入睡眠前，需要判断当前能否进入睡眠

系统必须满足以下条件才能睡眠：
* 没有 MQTT 消息传输
* 没有 UART 数据交互
* 没有设备控制（灯光 / 风扇）
* 长时间无人操作（例如 3 分钟）


为此需要单独设置一个低功耗任务来管理这些事情：

```c
1. 启动后一直等待【可进入睡眠条件】
2. 满足条件后：
   - 停止所有业务任务
   - 保存设备状态
   - 关闭所有外设（UART、I2C、传感器）
   - 配置唤醒源（定时器 + 外部中断）
3. 进入 Deep Sleep（μA级电流）
4. 被唤醒 → Power_Task 重新运行
5. 重新初始化系统：
   - 重启UART/MQTT/传感器
   - 恢复所有业务任务
6. 回到第1步，循环
```

# 程序升级任务是怎么工作的？

## 1.Bootloader（引导程序）

* 芯片上电最先跑
* 负责：判断从哪个分区启动、固件拷贝 / 校验
* 只做 “底层切换”，不做 “业务逻辑”
## 2. OTA 升级流程----OTA_Task（系统业务级）

* 在 FreeRTOS 里跑
* 负责：什么时候升级、从哪下载、怎么下载、是否要重启、失败怎么恢复
* 能联网、能 MQTT、能读写 Flash、能做业务判断
* 不直接写分区，只告诉 Bootloader 要升级

## 3.分工合作

    OTA_Task（负责前95%）
    1. 监听升级指令
    2. 下载固件到备用分区
    3. 校验固件合法性
    4. 设置启动标志位
    5. 指令系统重启

    Bootloader（只负责最后5%）
    → 读取标志
    → 从新分区启动

由MQTT订阅云端升级指令，手机APP推送升级，然后OTA_Task任务定期检查升级指令，判断需要升级后下载新的固件写入备用flash分区，然后设置eeprom中OTA升级标志，上报云端升级成功，然后设备自动重启，重启后由Bootloader检测到OTA升级标志，然后将外部flash的新固件拷贝到内部flash的运行分区，最后从新固件启动。
## 4.OTA_Task具体工作流程

    1. 后台循环监听 MQTT 云端升级指令
    2. 收到指令 → 检查版本号是否需要更新
    3. 申请互斥信号量（独占Flash，防止冲突）
    4. 开始下载固件包 → 写入备用Flash分区
    5. 下载完成 → 校验SHA256完整性
    6. 校验成功 → 设置OTA升级标志
    7. 释放互斥信号量
    8. 上报云端“升级成功”
    9. 安全重启
    10. 重启后Bootloader自动切换到新固件
