## 1. 进程和线程的区别？

* 进程：资源分配的基本单位，独立地址空间。
* 线程：调度的基本单位，共享所属进程的资源。

根本区别：进程是操作系统资源分配的基本单位，而线程是任务调度和执行的基本单位

在开销方面：每个进程都有独立的代码和数据空间（程序上下文），程序之间的切换会有较大的开销；线程可以看做轻量级的进程，同一类线程共享代码和数据空间，每个线程都有自己独立的运行栈和程序计数器（PC），线程之间切换的开销小。

所处环境：在操作系统中能同时运行多个进程（程序）；而在同一个进程（程序）中有多个线程同时执行（通过CPU调度，在每个时间片中只有一个线程执行）

内存分配方面：系统在运行的时候会为每个进程分配不同的内存空间；而对线程而言，除了CPU外，系统不会为线程分配内存（线程所使用的资源来自其所属进程的资源），线程组之间只能共享资源。

包含关系：操作系统中的每一个进程中都至少存在一个线程。如果一个进程内有多个线程，则执行过程不是一条线的，而是多条线（线程）共同完成的；线程是进程的一部分，所以线程也被称为轻权进程或者轻量级进程。

注：

    像 FreeRTOS 这样的小型 RTOS 通常将线程称为任务，因为它们不支持虚拟内存，因此进程和线程之间没有区别。

## 2.什么是死锁？产生的条件有哪些？

* 死锁是指多个进程/线程因争夺资源而相互等待，导致程序无法继续执行。
* 四个必要条件：
    1. 互斥
    2. 请求与保持
    3. 不可抢占
    4. 循环等待

## 3.什么是中断？硬中断和软中断的区别？

* 中断：CPU响应外部事件的一种机制。
* 硬中断：由外设触发（如定时器、串口）。
* 软中断：由软件触发（如系统调用、异常）。

## 4.实时操作系统（RTOS）的特点？

* 可预测性强，任务调度延迟确定。
* 支持硬实时任务。
* 内核轻量级，占用资源少。

实时操作系统与一般的操作系统相比，最大的特色就是“实时性”，如果有一个任务需要执行，实时操作系统会马上（在较短时间内）执行该任务，不会有较长的延时。这种特性保证了各个任务的及时执行。

实时操作系统中都要包含一个实时任务调度器，这个任务调度器与其它操作系统的最大不同是强调：严格按照优先级来分配CPU时间，并且时间片轮转不是实时调度器的一个必选项。

## 5.FreeRtos中 任务的三要素

一个任务的三要素是任务主体函数，任务栈，任务控制块

### 1. 任务函数（任务主体函数）
作用：任务函数定义了任务实际要执行的操作和逻辑，是任务的灵魂和代码载体。

* 是什么？ 它是一个普通的C函数，其函数签名（返回值和参数）必须符合FreeRTOS的要求（通常返回void，并接受一个void*参数）。

* 如何工作？ 一旦任务被调度器选中并获得CPU使用权，就从该函数的开始处（或上次被切换出去的地方）开始执行。

* 关键特性：

    * 无限循环： 任务函数通常包含一个for(;;)或while(1)无限循环，因为任务一旦创建，其工作逻辑通常是持续执行的。如果没有循环，任务函数执行完毕并返回时，任务将被内核自动删除。

    * 阻塞调用： 一个“好”的任务必须在适当的地方调用FreeRTOS的阻塞API函数（如vTaskDelay(), xQueueReceive(), xSemaphoreTake()等）。这会让任务进入阻塞（Blocked）状态，主动让出CPU给其他任务，这是实现多任务协作的核心。如果一个任务永不阻塞（例如只有一个死循环且不做任何延迟），它可能会饿死同优先级的其他任务。

示例：

```c
void vMyTaskFunction(void * pvParameters) {
    // 初始化代码（可选，只执行一次）

    for(;;) {
        // 任务的主体工作代码在这里重复执行
        do_something();

        // 关键：调用阻塞函数，让出CPU
        vTaskDelay(pdMS_TO_TICKS(1000)); // 阻塞 approximately 1000ms
    }
}
```

### 2. 任务栈（Stack）
作用：任务栈是任务完全独享的内存空间，用于保存任务在运行时的“现场”和局部变量，是任务能够独立运行的物质基础。

* 是什么？ 一块预先分配好的RAM（通常是一个数组），其大小由用户在创建任务时指定。

* 如何工作？

    * 保存上下文： 当任务被调度器切换出去时，CPU寄存器的当前值（程序的计数器、状态寄存器等）会被自动保存到它自己的任务栈中。当任务再次被调度时，这些值又从栈中恢复，CPU就能准确地从上次中断的地方继续执行。

    * 存储局部变量： 函数调用、中断发生时，所有的局部变量、函数返回地址等也都存放在这个私有的栈空间中。

* 关键特性：

    * 独立性： 每个任务都有自己独立的栈空间，互不干扰。这是实现多任务并发的关键。

    * 大小至关重要： 栈大小必须根据任务的实际情况（函数调用深度、局部变量大小等）合理设置。

        * 太小： 会导致栈溢出，覆盖其他内存区域，造成系统崩溃或难以预料的错误（这是嵌入式系统最常见的错误之一）。

        * 太大： 会浪费宝贵的RAM资源。FreeRTOS提供了方法（如uxTaskGetStackHighWaterMark()）来检测任务运行过程中栈的最大使用量，以便优化其大小。

### 3. 任务控制块（TCB）
作用：TCB是操作系统用于管理和描述一个任务的数据结构，是内核“眼中”的任务。操作系统通过TCB来感知和控制任务的一切。

* 是什么？ 一个struct（在FreeRTOS中类型为tskTCB），由内核在创建任务时自动分配和初始化。

* 如何工作？ TCB包含了任务的所有元信息，调度器通过遍历和维护一个包含所有任务TCB的链表（或就绪列表、延迟列表等）来管理系统中的任务。

* TCB中包含哪些关键信息？

    * 栈顶指针（pxTopOfStack）： 指向该任务栈的当前栈顶，用于上下文切换时保存和恢复现场。

    * 任务状态（eState）： 记录任务当前处于就绪（Ready）、运行（Running）、阻塞（Blocked）、挂起（Suspended）中的哪一种状态。

    * 任务优先级（uxPriority）： 决定调度器选择哪个任务来执行的依据。

    * 任务函数指针（pxTaskFunction）： 指向任务的主体函数。

    * 任务名（pcTaskName）： 可读的任务标识，用于调试。

    * 事件列表项（xEventListItem）和状态列表项（xStateListItem）： 用于将TCB链接到不同的内核列表（如就绪列表、事件等待列表）中。

    * 栈起始地址（pxStack） 以及其他一些运行时参数和统计信息。

简单来说，TCB是内核用来“记住”一个任务所有关键信息的地方。

## 6.为什么mallc、free等函数在FreeRtos中不适用？

* 不适合用在资源紧缺的嵌入式系统中
* 这些函数的实现过于复杂、占据的代码空间太大
* 并非线程安全的(thread- safe)
* 运行有不确定性：每次调用这些函数时花费的时间可能都不相同
* 内存碎片化
* 使用不同的编译器时，需要进行复杂的配置
* 有时候难以调试

## 7.freertos为什么要有动态和静态两种创建任务方式？

|特性|	动态创建 (xTaskCreate)	|静态创建 (xTaskCreateStatic)|
|-------|------|------|
|内存来源|	从FreeRTOS管理的堆（Heap） 中自动分配任务栈和TCB（任务控制块）所需的内存。|	由开发者预先分配好内存（通常是全局静态数组），然后将内存地址作为参数传递给API。|
|内存管理|	依赖FreeRTOS的堆内存管理（如heap_1.c至heap_5.c）。|	不依赖FreeRTOS的堆管理，完全由开发者管理。|
|初始化|	简单，一行代码完成所有分配和初始化。|	稍复杂，需要先定义栈数组和TCB对象。|
|可靠性|	如果堆内存不足，会返回NULL，导致任务创建失败。|	内存是否足够在编译链接阶段就已确定，更加确定和可靠。|
|适用场景|	通用场景，原型开发，功能简单的应用。|	对可靠性、安全性、内存使用确定性要求极高的场景（如汽车电子、医疗、工业控制）。|

### 原因一：满足不同应用场景的需求（可靠性 vs. 便利性）
* 动态分配的优点（便利性）：

    * 开发简单快捷：无需关心内存的具体位置，API会处理一切。这在项目初期和快速原型开发中非常有用。

    * 节省RAM：多个任务可以共享整个堆空间。如果一个任务被删除，其内存可以被回收并用于创建新的任务或队列等，提高了内存利用率。

* 静态分配的优点（确定性、可靠性）：

    * 无运行时分配失败风险：内存是在编译期分配的，链接器会直接报错（如果RAM不足），避免了产品在运行时因内存不足而创建任务失败的风险。这对于安全关键（Safety-Critical） 系统至关重要（如ISO 26262, IEC 61508标准）。

    * <b>内存使用完全可控：</b>开发者可以精确地知道每个任务使用了多少RAM，以及这些RAM的具体位置。便于进行严格的内存分析和优化。

    * <b>无内存碎片化问题：</b>静态分配不会导致堆内存碎片化。在需要长期连续运行（几年甚至十几年）的系统中，内存碎片化可能导致运行多年后无法分配连续内存而崩溃，静态分配彻底避免了这个问题。

    * <b>可用于无堆的系统：</b>有些极其资源受限的嵌入式系统可能完全禁用动态内存分配（即没有堆）。在这种情况下，静态创建是唯一的选择。

### 原因二：兼容不同的设计和标准
* <b>汽车电子（AUTOSAR）、医疗、航空电子等领域有严格的编码标准（如MISRA C）。MISRA C标准通常不推荐甚至禁止使用动态内存分配，</b>主要是因为其不确定性和潜在的风险（如碎片化、分配失败、非确定性时间开销）。

    * 为了符合这些标准，就必须使用静态创建方式。

### 原因三：性能与效率的权衡
* 动态分配在创建任务时有额外的时间开销，因为它需要在堆中寻找合适大小的空闲内存块。

* 静态分配的创建过程更快，因为不需要搜索内存池，只需初始化已有的内存块即可，时间更具确定性。


## 8.FreeRtos中defaultTask的作用

在基于 FreeRTOS 的项目中，尤其是在使用 STM32CubeMX 这类工具生成初始代码时，你经常会遇到一个名为 defaultTask 的任务。它的常见作用包括：

1. 系统初始化后的入口点：当 FreeRTOS 内核（调度器）启动后，defaultTask 往往是第一个或早期被创建的任务。它负责完成一些初始化和启动工作。

2. 创建其他任务或资源：defaultTask 内部可能会创建应用程序中的其他任务、队列、信号量等系统资源。

3. 执行背景活动：它也常用于执行一些不需要高实时性的后台任务，比如监视系统状态、打印日志等。

4. 示例和模板：在自动生成的代码中，defaultTask 提供了一个任务的基本结构和示例，方便开发者参考和修改。

### ⚠️ 关于 defaultTask 的重要提示
* 名称并非强制："defaultTask" 这个名字是可以任意更改的。你完全可以将其重命名为 "MainTask", "AppTask", 或者其他任何能清晰表达其功能的名称。

* 属性可配置：如你代码中所见，它的栈大小 (stack_size)、优先级 (priority) 等属性都是可以根据实际需求调整的。

* 并非系统任务：defaultTask 本身并不是 FreeRTOS 内核的一部分，它和你自己创建的其他任务在本质上是相同的。FreeRTOS 内核自己会创建一些系统任务（如空闲任务 Idle Task），但 defaultTask 不属于它们。

### 代码片段示例

```C
/* Definitions for defaultTask */
osThreadId_t defaultTaskHandle; // 任务句柄
const osThreadAttr_t defaultTask_attributes = {
  .name = "defaultTask",        // 任务名称
  .stack_size = 128 * 4,        // 栈大小 (512字节)
  .priority = (osPriority_t) osPriorityNormal, // 优先级 (普通优先级)
};

/* 任务函数原型 */
void StartDefaultTask(void *argument);

/* 在某个初始化函数中（如MX_FREERTOS_Init）创建任务 */
defaultTaskHandle = osThreadNew(StartDefaultTask, NULL, &defaultTask_attributes);

/* 任务函数实现 */
void StartDefaultTask(void *argument)
{
  /* 初始化工作 */
  for(;;) {
    /* 任务的主体循环 - 在这里执行你的代码 */
    // 例如：printf("defaultTask is running\r\n");
    osDelay(10); // 延迟一段时间，让出CPU给其他同优先级任务
  }
}
```

* osThreadNew：这是 CMSIS-RTOS API 中用于创建任务的函数，底层会调用 FreeRTOS 的 xTaskCreate 或 xTaskCreateStatic。

* 任务函数 (StartDefaultTask)：必须是一个无限循环，且不能返回。

## 9.FreeRtos中栈空间、控制块、任务句柄的分工

以静态分配为例：

```c
// 任务的三大部分：
static StackType_t g_pucStackOfLightTask[128];  // 🏗️  任务的"地基和框架"（栈空间）
static StaticTask_t g_TCBofLightTask;           // 📋  任务的"身份证和管理表"（控制块）
static TaskHandle_t xLightTaskHandle;           // 🎯  任务的"句柄和遥控器"（任务句柄）
```

### 🔍 详细解析
1. static StackType_t g_pucStackOfLightTask[128];
    *  类型：StackType_t 数组（通常是 uint32_t）

    * 作用：为任务分配专用的栈空间

    * 大小：128 × 4 = 512 字节（在32位系统中）

    * 特点：

        * 静态分配，编译时确定大小

        * 用于存储任务执行时的局部变量、函数调用返回地址等

        * 每个任务都需要独立的栈空间

2. static StaticTask_t g_TCBofLightTask;
    * 类型：StaticTask_t 结构体

    * 作用：任务控制块（Task Control Block）

    * 内容：包含任务的所有管理信息：

        * 任务状态（就绪、阻塞、挂起等）

        * 任务优先级

        * 栈指针

        * 任务名称

        * 各种链表指针

    * 特点：FreeRTOS 用此结构体来管理和调度任务

3. static TaskHandle_t xLightTaskHandle;
    * 类型：TaskHandle_t（任务句柄，通常是指针）

    * 作用：任务的引用标识符

    * 用途：

        * 用于操作任务（删除、挂起、恢复等）

        * 用于任务间通信（通知、消息队列等）

        * 用于调试和监控

        ```c
        // 创建静态任务
        xLightTaskHandle = xTaskCreateStatic(
            Led_Test
            "LightTask",              // 任务名称
            128,                      // 栈深度（单位：字）
            NULL,                     // 传递给任务的参数
            osPriorityNormal,         // 任务优先级
            g_pucStackOfLightTask,    // 栈空间数组
            &g_TCBofLightTask         // 任务控制块
        );
        ```

简单来讲，栈空间是任务所需要的内存大小，控制块则存储了任务的各种信息，任务句柄则用来去对任务进行操作（比如创建、删除、休眠等）


### ⚖️ 静态分配 vs 动态分配

静态分配

```c
// 需要预先定义：
static StackType_t stack[128];
static StaticTask_t tcb;
static TaskHandle_t handle;

// 创建任务：
handle = xTaskCreateStatic(task_func, "Task", 128, NULL, priority, stack, &tcb);
```

动态分配（更简单）

```c
// 只需要定义句柄：
static TaskHandle_t handle;

// 创建任务：
xTaskCreate(task_func, "Task", 128, NULL, priority, &handle);
// FreeRTOS 会自动从堆中分配栈空间和TCB
```


## 10.FreeRTOS两种延时函数的区别是什么？

根据运行情况来讲，可以理解为vTaskDelay()是从调用其本身开始计时，vTaskDelayUntil()是从调用任务开始计时。

但是两个任务都非最高优先级的情况下，任务也并不能精准的延时去执行。vTasskDelay在这种情况下，任务肯定会被打乱执行，而vTaskDelayUntil虽然会周期的将任务从就绪变为阻塞，然后阻塞又变为就绪，但由于有比它更高优先级的任务，因此CPU也不会执行该任务。

## 9.FreeRtos的四种状态

* 就绪态：已经可以运行，等待调度器的切入
* 运行态：正在占用CPU运行
* 阻塞态：等待某个事件的到来，定时或者同步
* 挂起态：退出调度系统，调度器不可见，只能使用vTaskSuspend()挂起和vTaskResume()唤醒后进入就绪态

## 10.FreeRtos空闲任务

当 FreeRTOS 的调度器启动以后就会自动的创建一个空闲任务，这样就可以确保至少有一任务可以运行。但是这个空闲任务使用最低优先级，如果应用中有其他高优先级任务处于就绪态的话这个空闲任务就不会跟高优先级的任务抢占 CPU 资源。

空闲任务（Idle Task）并不仅仅是一个在CPU无事可做时运行的“占位符”。它的核心职责包括：

* 清理资源：这是最重要的一点。当其他任务被删除（例如调用 vTaskDelete()）时，该任务的内核对象（如TCB任务控制块）和其运行时在堆栈上分配的内存并不会被立即释放。这个清理工作是由空闲任务来完成的。空闲任务会在其循环中调用一个名为 prvCheckTasksTerminated() 的函数来检查并释放这些“已死亡”任务的资源。

* 执行空闲钩子函数：用户可以提供一个 vApplicationIdleHook() 函数，空闲任务会在每次循环时调用它。这通常用于低功耗模式（让MCU进入Sleep或Wait-for-Interrupt状态）、简单的后台状态监测等。

* 为某些功能提供执行上下文：例如，当使用 configUSE_TIMERS 为1时，定时器服务任务（Daemon Task）的指令就是由空闲任务发出的。

空闲函数绝不能被阻塞，如果空闲函数被阻塞，则整个系统会由于没有任务能够执行而“饿死”，另一方面空闲函数充当释放内存的任务，若空闲函数没有释放完就被阻塞，就算有任务能够执行也可能导致使用错误的内存空间。



## 11.FreeRtos中针对队列的操作为什么分为任务中和ISR中两种方式？

### 根本原因：任务与中断的上下文差异

#### 任务上下文（Task Context）：

* 任务是由 FreeRTOS 内核调度器管理的。

* 当任务运行并调用类似 xQueueSend() 的 API 时，它是在内核的控制之下。

* 如果队列操作导致了一个更高优先级的任务就绪（例如，因为发送数据唤醒了一个等待接收的任务），内核调度器可以立即执行上下文切换，挂起当前任务，去运行那个更高优先级的任务。这种行为是可预期的，也是抢占式调度器的核心功能。

#### 中断上下文（ISR Context）：

* 中断是硬件异步触发的，它的执行会抢占当前任务，且独立于内核调度器。

* ISR 的首要原则是快进快出，不能在其中执行可能引起阻塞或调度的操作。

* 如果在 ISR 中直接调用任务的 xQueueSend()，而这个函数试图进行任务切换，就会破坏内核的状态，因为调度器并没有为在中断中切换做好准备。这会导致系统行为异常甚至崩溃。

### 具体区别：API 函数与行为

为了解决上述问题，FreeRTOS 为几乎所有核心的、可能引起阻塞或切换的 API 都提供了两个版本：

* 用于任务的版本：xQueueSend(), xQueueReceive(), xSemaphoreTake(), xSemaphoreGive() 等。

* 用于 ISR 的版本：xQueueSendFromISR(), xQueueReceiveFromISR(), xSemaphoreGiveFromISR() 等。

它们的区别主要体现在：

|特性|	任务版 API (如 xQueueSend)|	ISR 版 API (如 xQueueSendFromISR)|
|------|-----|-----|
|调用上下文|	只能在任务中调用|	只能在 ISR 中调用|
|阻塞行为|可以阻塞。如果队列满，可以指定一个超时时间等待空间可用。|	绝不阻塞。如果队列满，函数会立即返回错误码 errQUEUE_FULL。|
|触发调度|	可能触发。如果发送数据解除了另一个更高优先级任务的阻塞，内核会立即进行上下文切换（如果启用了抢占）。|	不会立即触发。它不会在 ISR 内部进行上下文切换。取而代之的是，它会返回一个名为 pxHigherPriorityTaskWoken 的参数。|
|pxHigherPriorityTaskWoken 参数|	无此参数|	有这个关键参数。它是一个指向 BaseType_t 的指针。如果 API 调用确实解除了一个优先级高于当前被中断任务的任务的阻塞，那么这个变量会被设置为 pdTRUE。|

### 总结

为什么要有这种区分？

* 为了系统的稳定性和可靠性：防止在不受内核控制的 ISR 上下文中进行危险的任务调度操作。

* 为了保证中断的实时性：ISR 必须快速执行完毕，不能等待或阻塞。

* 为了实现高效的任务同步：通过 FromISR 版本和 pxHigherPriorityTaskWoken 参数，提供了一种安全、高效的机制，让中断能够及时通知并唤醒合适的任务来处理异步事件，同时将实际的调度工作推迟到安全的时候（中断退出时）进行。

## 12.FreeRtos中的ISR在执行的时候可不可以被阻塞

在 FreeRTOS 中，中断服务程序（ISR）绝对不可以阻塞。这是一个非常重要的设计原则，违反它会导致系统稳定性、响应速度和功能上的严重问题。


|特性/场景|	在任务 (Task) 中|	在中断服务程序 (ISR) 中|
|------|------|-----|
|能否阻塞|	✅ 可以|	❌ 绝对不可以|
|原因|	受内核调度器管理，阻塞后调度器可运行其他任务|	中断上下文独立于调度器，阻塞会冻结整个系统|
|可用 API|	标准 API (如 xQueueSend, vTaskDelay)|	专用的 FromISR 结尾 API (如 xQueueSendFromISR)|
|阻塞后果|	系统正常运行，调度器切换任务|	系统死锁或响应极度迟缓，所有同级及更低优先级中断被屏蔽，任务调度停止|
|设计原则|	完成任务功能，可等待资源|	快进快出，仅记录事件、发送通知，将耗时处理交由任务处理|

### ⚠️ 为什么不能阻塞？
ISR 不允许阻塞，主要源于其中断上下文这一特殊身份：

* 会冻结系统：ISR 的优先级高于所有任务。如果在 ISR 中阻塞，CPU 就无法返回到被中断的任务，也无法响应新的中断（除非是更高优先级的中断，但即使如此，系统状态也已异常）。这会导致整个系统“卡死”。

* 违背中断设计初衷：中断的核心目的是快速响应硬件事件。ISR 应该只完成最紧急、最精简的工作（例如读取数据寄存器、清除中断标志），然后迅速退出。任何可能等待的操作都应放到任务中去处理。

* 调度器在中断中无法工作：FreeRTOS 的任务调度器无法在 ISR 内部进行上下文切换。ISR 执行时，系统处于一种特殊状态，任务调度器通常被禁用。试图在此状态下调用可能导致任务切换的 API 是危险且不被支持的。

## 13.FreeRtos中任务什么时候会被切换？

FreeRTOS 中的任务切换发生在多种情况下，主要可以分为主动切换和被动切换两大类。

### 1. 主动切换（任务自愿放弃CPU）

#### 1.1 使用任务延迟函数

```c
// 任务主动延迟，让出CPU
vTaskDelay(pdMS_TO_TICKS(100)); // 延迟100毫秒
```

#### 1.2 等待事件或资源

```c
// 等待信号量
xSemaphoreTake(xSemaphore, portMAX_DELAY);

// 等待队列消息
xQueueReceive(xQueue, &data, portMAX_DELAY);

// 等待事件组
xEventGroupWaitBits(xEventGroup, BIT_0, pdTRUE, pdTRUE, portMAX_DELAY);
```

### 2. 被动切换（系统强制切换）

#### 2.1 中断服务程序(ISR)中

```c
// 在ISR中发送信号量，引起任务切换
void IRAM_ATTR gpio_isr_handler(void* arg) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    
    // 从中断给出信号量
    xSemaphoreGiveFromISR(xSemaphore, &xHigherPriorityTaskWoken);
    
    // 如果需要立即切换任务
    if(xHigherPriorityTaskWoken == pdTRUE) {
        portYIELD_FROM_ISR();
    }
}
```

#### 2.2 时间片调度

```c
// 在FreeRTOSConfig.h中配置时间片长度
#define configTICK_RATE_HZ (1000) // 1ms tick

// 相同优先级的任务会按时间片轮转调度
void vTask1(void *pvParameters) {
    for(;;) {
        // 任务1代码
        // 时间片用完后自动切换到同优先级任务2
    }
}

void vTask2(void *pvParameters) {
    for(;;) {
        // 任务2代码
        // 时间片用完后自动切换回任务1
    }
}
```

### 3.优先级引发的切换

#### 3.1 高优先级任务就绪

在FreeRTOS中有一个硬件定时器中断，由系统节拍器触发，通常每1ms触发一次，每次SysTick中断时：

        1.检查所有任务的延迟是否到期
        2.如果高优先级任务延迟到期，将其标记为就绪
        3.比较优先级，如果需要就触发任务切换

```c
void vHighPriorityTask(void *pvParameters) {
    for(;;) {
        // 当这个高优先级任务就绪时，会立即抢占低优先级任务
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void vLowPriorityTask(void *pvParameters) {
    for(;;) {
        // 如果高优先级任务就绪，此任务会被立即抢占
        // 执行一些工作...
    }
}
```

### 4. 系统调用引起的切换

#### 4.1 任务通知

```c
// 发送通知导致任务切换
xTaskNotifyGive(xTaskHandle);

// 或者
xTaskNotify(xTaskHandle, ulValue, eAction);
```

#### 4.2 资源释放

```c
// 释放互斥量可能导致高优先级任务就绪
xSemaphoreGive(xMutex);
```

### 5.任务切换时机总结表


|切换类型|	触发条件|	相关函数|
|------|-------|------|
|主动切换|	任务主动放弃CPU|	vTaskDelay(), taskYIELD()|
|时间片切换|	时间片用完|	自动由调度器处理|
|资源等待|	等待信号量/队列/事件|	xSemaphoreTake(), xQueueReceive()
|中断触发|	ISR中释放资源|	xSemaphoreGiveFromISR()
|优先级抢占|	高优先级任务就绪|	任何使高优先级任务就绪的操作
|任务通知|	发送任务通知|	xTaskNotifyGive(), xTaskNotify()

### 6.关键配置参数

在 FreeRTOSConfig.h 中影响任务切换的配置：

```c
#define configUSE_PREEMPTION             1   // 启用抢占式调度
#define configUSE_TIME_SLICING           1   // 启用时间片调度
#define configTICK_RATE_HZ               1000 // 系统时钟频率(Hz)
#define configMAX_PRIORITIES             5   // 最大优先级数量
```

## 14.FreeRtos中为什么往往需要在中断中唤醒高优先级任务？

等待系统节拍触发中断来切换任务所需的时间还是比较长，而在中断中唤醒高优先级任务然后让中断完毕后立即切换任务则花费的时间要少的多。

高优先级任务在唤醒之后我们往往要求其快速被执行，因此任务调度所花时间越少越好，其次就是安全性等角度的考虑，如果任务调度时间花费太长可能会导致一些意外产生。如电机出错我们希望高优先级任务立马执行电机错误修正的代码，而画的时间长一点点就可能导致电机损坏。

## 15. FreeRtos中优先级继承是什么？

### 什么是优先级继承？

优先级继承 是一种用于解决优先级反转问题的算法。

1. **优先级反转**

    * 定义：这是一种不希望出现的情况，即一个高优先级的任务因为被一个低优先级的任务所阻塞，而无法按时执行，导致中优先级的任务先于高优先级任务执行。

    * 根本原因：发生在多个任务共享同一个互斥锁（或信号量、其他资源）时。

2. **优先级继承如何工作**

    * 当一个高优先级任务因为请求一个已被低优先级任务占有的互斥锁而被阻塞时，优先级继承机制会临时将低优先级任务的优先级提升到与这个被阻塞的高优先级任务相同的级别。

    * 这样，这个（现在拥有高优先级的）原低优先级任务就能尽快地执行，释放它所占有的互斥锁。

    * 一旦互斥锁被释放，该任务的优先级就会自动恢复到他原来的优先级。

    * 然后，一直在等待的高优先级任务就能立刻获得互斥锁并继续执行。

**目的**：优先级继承通过临时提升低优先级任务的优先级，来“搭建一座桥梁”，让低优先级任务能尽快完成其临界区代码并释放资源，从而最大限度地减少高优先级任务被阻塞的时间。它并不能消除阻塞，但可以显著减轻阻塞的严重程度。

### 在FreeRtos中的使用

在 FreeRTOS 中，只有使用互斥锁（Mutex）时才会发生优先级继承，使用二值信号量（Binary Semaphore）或计数信号量（Counting Semaphore）则不会。

* **创建互斥锁：**

    ```c
    SemaphoreHandle_t xMutex;
    xMutex = xSemaphoreCreateMutex(); // 这个函数创建的互斥锁具有优先级继承特性
    ```

* **创建二值信号量：**

    ```c
    SemaphoreHandle_t xBinarySemaphore;
    xBinarySemaphore = xSemaphoreCreateBinary(); // 这个没有优先级继承特性
    ```

因此，在实现任务间同步以访问共享资源时，如果涉及优先级问题，应始终使用互斥锁而不是二值信号量，以避免优先级反转。

## 16.FreeRtos中的递归锁

### 什么是递归锁？

递归锁（也称为可重入互斥锁）是一种特殊的互斥锁，它允许同一个任务多次获取（Take）该锁，而不会造成死锁。

这与普通的互斥锁形成鲜明对比：

* 普通互斥锁：如果一个任务已经获取了一个互斥锁，再次尝试获取同一个互斥锁时，任务会被永久阻塞，因为它在等待一个自己永远不会释放的锁，从而导致死锁。

* 递归互斥锁：内部有一个计数器来记录它被同一个任务获取的次数。任务每次成功获取锁，计数器加一；每次释放锁，计数器减一。锁只有在计数器减回到 0 时，才会真正被释放，从而变得可供其他任务使用。

核心思想：递归锁记录所有者（任务）和所有权计数。只有锁的原始获取者才能获取它多次，并且必须释放相同的次数才能完全释放该锁。

### 为什么需要递归锁

递归锁的主要用途是保护可能从多个函数层级调用、并且可能递归或相互调用的代码。

**典型场景：**

假设一个任务调用了一个函数 A()，该函数获取了一个互斥锁来访问共享资源。在持有锁的过程中，A() 又调用了另一个函数 B()，而 B() 也需要访问同一个共享资源，因此它也需要获取同一个互斥锁。


* 如果使用普通互斥锁，任务在 B() 中尝试获取它已经持有的锁时，会立即死锁。

* 如果使用递归互斥锁，B() 可以成功再次获取该锁（计数器从1增加到2）。当 B() 执行完毕释放锁时，计数器减为1，锁并未真正释放。最后 A() 释放锁，计数器归零，锁才真正被释放。

这允许你编写更模块化的代码，其中每个函数都独立地管理自己的同步，而不必担心调用它的上层函数是否已经持有了锁。

## 17.什么是临界资源？什么是临界区？

### 临界资源

**定义**：临界资源是指在同一时刻只能被一个任务访问的共享资源。
常见的临界资源包括：

* 全局变量
* 外设寄存器（如UART、SPI、I2C等）
* 共享内存缓冲区
* 文件系统
* 打印输出设备
* 硬件资源（如定时器、ADC等）

### 临界区（Critical Section）

定义：临界区是指访问临界资源的那段代码。在临界区内，必须保证代码的原子性执行，不能被其他任务打断。

为什么需要临界区：

* 防止数据竞争（Race Condition）
* 保证操作的原子性
* 避免数据不一致

### FreeRtos中临界区保护方法：

#### 1. 任务级临界区保护

```c
// 方法1：关闭所有中断
taskENTER_CRITICAL();
// 访问临界资源的代码
g_counter++;
taskEXIT_CRITICAL();

// 方法2：关闭调度器（不关中断）
vTaskSuspendAll();
// 访问临界资源的代码
g_counter++;
xTaskResumeAll();
```

#### 2. 中断级临界区保护

```c
// 在中断服务程序中使用
UBaseType_t uxSavedInterruptStatus;
uxSavedInterruptStatus = taskENTER_CRITICAL_FROM_ISR();
// 访问临界资源的代码
g_counter++;
taskEXIT_CRITICAL_FROM_ISR(uxSavedInterruptStatus);
```

### 使用原则

1. 临界区越短越好 - 减少对系统实时性的影响
2. 避免嵌套 - 防止死锁
3. 不要在临界区内调用阻塞函数 - 如vTaskDelay()
4. 考虑使用其他同步机制 - 如互斥量、信号量等

## 18.为什么临界区内必须保证代码的原子性执行，不能被其他任务打断

### 什么是原子性

原子性意味着一个操作要么完全执行完成，要么完全不执行，不能被中途打断。就像化学中的原子一样，是不可再分的最小单位。

### 为什么需要原子性？

#### 1. 防止数据竞争（Race Condition）

当多个任务同时访问同一个共享资源时，如果操作可以被打断，就会出现数据竞争：


    任务A: 读取 counter = 5
    任务A: 计算 5 + 1 = 6
    [被任务B打断]
    任务B: 读取 counter = 5 (还是旧值!)
    任务B: 计算 5 + 1 = 6  
    任务B: 写入 counter = 6
    [任务A恢复]
    任务A: 写入 counter = 6

    结果：两次加1操作，但counter只增加了1！

#### 2. 保证复合操作的完整性
很多看似简单的操作实际上包含多个步骤：

* i++ = 读取 + 计算 + 写入
* 结构体赋值 = 多个字段逐一赋值
* 硬件配置 = 多个寄存器顺序设置

#### 3. 维护数据一致性
相关的数据必须作为一个整体来更新：

```c
// 这些数据必须同时更新
position.x = new_x;
position.y = new_y;  // 如果在这里被打断，位置数据就不一致了
position.timestamp = current_time;
```

#### 4.CPU指令级别的考虑

即使是简单的操作，在CPU指令级别也可能需要多个时钟周期：

```c
; i++ 对应的汇编指令
LDR  R0, [g_counter]    ; 1. 从内存加载值到寄存器
ADD  R0, R0, #1         ; 2. 寄存器值加1
STR  R0, [g_counter]    ; 3. 存储回内存
```

如果在这3条指令之间发生任务切换，其他任务看到的就是不完整的状态。

## 19.所有非原子化的操作是否都要保证其原子性？

并非所有资源都是临界资源，也并非所有操作都需要保证原子性。

将非临界资源当作临界资源来处理，过度使用互斥锁、关中断等同步机制，反而会不必要的降低系统性能和响应能力。

### 什么时候不需要保证原子性？（非临界资源）
首先临界资源一定要保证原子性，因为临界资源是指同一时刻只能被一个任务访问的共享资源，作为共享资源，如果临界资源的原子性无法保证，操作临界资源的时候由于任务切换等原因而被打断，可能导致数据混乱。

如果一个资源同时满足以下两个条件，那么它通常不是临界资源，对其的操作也不需要保证原子性：

1. 只读数据：多个任务同时读取同一个数据，而该数据在系统运行时永远不会被修改。

    * **例子**：存储在Flash中的常量查找表、配置参数（在初始化后不再修改）、设备ID等。

    * **为什么安全**：因为读取操作不会改变数据状态，无论多少个任务同时读，都不会导致数据不一致。

2. 完全独立的数据：每个任务都拥有其专属的变量或内存区域，即使这些变量名相同（例如函数内的局部变量、通过参数传递的私有数据副本）。

    * **例子**：任务栈中的局部变量。每个任务都有自己的栈空间，即使两个任务调用同一个函数，函数内的int i变量也是分别存储在两个不同的栈上，互不干扰。

    * **为什么安全**：资源在物理上就是分离的，不存在共享，自然不会产生竞争。

3. 线程局部存储：虽然FreeRTOS标准版本不直接支持，但可以通过设计模式实现每个任务访问自己独有的全局变量实例。

* **例子**：一个全局结构体数组TaskContext_t taskContext[MAX_TASKS]，每个任务通过自己的ID号来访问属于自己的那一个元素taskContext[myTaskId]。

* **为什么安全**：每个任务访问的是数组中的不同元素，没有交集。

### 什么时候必须保证原子性？（临界资源）

当一个资源是可写的并且可能被多个执行上下文（任务/中断）访问时，它就是临界资源，必须保护其访问的原子性。

“执行上下文”包括：

* 两个或更多任务

* 一个任务和一个中断服务程序（ISR）

* 两个或更多ISR（较少见）

**判断的核心是：是否存在“读-改-写”或“写-写”的交叉风险。**

### 总结


|资源类型|	是否需要保护？|	原因|
|-----|-----|----|
|只读全局数据|	否|	并发读取不会改变数据状态，是安全的。|
|任务局部变量|	否|	数据本身存储在私有栈中，无共享。
|可写的全局变量/硬件|	是|	存在“读-改-写”风险，会导致数据竞争或硬件配置错误。
|被多个任务/中断访问的复杂数据结构（链表、队列）|	是|	中间状态可能被破坏，导致系统崩溃。


**核心思想**：不要盲目地为所有全局变量加锁。首先分析数据的访问模式（谁读？谁写？），**只对那些真正共享的、可写的资源施加保护**。这样才能设计出既正确又高效的高性能嵌入式系统。

## 20.FreeRtos中任务通知的有什么作用？

### 任务通知的作用

任务通知可以实现多种传统的通信机制的功能，但通常更高效，因为它的实现不涉及创建额外的内核对象（如队列、信号量、事件组等），从而节省了内存并减少了处理开销。

其主要作用包括：

1. **替代二值信号量（Binary Semaphore）**： 用于任务与任务、任务与中断之间的同步。例如，通知一个任务某个事件已经发生。

2. **替代计数型信号量（Counting Semaphore）**： 通过递增任务的通知值来“释放”信号量，任务可以“获取”并递减该值。

3. **替代事件组（Event Group）**： 可以更新任务通知值中的特定位，任务可以等待一个或多个位的置位。

4. **替代队列（Queue）**： 可以向任务“发送”一个 32 位的数据。虽然只能传递一个数据，但对于很多场景已经足够。

5. **直接解除任务阻塞**： 即使不传递任何数据，也可以单纯地解除一个正在等待某个事件的任务的阻塞状态。

### 任务通知的优势与劣势

**优势（为什么用它？）**
1. **速度更快**： 比传统的队列、信号量等快得多（根据 FreeRTOS 官方文档，速度提升可达 45%）。

2. **内存占用更少**： 不需要创建额外的通信对象（队列、信号量等），每个任务的通知功能是任务控制块（TCB）中固有的，因此节省了 RAM。

**劣势（什么时候不用它？）**
1. **只能有一个发送者**： 这是最大的限制。任务通知是直接发送给特定任务的。如果有多个不同的发送者（任务或中断）需要通知同一个任务，使用任务通知会变得复杂，因为你需要管理多个发送者对同一个通知值的写入冲突。在这种情况下，使用传统的事件组（多个发送者设置不同的位）或队列（多个发送者发送数据）可能更合适。

2. **接收者只能有一个**： 任务通知是“一对一”的通信。一个通知只能被一个任务接收。而一个队列、信号量或事件组可以被多个任务等待（“一对多”），这在某些场景下是必要的。

3. **数据的局限性**： 只能传递一个 32 位的值。对于更复杂的数据结构，仍需使用队列。

4. **状态的局限性**： 任务的通知状态只有两种：“未决”（pending） 或 “非未决”（not pending）。这意味着它无法像计数型信号量那样累积多次“释放”操作（除非使用 eIncrement 模式来增加计数，而不是简单地设置状态）。

### 关键API函数
任务通知有两套 API：一套用于任务中发送，一套用于中断服务程序（ISR）中发送（以 FromISR 结尾）。

**发送通知（Sender）**
* xTaskNotifyGive() / vTaskNotifyGiveFromISR()

    * 主要用于模拟“给出”信号量的操作。它会增加接收任务的通知值，并将其状态设置为“未决”。接收任务通常使用 ulTaskNotifyTake() 来等待这个通知。

* xTaskNotify() / xTaskNotifyFromISR()

    * 功能最强大的通知函数。它通过一个 eAction 参数来指定如何更新接收任务的通知值和状态，提供了极大的灵活性。

    * eAction 参数常见值：

        * eNoAction： 仅设置通知状态为“未决”，不修改通知值。相当于轻量级的二值信号量。

        * eSetBits： 对通知值进行按位或（OR）操作。相当于事件组。

        * eIncrement： 将通知值加 1。相当于计数型信号量。

        * eSetValueWithOverwrite： 直接覆盖写入通知值。

        * eSetValueWithoutOverwrite： 如果通知还未被取走（状态为“未决”），则不覆盖写入。

**接收通知（Receiver）**
* ulTaskNotifyTake()

    * 专门设计用于与 xTaskNotifyGive() 配合使用，模拟“获取”信号量。

    * 参数 xClearCountOnExit：

        * 设为 pdTRUE： 在函数退出时，将通知值清零。模拟二值信号量。

        * 设为 pdFALSE： 在函数退出时，将通知值减一。模拟计数型信号量。

    * 返回值： 在函数退出前，通知值的值（对于计数型信号量场景非常有用）。

* xTaskNotifyWait()

    * 功能更强大的等待函数，通常与 xTaskNotify() 配合使用。

    * 可以指定在进入函数时清除通知值中的哪些位（ulBitsToClearOnEntry），以及在退出时清除哪些位（ulBitsToClearOnExit）。

    * 还可以将接收到的通知值保存到一个变量中（pulNotificationValue）。

## 总结与选择指南

选择通信机制时，可以遵循以下决策流程：

1. **需要传递数据吗？**

    * 是 -> 进入第2步。

    * 否 -> 你只需要同步，进入第4步。

2. **数据是什么形式？**

    * 单个32位值/指针 -> 考虑任务通知（如果是一对一）或队列（如果是多对多）。

    * 结构体/大数据 -> 必须使用队列。

    * 字节流（如UART） -> 考虑流缓冲区（单读者单写者）。

    * 离散消息包 -> 考虑消息缓冲区（单读者单写者）。

3. **有多少发送者和接收者？**

    * 一对一 -> 任务通知（性能最佳）或流/消息缓冲区。

    * 多对一、一对多、多对多 -> 队列或事件组（如果不传递数据）。

4. **只需要同步（不传数据）？**

    * 保护共享资源（互斥） -> 互斥量。

    * 管理N个同类资源 -> 计数信号量。

    * 通知一个事件发生（一对一） -> 任务通知（最佳）或二值信号量。

    * 通知一个事件发生（多对多） -> 事件组。

    * 等待多个事件的复杂组合 -> 事件组。
