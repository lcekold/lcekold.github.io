## 一、DMA、MDMA、DMA2D都有什么区别

DMA挂载在AHB总线上

MDMA：高速主DMA，专做内存到内存的超高速传输，挂载在AXI总线上，支持更高的传输速率和更复杂的传输模式，适用于大数据量的传输。

DMA2D是专门用于图像处理的DMA控制器，支持图像格式转换、颜色空间转换和图像混合等操作，适用于图形显示和图像处理应用。

## 二、D1 Domain、D2 Domain、D3 Domain

D1 Domain：

    * D1 域中的各个外设是挂在 64 位 AXI 总线组成 67 的矩阵上。

    * 外接的主控是CPU,SDMMC1,MDMA,DMA2D,LTDC，D2 to D1总线。

    * 外接的从设备是 AHB3 总线，Flash A，Flash B，FMC 总线，QSPI 和 AXI SRAM， APB3 总线是由AHB3分出来的。

D2 Domain：

    * D2 域的各个外设是挂在 32 位 AHB 总线组成 109 的矩阵上。

    * 外接的主控是 D1-to-D2 AHB 总线，AHBP 总线，DMA1，DMA2，Ethernet MAC，SDMMC2，USB HS1 和 USB HS2。

    * 外接的从设备是 SRAM1，SRMA2，SRAM3，AHB1，AHB2，APB1，APB2，D2-to-D1 AHB总线和 D2-to-D3 AHB 总线。

D3 Domain:

    * D3 域的各个外设是挂在 32 位 AHB 总线组成 3*2 的矩阵上。

    * 外接的主控 D1-to-D3 AHB 总线，D2-to-D3 AHB 总线和 BDMA。

    * 外接的从设备是 AHB4，SRAM4 和 Bckp SRAM。另外 AHB4 也是这个总线矩阵分支出来的，然后再由 AHB4 分支出 APB4 总线。


# 项目流程以及遇到的问题


## 一、 网络接收与数据组帧（WiFi 透传 JPEG）
【实现方式】

上位机（比如你用 Qt 开发的程序）将摄像头采集的画面压缩为 JPEG 格式，通过 UDP 协议发送给 STM32 端的 WiFi 模块。STM32 底层通过普通 DMA 将接收到的网络 payload 搬运到指定的 SRAM 接收缓冲区中。

【遇到的问题：花屏与解码器 HardFault】

UDP 是不可靠传输，在无线环境下必然存在丢包。如果由于丢包导致一段 JPEG 数据不完整（比如丢失了关键的霍夫曼表或图像尾部标志），直接强行喂给 STM32 的硬件 JPEG 解码器，轻则画面出现大面积马赛克/色彩错乱（花屏），重则导致解码硬件死锁甚至触发单片机的 HardFault 中断。

【解决方案：应用层封包与完整性校验】

1. 增加帧头： 在上位机发送时，给每个 UDP 包加上自定义报头（包含帧序号、总包数、当前包偏移量）。

2. 丢帧策略： STM32 端在组包时，如果发现某一帧少了一个分片，直接果断丢弃整帧，绝不将残缺的数据送入解码器。

3. 头尾校验： 在启动 MDMA 解码前，扫描缓冲区的头部是否为 0xFF 0xD8 (SOI，图像开始)，尾部是否为 0xFF 0xD9 (EOI，图像结束)，双重确保数据结构的完整性。

## 二、硬件解码与高速调度（JPEG Codec + MDMA）

【实现方式】

确认接收到完整的 JPEG 帧后，配置 MDMA（Master DMA）。MDMA 采用节点链表模式，全自动地将 SRAM 中的 JPEG 压缩码流源源不断地送入硬件 JPEG 解码器的输入 FIFO，同时将其解码输出的 YCbCr 原始像素数据搬运到另一块内存中。

【遇到的问题：Cache 数据一致性（经典大坑）】

STM32H7 带有 L1-Cache（一级缓存）。CPU 认为它已经处理好接收数据了，但数据可能还停留在 D-Cache 里，没有真正写进 SRAM。此时 MDMA 去 SRAM 里拿数据喂给解码器，拿到的其实是“旧数据”或者“乱码”，导致解码失败。
相反，MDMA 把解码好的 YCbCr 放进内存后，CPU 如果直接去读，读到的可能也是 Cache 里的历史残留。

【解决方案：手动维护 Cache 或 配置 MPU】

* 方案 A（软件）： 在启动 MDMA 前，调用 SCB_CleanDCache() 强制把 Cache 里的数据刷进内存；在 MDMA 搬运完成后，调用 SCB_InvalidateDCache() 让 CPU 的 Cache 失效，强制去内存读最新数据。

* 方案 B（硬件）： 通过配置 MPU（内存保护单元），将存放 JPEG 接收区和 YCbCr 输出区的内存段属性设置为 Non-Cacheable（不可缓存），从根源上避开一致性问题（推荐用于这类由外设主导的大数据量区域）。

## 三、 像素加工与跨域传输（DMA2D 硬件加速）

【实现方式】

解码器输出的 YCbCr 数据不能直接点亮屏幕。此时配置 DMA2D 工作在**“存储器到存储器并执行 PFC（像素格式转换）”**模式。将源端设置为 YCbCr 缓冲区，目标端设置为显存（Frame Buffer），DMA2D 会在后台利用硬件乘加器，瞬间将画面转换为 RGB565 格式并写入显存。

【遇到的问题：总线拥堵导致帧率下降】

STM32H7 虽然主频高达 400MHz+，但如果所有数据（接收缓冲、解码缓冲、显存）都挤在一块内存里（比如全放在 AXI-SRAM），MDMA、DMA2D 和 LTDC 同时去读写这块内存，会导致严重的 AHB/AXI 总线竞争。表现为 DMA2D 转换极慢，甚至 LTDC 因为拿不到数据导致屏幕闪烁。

【解决方案：内存分域布局优化】

利用 H7 的 D1/D2/D3 域架构进行物理分流：

* 将 WiFi 接收缓冲区和 JPEG 解码输出区 (YCbCr) 放在 D2 域的 SRAM1/SRAM2。

* 将 双帧缓冲显存 (RGB565) 放在 D1 域的 AXI-SRAM 或外部 SDRAM。
这样，MDMA 在 D2 域干活，LTDC 在 D1 域干活，DMA2D 作为桥梁跨域传输，最大程度利用了总线矩阵的并行能力。

## 四、 画面输出与防撕裂机制（LTDC + 双帧缓冲）

【实现方式】

在内存中开辟 Buffer A 和 Buffer B 两块显存。LTDC 一直循环读取 Buffer A 输出到 4.3 寸 TFT 屏；同时，DMA2D 将刚转换好的新一帧数据写入 Buffer B（后台）。

【遇到的问题：画面撕裂（Tearing）】

如果 DMA2D 刚把新画面写进 Buffer B，你就立刻把 LTDC 的指针切到 Buffer B，而此时 LTDC 刚好扫描到屏幕正中间。那么屏幕上半部分显示的是旧帧，下半部分瞬间变成了新帧，出现明显的“画面断层”或“撕裂感”。

【解决方案：垂直同步中断（Vsync）精准切换】

绝不随意切换显存指针。开启 LTDC 的 Line Event Interrupt（行中断/垂直同步中断）。
当 DMA2D 后台绘制完成后，仅仅立一个 Flag（比如 frame_ready = 1）。
必须等到 LTDC 扫描完屏幕的最后一行，触发了 Vsync 中断时，在中断服务函数里检查到 Flag 置位，才将 LTDC 的底层显存地址寄存器切换到 Buffer B。这样保证了每一帧都是从屏幕最左上角的第一行开始全新扫描的。
