# 第2章 EtherCAT 协议

> 本章是全书的地基。搞懂这一章，后面所有硬件、驱动、伺服协议都是它的展开。
>
> 一句话主线：**主站发一帧 → 帧穿过每一个从站 → 每个从站顺手读写自己那一格 → 帧绕回来，主站拿到所有人的最新数据。**

---

## 2.1 EtherCAT 系统组成

EtherCAT 充分利用以太网的**全双工**特性，使用**主从模式**的介质访问控制（MAC）：

* **主站**发送以太网帧给各从站；
* **从站**从数据帧中**抽取**数据，或把数据**插入**数据帧；
* 主站用**标准以太网接口卡**，从站用**专用的 EtherCAT 从站控制器 ESC**（EtherCAT Slave Controller）；
* 物理层用标准以太网物理层器件。

**从以太网的角度看**：一个 EtherCAT 网段就相当于**一个以太网设备**——它接收和发送标准的 ISO/IEC 8802-3 以太网数据帧。但这个"设备"内部其实由多个 EtherCAT 从站串成：

1. 从站直接处理收到的报文，提取或插入用户数据；
2. 然后把报文转给下一个从站；
3. 最后一个从站把处理完的报文**发回**，由第一个从站作为响应送回主站。

### 2.1.1 EtherCAT 主站组成

**图 2.1　EtherCAT 主站组成**（原书 p.17）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F003_p017.png" alt="图 2.1 EtherCAT 主站组成">

主站使用**标准的以太网控制器**，传输介质通常用 **100BASE-TX 规范的 5 类 UTP 线缆**。

```
标准以太网通信控制器芯片 --MII--> 物理层芯片 PHY --> 隔离变压器 --> RJ45
```

* **通信控制器**负责以太网数据链路层的 MAC 功能；
* **物理层芯片 PHY** 负责数据编码、译码和收发；
* 两者之间通过 **MII**（Media Independent Interface，介质无关接口）交互数据。

> **MII 的意义**：它把"数据链路层"和"物理层"彻底解耦，定义了与传输介质无关的标准电气和机械接口。所以以太网可以换任何介质（双绞线、光纤、同轴），上层软件一行都不用改。

**MII 具体是怎么"解耦"的？**

解耦的办法其实很朴素：**在两层之间插一个双方都必须遵守的中间约定**，谁也不用知道对方内部在干什么。

**第一步，看 MII 都定义了哪些线。** MII 规定了一组固定的信号，大致分四类（100M 速率下）：

| 类别 | 信号 | 作用 |
| :--- | :--- | :--- |
| 发送 | `TX_CLK`、`TXD[3:0]`、`TX_EN`、`TX_ER` | 发送时钟、4 位并行发送数据、发送使能、发送出错 |
| 接收 | `RX_CLK`、`RXD[3:0]`、`RX_DV`、`RX_ER` | 接收时钟、4 位并行接收数据、接收有效、接收出错 |
| 冲突 | `COL`、`CRS` | 冲突检测、载波侦听（半双工时代遗留） |
| 管理 | `MDC`、`MDIO` | 配置 PHY 的串行管理总线（速率、双工、自协商） |

**第二步，看这套约定为什么就解耦了。** 关键是在**数据**和**控制**上各定死一件事：

* **数据按统一格式交**：MAC 要发的帧，不再以"线上的电平"形式出现，而是**拆成 4 位一组的半字节（nibble），在 `TX_CLK` 的节拍下一组一组送出去**；接收方向反过来，PHY 把收到的数据同样以 4 位一组交给 MAC。
* **边界按统一信号标**：一帧从哪开始、到哪结束，靠 `TX_EN` / `RX_DV` 拉高拉低来标；出错就拉 `TX_ER` / `RX_ER`。

于是**两边各自只需要管好自己那一侧**：

| 视角 | 它看到的／要做的 | 它完全不知道的 |
| :--- | :--- | :--- |
| **MAC 侧** | 按节拍收发 4 位数据，看 `TX_EN`/`RX_DV` 定帧边界，看 `TX_ER`/`RX_ER` 判错误 | 下面接的是双绞线、光纤还是背板；用了什么编码和调制 |
| **PHY 侧** | 100BASE-TX：4B/5B 编码 → 扰码 → MLT-3 → 双绞线<br>100BASE-FX：4B/5B → 光模块<br>100BASE-T2：PAM5 × 3 → 双绞线 | 上面跑的是 IP 还是 EtherCAT，帧里是什么业务 |

```
   MAC  ──[ MII：4 位数据 + 时钟 + 使能/错误 ]──  PHY  ──▶  介质
（只管收发格式统一的数据）                  （编码、调制、驱动全在这层消化掉）
```

**第三步，这一步换来了什么。**

对 **MAC** 来说，它拿到的永远是"**按时钟节拍排好的 4 位数据 + 几个使能/错误标志**"。它**既不知道**线路那头是双绞线、光纤还是背板，也**不知道**下面用了 4B/5B、MLT-3 还是光模块——**这些差异全被 PHY 吸收掉了**。所以想换介质时，**只需要换 PHY**，MAC、驱动程序、协议栈、应用程序**一行都不用改**。这就是"介质无关"这四个字的实际含义。

> 类比：MII 像**标准 USB 接口**。你插U盘、插键盘、插网卡，电脑（相当于 MAC）都只需要"按 USB 协议收发数据"，根本不用知道那设备里面是闪存芯片还是机械结构（相当于 PHY 和介质的差别）。**换设备只需换外设，电脑不用换。** MII 就是 MAC 和 PHY 之间的那个 USB 口。

**两点容易混的地方：**

* **MII 只管数据通道，不管配置。** 想让 PHY 跑 100M 还是 10M、全双工还是半双工、要不要自协商，走的是另一条独立的管理总线 **MDC/MDIO**。所以是"**数据走 MII，配置走 MDIO**"，两条路分工明确。
* **速率变了，接口就变宽。** 100M 用的就是 MII（4 位 @ 25MHz）；1000M 带宽是它的 10 倍，接口扩成 **GMII**（8 位 @ 125MHz）——**接口本身按位宽和时钟适配速率，但"解耦"这个思路没变**。

**这对 EtherCAT 从站意味着什么？** 正因为有 MII，ESC 芯片（如 ET1100）的 MII 端口**可以接任何满足 MII 规范的 PHY 芯片**，不必和某一家的器件绑死——这也解释了第 4 章为什么把 **PHY 选型**单独列成一节。而且那一节的结论很有意思：功能上"谁都兼容"，**但 ET1100 为了压低转发延时，把 MII 接口的发送 FIFO 省掉了**，反过来对 PHY 提出了额外要求。也就是说，**MII 给了你选择的自由，但"低延时"这个目标会把选择范围重新收窄**——这是第 3、4 章要展开的内容。

* **隔离变压器**：实现信号隔离，提高通信可靠性（也防止不同设备地电位差烧芯片）。
* 基于 PC 的主站通常用**网络接口卡 NIC**，网卡芯片里已经把通信控制器和物理收发器集成在一起了；嵌入式主站则通常把通信控制器**内嵌到微处理器**里。

### 2.1.2 EtherCAT 从站组成

**图 2.2　EtherCAT 物理层连接原理图**（原书 p.18）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F004_p018.png" alt="图 2.2 EtherCAT 物理层连接原理图">

**图 2.3　EtherCAT 从站组成**（原书 p.18）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F005_p018.png" alt="图 2.3 EtherCAT 从站组成">

一个从站同时干两件事：**通信**和**控制应用**。由四部分组成：

| 组成 | 作用 |
| :--- | :--- |
| **① ESC（从站控制芯片）** | 处理 EtherCAT 数据帧，用双端口存储区实现主站与从站本地应用的数据交换 |
| **② 从站控制微处理器** | 从 ESC 读控制数据、实现设备控制、采样反馈写回 ESC |
| **③ 物理层器件** | 用 MII 时需要 PHY + 隔离变压器；用 EBUS 时不需要任何额外芯片 |
| **④ 其他应用层器件** | A/D、D/A、电机脉冲输出等，视控制对象而定 |

#### ESC 的工作方式（关键）

* 各从站 ESC 按**各自在环路上的物理位置顺序**移位读写数据帧；
* 报文经过时，ESC 从报文中**提取发给自己的输出命令数据**，存入内部存储区；同时把**内部存储区的输入数据写回**相应子报文；
* 数据的提取和插入**全部由数据链路层硬件完成**——不占用微处理器，所以极快。

#### ESC 的四个数据收发端口

ESC 有 4 个端口，每个都能收发以太网帧。**帧在 ESC 内部的传输顺序是固定的**：

> **端口 0 进入 → 端口 3 → 端口 1 → 端口 2 → 端口 0 出去**

**如果 ESC 检测到某个端口没有外部连接，会自动闭合（旁路）此端口**，数据自动回环转发到下一端口。这就是"末站不用特意配置"的原因。

一个从站**至少用两个端口**；用多个端口就能构成各种物理拓扑（星形、树形）。

#### 两种物理层接口：MII vs EBUS

| | MII | EBUS |
| :--- | :--- | :--- |
| 本质 | 标准以太网物理层接口，**需外部 PHY 芯片** | 倍福用 **LVDS**（低压差分信号）定义的数据传输标准，**直连 ESC** |
| 单端口传输延时 | 约 **500ns** | 约 **100ns** |
| 最大距离 | 100m（标准以太网） | **10m** |
| 适用 | 通用从站、跨柜连接 | 距离很近的 I/O 设备、伺服驱动器之间互联 |

> **EBUS 为什么快 5 倍**：它砍掉了整个 PHY 芯片和变压器这一层"翻译工作"，信号直接从芯片到芯片。代价是距离短——这很合理，**同一机柜里几个模块挨着插，没必要上 100 米级的驱动能力**。

### 2.1.3 EtherCAT 物理拓扑结构

**图 2.4　ESC 数据传输顺序（数据从端口 0 进、端口 3 出）**（原书 p.19）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F006_p019.png" alt="图 2.4 ESC 数据传输顺序（数据从端口 0 进、端口 3 出）">

**图 2.5　EtherCAT 线型拓扑结构**（原书 p.20）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F007_p020.png" alt="图 2.5 EtherCAT 线型拓扑结构">

**逻辑上**，EtherCAT 网段内的从站构成一个**开口的环型总线**：

* 一端：主站直接或通过标准交换机**插入**以太网数据帧；
* 另一端：接收经过处理的数据帧；
* 最后一个从站把数据帧**返回**主站。

**物理上**，因为从站可以"分支"而不打破逻辑环路，所以能构成各种拓扑：

* 线形（菊花链）、树形、星形，以及任意组合；
* 布线非常灵活。

> **怎么理解"分支不打破环路"**：把数据流想象成送快递的路线图。一个从站的 4 个端口就像一个**四岔路口**：快递按规定顺序走完四个口，虽然物理上像是"分叉"了，但**逻辑上的行走顺序始终是一条确定的路线**——这就是"分支结构 + 逻辑环路"并存的意思。

## 2.2 EtherCAT 数据帧结构

**图 2.6　EtherCAT 报文嵌入以太网数据帧**（原书 p.21）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F008_p021.png" alt="图 2.6 EtherCAT 报文嵌入以太网数据帧">

EtherCAT **直接使用以太网数据帧传输**，帧类型（EtherType）为 **0x88A4**。

```
┌──────────┬──────────┬──────────┬─────────┬──────────────┬─────┐
│ 目的地址  │ 源地址    │ 帧类型    │ EtherCAT│ EtherCAT     │ FCS │
│ 6 字节    │ 6 字节    │ 0x88A4   │ 头 2字节 │ 数据 44~1498B │ 4B  │
└──────────┴──────────┴──────────┴─────────┴──────────────┴─────┘
```

* **EtherCAT 头** 2 字节：后续 EtherCAT 数据长度 + 类型（Type=1 表示后面是 EtherCAT 子报文）。
* **EtherCAT 数据区**由一个或多个**子报文（Datagram）**组成；**每个子报文对应独立的设备或从站存储区域**。

### 子报文结构

每个子报文 = **10 字节子报文头 + 数据 + 2 字节 WKC**：

| 字段 | 含义 |
| :--- | :--- |
| **命令** | 寻址方式 + 读写方式的组合（见 2.3.4） |
| **索引** | 帧编码，可用于区分周期/非周期报文 |
| **地址区** | 4 字节：设备寻址时高 16 位是站地址、低 16 位是站内偏移；逻辑寻址时整体是逻辑地址 |
| **长度** | 数据区长度 |
| **R** | 保留位 |
| **M** | 后续子报文标志（more），最后一个是 0 |
| **状态位** | 中断到来指示等 |
| **数据区** | 子报文数据结构，具体含义由命令和地址决定 |
| **WKC** | 工作计数器，见下 |

### 工作计数器 WKC（Working Counter）

**WKC 是 EtherCAT 最巧妙的自检机制之一。**

* 主站发出去时，WKC = 0；
* 每个从站**正确处理**了这个子报文，WKC 就**增加**；
* 主站收到返回帧后，**比较实际 WKC 和预期 WKC**：
  * 相等 → 这个子报文被所有该处理的从站正确处理了；
  * 不相等 → 有从站没收到、没配置好或掉线了。

增加规则：

| 操作 | WKC 增量 |
| :--- | :--- |
| 只读 或 只写 | **+1** |
| 读写（读成功） | **+1** |
| 读写（写成功） | **+2** |
| 读写（读写都完成） | **+3** |

子报文被多个从站处理时，WKC 是**各从站结果的累加**。

> **WKC 相当于"点名册"**：主站出门前算好"这一趟应该有 5 个人举手"，回来一看只有 4 只手——立刻知道有人缺席，而且知道是**哪条子报文**对应的那组人里有问题。比超时重试之类的机制精确得多，而且**零额外开销**。

### 也可以用 UDP/IP 传

**图 2.7　EtherCAT 数据帧嵌入 UDP 数据帧**（原书 p.22）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F009_p022.png" alt="图 2.7 EtherCAT 数据帧嵌入 UDP 数据帧">

## 2.3 EtherCAT 报文寻址和通信服务

**图 2.8　EtherCAT 网络寻址模式（直连／开放）**（原书 p.23）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F010_p023.png" alt="图 2.8 EtherCAT 网络寻址模式（直连／开放）">

EtherCAT 通信的本质是：**主站发送 EtherCAT 数据帧，读写从站设备的内部存储区**。

寻址是**两级**的：

```
第 1 级：以太网帧头的 MAC 地址  →  定位到"网段"这个以太网设备
第 2 级：EtherCAT 子报文头的 32 位地址  →  定位到段内的设备/存储区
```

段内寻址又分两种：

* **设备寻址**：针对**某一个**从站读写 → 单播；
* **逻辑寻址**：面向**过程数据**，可以多播，**一个子报文能同时读写多个从站**。

> 支持所有寻址模式的从站叫**完整型从站**；只支持部分寻址模式的叫**基本从站**。

| 方式 | 连接 | 目的 MAC 地址 | 特点 |
| :--- | :--- | :--- | :--- |
| **直连模式** | 网段直接接主站的标准以太网口 | **广播地址 FF:FF:FF:FF:FF:FF** | 最简单，最常用 |
| **开放模式** | 网段接在标准以太网交换机上 | **网段的 MAC 地址** | 可与普通以太网设备共存于同一交换机 |

* **开放模式**下，网段内的**第一个从站**拥有一个 ISO/IEC 8802-3 的 MAC 地址，这个地址**代表整个网段**，该从站叫**段地址从站**。它会交换以太网帧内的目的/源地址区。
* 如果 EtherCAT 走 UDP 传送，这个从站还会交换**源/目的 IP 地址和 UDP 端口号**，使响应帧完全满足 UDP/IP 协议标准。

> **段地址从站像"公司前台"**：快递员（交换机）只认前台的门牌（网段 MAC），里面的部门和工位怎么排，由前台自己转发——外部网络完全不需要知道 EtherCAT 内部的拓扑。

设备寻址时，子报文头内的 **32 位地址被拆成两半**：

```
┌────────────────┬────────────────────────┐
│ 16 位从站设备地址 │ 16 位站内物理存储空间地址 │
└────────────────┴────────────────────────┘
```

* 16 位站地址 → 最多 **65535 个从站**（这就是"最多 65535 个设备"的由来）；
* 16 位站内偏移 → 每个从站内最多 **64KB** 本地地址空间。

设备寻址时**每个报文只寻址唯一一个从站**，但有两种机制：

#### （1）顺序寻址（Auto-increment，自动增量寻址）

**地址由从站在网段内的连接位置决定**，用一个**负数**表示每个从站的位置：

| 从站 | 顺序地址 |
| :--- | :--- |
| 第 1 个 | 0 |
| 第 2 个 | −1（即 0xFFFF） |
| 第 3 个 | −2（即 0xFFFE） |

**工作过程**：子报文每经过一个从站，**所有子报文的位置地址加 1**；某个从站发现**自己的那份地址变成了 0**，就说明这报文是发给自己的。

以 3 个从站为例，主站发出地址为 `0、−1、−2` 的三个子报文：

| 阶段 | 子报文1 | 子报文2 | 子报文3 | 谁处理了 |
| :--- | :--- | :--- | :--- | :--- |
| 主站发出 | 0 | −1 | −2 | — |
| 到从站① | 0 ✅ | −1 | −2 | 从站① 拿走子报文1 |
| 从站①处理后 | 1 | 0 | −1 | — |
| 到从站② | 1 | 0 ✅ | −1 | 从站② 拿走子报文2 |
| 从站②处理后 | 2 | 1 | 0 | — |
| 到从站③ | 2 | 1 | 0 ✅ | 从站③ 拿走子报文3 |
| 从站③处理后 | 3 | 2 | 1 | 回到主站 |

> **类比**：像一队人传一叠"取件单"，每传一手，单子上的序号就 +1。谁看到某张单子变成 0，就知道那张是给自己的。**不需要预先知道谁叫什么名字，完全靠"传到第几手"来定位。**

**用途**：主要用在**启动阶段**，主站用顺序寻址给各个从站**配置站地址**。之后就可以用与物理位置无关的站点地址来寻址了。这个机制能**自动为从站设定地址**——从站不需要任何拨码开关。

#### （2）设置寻址（Configured Station Address，配置站地址）

**地址与连接顺序无关**。地址来源有两种：

1. 主站在**数据链路启动阶段**配置给从站；
2. 从站**上电初始化时**从自身的配置数据存储区（EEPROM）装载，然后主站在链路启动阶段用**顺序寻址**读回各从站的设置地址，在后续运行中使用。

**: 这是运行阶段的主力寻址方式**——因为站地址固定，主站可以随时直接点名某个从站，不用管它接在第几个位置。

### 2.3.3 逻辑寻址和 FMMU

**图 2.17　现场总线内存管理单元（FMMU）运行原理**（原书 p.27）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F019_p027.png" alt="图 2.17 现场总线内存管理单元（FMMU）运行原理">

**图 2.18　FMMU 映射举例**（原书 p.28）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F020_p028.png" alt="图 2.18 FMMU 映射举例">

逻辑寻址时，从站地址**不是单独定义的**，而是使用寻址段内 **4GB 逻辑地址空间**中的一段区域。子报文内的 32 位地址区作为**整体的数据逻辑地址**完成寻址。

实现者是 **FMMU**（Fieldbus Memory Management Unit，现场总线内存管理单元），**位于每一个 ESC 内部**，负责**把从站本地物理存储地址映射到网段内逻辑地址**。

FMMU 由**主站配置**，在数据链路启动过程中下发给从站。每个 FMMU 需要这些配置信息：

* 数据逻辑位起始地址
* 从站物理内存起始地址
* 位长度
* 映射方向类型位（输入 / 输出）
* 起始位 / 终止位（因为**可以按位映射**）

#### FMMU 配置实例

把主站控制变量区 `0x00014711` 从**第 3 位**开始的 **6 位**数据，映射到设备地址 `0x0F01`（一个开关量输出设备）从**第 1 位**开始的 6 位数据写操作：

| FMMU 配置寄存器 | 数值 |
| :--- | :--- |
| 数据逻辑起始地址 | 0x00014711 |
| 数据长度（字节数，仅用于字节计算） | 2 |
| 数据逻辑起始位 | 3 |
| 数据逻辑终止位 | 7 |
| 从站物理内存起始地址 | 0x0F01 |
| 物理内存起始位 | 0 |
| 操作类型（1 只读 / 2 只写 / 3 读写） | 2 |
| 激活（使能） | 1 |

**从站收到逻辑寻址的子报文时**：检查是否有 FMMU 地址匹配。

* 有匹配 → 把**输入类型数据插入**子报文数据区的对应位置，并从对应位置**抽取输出类型数据**；
* 没有 → 原样放行。

**逻辑寻址特别适合传输/交换周期性过程数据**，能灵活组织控制系统、优化系统结构。

#### FMMU 的功能特点

* 每个数据逻辑地址字节**只允许被一个 FMMU 读、另一个 FMMU 写**，或被**同一个 FMMU 读写交换**；
* 对一个逻辑地址的读写，与"用两个 FMMU 分别读和写"**结果相同**；
* **按位读写不影响没被映射到的其他位**——所以可以把**几个从站 ESC 中的位数据映射到主站的同一个逻辑字节**；
* 读写**未配置**的逻辑地址空间**不会改变其内容**。

> **FMMU 之于 EtherCAT，就像内存管理单元 MMU 之于操作系统**：进程（从站）看到的是自己的连续空间，实际物理地址怎么摆由映射表决定。主站的"过程映像区"就是那个虚拟地址空间，**一帧数据里每一格该给谁，全靠 FMMU 表说话**。

### 2.3.4 通信服务和 WKC

EtherCAT 子报文的**所有服务都是以主站操作描述的**。数据链路层规定了从站内部物理存储的**读、写、读写交换**服务。**读写操作 + 寻址方式共同决定子报文的通信服务类型**，由子报文头中的**命令字节**表示。

| 寻址方式 | 读写方式 | 命令 | 编号 | 含义 |
| :--- | :--- | :--- | :--- | :--- |
| — | 无操作 | **NOP** | 0 | 没有操作 |
| 顺序寻址 | 读 | **APRD** | 1 | 用顺序寻址从从站读取一定长度数据 |
| 顺序寻址 | 写 | **APWR** | 2 | 用顺序寻址向从站写入一定长度数据 |
| 顺序寻址 | 读写 | **APRW** | 3 | 用顺序寻址与从站交换数据 |
| 设置寻址 | 读 | **FPRD** | 4 | 用设置寻址从从站读取一定长度数据 |
| 设置寻址 | 写 | **FPWR** | 5 | 用设置寻址向从站写入一定长度数据 |
| 设置寻址 | 读写 | **FPRW** | 6 | 用设置寻址与从站交换数据 |
| 广播 | 读 | **BRD** | 7 | 从所有从站的物理地址读取数据，逻辑**或**操作 |
| 广播 | 写 | **BWR** | 8 | 广播写入所有从站 |
| 广播 | 读写 | **BRW** | 9 | 与所有从站交换数据，读回数据做逻辑**或**操作 |
| 逻辑寻址 | 读 | **LRD** | 10 | 按逻辑地址读取一定长度数据 |
| 逻辑寻址 | 写 | **LWR** | 11 | 按逻辑地址写入一定长度数据 |
| 逻辑寻址 | 读写 | **LRW** | 12 | 按逻辑地址与从站交换数据 |
| 顺序寻址 | 读+写同值 | **ARMW** | 13 | 从从站读取数据，并**写入以后所有从站的相同地址** |
| 设置寻址 | 读+写同值 | **FRMW** | 14 | 同上，用设置寻址 |

> **ARMW / FRMW 要特别记住**：它们是**分布式时钟同步的专用命令**。参考时钟从站把自己的系统时间放在报文里，后面每一个从站都读到同一个值并写进自己的寄存器——一帧数据就同步了一整条链上的所有时钟。**这是 EtherCAT 同步精度的关键技巧**：不需要给每个从站单独发时间，一次广播就同步全部。

**WKC 预期值**由服务类型和寻址地址共同决定：

* 单独读或写：+1；
* 读写：读成功 +1，写成功 +2，全完成 +3；
* 多个从站处理：累加。

## 2.4 分布时钟（DC，Distributed Clock）

**目的**：让所有 EtherCAT 设备使用**相同的系统时间**，从而控制各设备任务的**同步执行**。

支持分布式时钟的从站叫 **DC 从站**。DC 的主要功能：

* 实现从站之间时钟同步；
* 为主站提供同步时钟；
* 产生同步的输出信号；
* 为输入事件产生精确的时间标记；
* 产生同步的中断；
* 同步更新数字量输出；
* 同步采样数字量输入。

> **为什么这么重要**：多轴联动时，如果 A 轴的指令比 B 轴晚 20µs 到达，加工出来的轨迹就是歪的。DC 让所有从站在**同一纳秒时刻**执行各自的输出——这就是"分布式"的含义：时钟不是集中一个，而是每个从站一个，但**被对齐成一个**。

### 2.4.1 分布时钟描述

机制：**所有从站同步于一个参考时钟**。

* **参考时钟**：主站连接的**第一个具有 DC 功能的从站**。
* 所有其他从站（含主站）的时钟叫**从时钟**，同步于参考时钟。
* 参考时钟提供 **EtherCAT 系统时间**。

**6 个时间概念**：

| 概念 | 说明 |
| :--- | :--- |
| **① 系统时间** | 从 **2000 年 1 月 1 日零点**开始计时。64 位变量表示、单位 ns、最大可计时 **500 年**；也可用 32 位表示（最大 4.2s），用于通信和时间标记 |
| **② 参考时钟 / 从时钟** | 参考时钟 = 第一个 DC 从站；其余为从时钟 |
| **③ 主站时钟** | 主站也有计时功能，可以作为**从时钟**被同步。初始化阶段主站可以把主站时间按系统时间格式发给参考时钟从站 |
| **④ 本地时钟 / 初始偏移量 / 时钟漂移** | 每个 DC 从站有独立运行的本地时钟。启动时与参考时钟的差值叫**时钟初始偏移量**；运行中因时钟源不同产生的计时周期差异叫**时钟漂移**。两者都必须补偿 |
| **⑤ 本地系统时间** | 本地时钟经补偿同步后产生的时间。DC 的目标就是让所有从站的本地系统时间保持一致 |
| **⑥ 传输延时** | 数据帧在从站之间传输的延迟（含设备内部 + 物理连接延迟）。同步从时钟时必须考虑 |

### 2.4.2 传输延时和时钟初始偏移量的测量

**图 2.19　传输延时和时钟初始偏移量测量原理**（原书 p.31）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F021_p031.png" alt="图 2.19 传输延时和时钟初始偏移量测量原理">

**测量原理**（第 ① 步）：主站发一个**广播写命令**数据帧，**每个从站分别保存每个端口收到帧前导符第一位（SOF）的时刻**。

用 4 个时刻点：

* `T1`：帧到达**参考时钟**时的系统时间
* `T2(n)`：帧到达**从站 n** 时，从站 n 本地时钟的时刻
* `T3(n)`：帧**返回**再次到达从站 n 时，从站 n 本地时钟的时刻
* `T4`：帧返回到达**参考时钟**时的系统时间

由几何关系可得：

```
传输延时：T_delay(n) = [(T4 − T1) − (T3(n) − T2(n))] / 2
```

**这个公式的直觉**：`T4 − T1` 是帧"绕一圈"的总时间。`T3(n) − T2(n)` 是从站 n **自己看到的**帧从它这里出去又回来的时间。两者相减，就把从站内部的处理延时消掉了，剩下的是**一个来回的纯线路延时**，除以 2 就是**单程传输延时**。

**初始偏移量**：

```
初始偏移量 T_offset(n) = T2(n) − T1 − T_delay(n)
```

即"从站 n 以为的时间"减去"实际应该的时间"。

**流程**：

1. 主站读取各从站保存的时间值，用公式算 `T_delay(n)`，**写入各从站**；
2. 为提高准确度可以**多次测量求平均**；运行中也可以**随时重测**以补偿环境变化（比如温度导致线缆延时变化）；
3. 主站算出 `T_offset(n)` 并写入各从站。**初始偏移量只用于粗略同步，只需测量一次**。

### 2.4.3 时钟同步

**图 2.20　分布时钟同步原理**（原书 p.33）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F022_p033.png" alt="图 2.20 分布时钟同步原理">

每个设备的本地时钟**自由运行**，会与参考时钟产生漂移。同步的做法是：

**① 不改本地时钟，改"解读方式"**：主站计算参考时钟与每个从站时钟的偏移量 `T_offset(n)` 写入从站。从站这样算出自己的本地系统时间：

```
T_sys_local(n) = T_local(n) − T_offset(n)
```

**② 周期性同步**：主站用 **ARMW / FRMW 命令**发送数据报文，从参考时钟从站**读**当前系统时间 `T_sys_ref`，并**写入**从时钟从站。

每个从时钟从站在数据帧 **SOF 到达时锁存本地时钟时刻**，计算本地系统时间，然后算**漂移量 Δt**：

```
Δt = T_local(n) − T_offset(n) − T_delay(n) − T_sys_ref
```

**怎么补偿漂移——这个技巧很妙**：

* 正常情况下，ESC 控制本地时间**每 10ns 增加 10 个单位**；
* 若 **Δt > 0**（本地时钟走得**快**了）→ 每 10ns 只增加 **9**（走慢点）；
* 若 **Δt < 0**（本地时钟走得**慢**了）→ 每 10ns 增加 **11**（走快点）。

> **类比**：不用停表、不用重新对时，只是**每天偷偷把表"稍微拨快/拨慢一丁点"**，几十个周期后就自动对齐了。这叫"时间控制环路"，**平滑、无跳变**，非常适合运动控制——如果是硬跳变，伺服可能瞬间抖动。

**同步时机**：

* **初始化阶段**：主站应在测量传输延时和偏移补偿后，**在独立的数据帧中连续发送很多 ARMW/FRMW 命令**，让从站时钟快速同步，完成 DC 初始化；
* **周期性运行阶段**：随过程数据周期性发送 ARMW/FRMW，**实时补偿动态时钟漂移**；
* 发送时钟同步帧的**周期必须保证从时钟漂移小于控制应用规定的限制**。

#### 从站按 DC 支持情况分三类

| 类型 | 能力 |
| :--- | :--- |
| **完全支持 DC** | 有接收时间标记和系统时间功能，能产生同步信号或锁存信号时间标记 |
| **只支持传输延时测量** | **3 个端口以上**的从站必须支持；需要本地时钟和锁存帧到达时刻功能 |
| **不支持 DC** | **只有两个端口**的从站可以不支持。它们的处理和转发延时被周围支持 DC 的从站**当作物理连接延迟**一并处理 |

#### 从站设备的三种同步运行模式

**（1）自由运行（Free Run）**

* 本地控制周期由**本地定时器中断**产生；
* 周期时间可以由主站设定（可选功能）；
* 从站**不管主站什么时候发帧**，自己按自己的节奏走。

> 时间参数：`T1` = 本地微处理器从 ESC 复制数据并计算输出数据的时间；`T2` = 输出硬件延时；`T3` = 输入锁存偏移时间。这些参数反映了从站的时间性能。

**（2）同步于数据输入或输出事件**

* 本地周期在**数据输入/输出事件发生时**触发；
* 主站可以把过程数据帧的发送周期写给从站，从站可以检查是否支持或做本地优化；
* 通常**同步于数据输出事件**；如果从站只有输入数据，则同步于数据输入事件。

**（3）同步于分布式时钟同步事件（SYNC）**

* 本地周期由 **SYNC 事件**触发；
* **主站必须在 SYNC 事件之前完成数据帧的发送**；
* 要求**主站时钟也同步于参考时钟**。

**进一步优化**：从站应该在**数据收发事件发生时**就从收到的过程数据帧里**复制好输出数据**，然后**等 SYNC 信号到达后再执行输出**。数据帧必须比 SYNC 提前 `T1` 时间到达。

> **这个优化的意义**：把"搬数据"和"执行输出"拆开。搬数据是慢活（要读帧、算），输出是瞬间动作（把寄存器的值推到引脚）。**先慢慢搬好、瞄准，等号令一响立刻开枪**——这样所有从站的"开枪时刻"才能精确一致。

#### 主站的两种同步模式

| 模式 | 说明 |
| :--- | :--- |
| **周期性模式** | 主站周期性发送过程数据帧，周期由本地定时器控制。可以**用不同周期发送多种过程数据帧**以获得最优带宽（例如：小周期发运动控制数据、大周期发 I/O 数据） |
| **DC 模式** | 与周期性模式类似，但**主站本地周期要和参考时钟同步**。主站本地定时器根据发布参考时钟的 ARMW 报文进行调整 |

**DC 模式下主站本地定时器要比 DC 参考时钟提前的一段时间 = 以下几项之和**：

* 控制程序执行时间；
* 数据帧传输时间；
* 数据帧传输延时 D；
* 附加偏移（用于吸收从站延迟时间的抖动和控制程序执行时间的抖动）。

### 2.5.2 非周期性邮箱数据通信

**图 2.26　邮箱数据单元结构**（原书 p.37）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F028_p037.png" alt="图 2.26 邮箱数据单元结构">

EtherCAT 中的非周期通信叫**邮箱数据通信（Mailbox）**。

* **双向**：主站→从站、从站→主站；
* 支持**全双工、两个方向独立通信和多用户协议**；
* **从站到从站的通信由主站充当路由器**来管理（邮箱数据头里有一个地址域，主站可以重寄邮箱数据）；
* 邮箱通信是实现**参数交换的标准方式**。需要配置周期性过程数据通信或需要其他非周期服务时，就要用它。

**特点**：通常邮箱通信**只对应一个从站**，所以报文中使用**设备寻址**模式。

#### 邮箱数据头

| 数据元素 | 位数 | 描述 |
| :--- | :--- | :--- |
| **长度** | 16 位 | 跟随的邮箱服务数据长度 |
| **地址** | 16 位 | 主站→从站通信：**源**从站地址；从站→从站通信：**目的**从站地址 |
| 通道 | 6 位 | 保留 |
| 优先级 | 2 位 | 保留 |
| **邮箱类型** | 4 位 | 后续数据的协议类型：`0` 邮箱出错、`2` EoE、`3` CoE、`4` FoE、`5` SoE、`15` VoE（厂商自定义） |
| **计数器** | 4 位 | 用于重复检测的顺序编号，每个新邮箱服务加 1（为兼容老版本只用 1~7） |

#### 两种方向的通信

**（1）主站 → 从站（写邮箱命令）**

* 主站发送写命令把邮箱数据给从站；
* 主站**检查从站应答报文中的 WKC**：
  * WKC = 1 → 写成功；
  * WKC 没增加 → 通常因为从站**还没读完上一个命令**，或在限定时间内没响应 → **主站必须重发**。

**（2）从站 → 主站（读邮箱命令）**

* 从站有数据要发给主站，必须**先把数据写入输入邮箱缓存区**，再由主站来读；
* 主站发现输入邮箱有数据等待时，尽快发送读命令取走；
* **主站怎么知道从站填好了数据？** 两种方法：
  1. 用 **FMMU 周期性读某个标志位**（可以同时读多个从站的标志位，缺点：每个从站都需要一个 FMMU）；
  2. **直接轮询** ESC 输入邮箱数据区——读命令的 WKC 增加 1 就表示从站已填入新数据。

#### 邮箱通信出错时应答数据定义

| 命令码 | 含义 |
| :--- | :--- |
| 0x01 | 邮箱命令未知，不支持 |
| 0x02 | 不支持邮箱协议 |
| 0x03 | 邮箱通道无效 |
| 0x04 | 不支持邮箱服务 |
| 0x05 | 邮箱头无效 |
| 0x06 | 邮箱数据太长 |
| 0x07 | 邮箱服务内存不足 |
| 0x08 | 邮箱发生次数错误 |

## 2.6 状态机和通信初始化

**图 2.27　EtherCAT 状态转化关系**（原书 p.39）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F029_p039.png" alt="图 2.27 EtherCAT 状态转化关系">

**EtherCAT 状态机 ESM**（EtherCAT State Machine）负责协调**主站和从站应用程序在初始化和运行时的状态关系**。

EtherCAT 设备必须支持 **4 种状态**，另有 **1 个可选状态**：

| 状态 | 缩写 | 含义 |
| :--- | :--- | :--- |
| **Init** | I | 初始化 |
| **Pre-Operational** | P | 预运行 |
| **Safe-Operational** | S | 安全运行 |
| **Operational** | O | 运行 |
| **Boot-Strap** | B | 引导状态（可选） |

### 转换规则（非常重要）

* **向上（I→P→S→O）必须逐级，不可越级**；
* **向下（O→S→P→I）可以越级**（比如从 O 直接回 I）；
* **Boot-Strap 只能与 Init 互相转换**；
* **所有状态改变都由主站发起**：主站向从站发送状态控制命令请求新状态，从站响应执行，并把结果写入**从站状态指示变量**；如果转换失败，从站给出**错误标志**。

> **为什么向上不能越级**：这三级是"逐步放开权限"的过程——先能聊天（邮箱），再能看不能动（只读输入），最后才能动手（输出有效）。**必须一步步确认每一级都没问题才给下一级权限**，这样任何一级出错都在"还没有输出"的时候被发现，不会伤到设备。
>
> 向下可以越级，因为**收权限不需要谨慎**——越快地停下来越安全。

### 各状态详细含义

**（1）Init：初始化**

* 定义了主站与从站在**应用层的初始通信关系**；
* 此时**主站与从站应用层不能直接通信**；
* 主站用这个状态初始化 ESC 的一些**配置寄存器**；
* 如果从站支持邮箱通信，则**配置邮箱通道参数**。

**（2）Pre-Operational：预运行**

* **邮箱通信被激活**；
* 主站与从站可以用邮箱交换与应用程序相关的**初始化操作和参数**；
* **这个状态下不允许过程数据通信**。

**（3）Safe-Operational：安全运行**

* 从站应用程序**读入输入数据，但不产生输出信号**；
* 设备无输出，处于"**安全状态**"；
* 仍然可以使用邮箱通信。

**（4）Operational：运行**

* 从站读入输入数据，主站发出输出数据，**从站设备产生输出信号**；
* 仍然可以使用邮箱通信。

**（5）Boot-Strap：引导状态（可选）**

* 功能是**下载设备固件程序**：主站可以用 **FoE 协议**的邮箱通信下载新固件给从站。

### 状态转化操作总结

| 状态 / 转化 | 操作 |
| :--- | :--- |
| **初始化** | 应用层没有通信，主站只能读写 ESC 寄存器 |
| **Init → Pre-Op（IP）** | 主站配置从站**站地址寄存器**；如果支持邮箱通信则**配置邮箱通道参数**；如果支持分布式时钟则**配置 DC 相关寄存器**；主站写状态控制寄存器请求 Pre-Op |
| **预运行** | 应用层邮箱数据通信 |
| **Pre-Op → Safe-Op（PS）** | 主站用邮箱初始化过程数据配置；主站**配置过程数据通信的 SM 通道**；主站**配置 FMMU**；主站写状态控制寄存器请求 Safe-Op |
| **安全运行** | 应用层支持邮箱数据通信；有过程数据通信，但**只允许读输入数据，不产生输出信号** |
| **Safe-Op → Op（SO）** | 主站**发送有效的输出数据**；主站写状态控制寄存器请求 Op |
| **运行状态** | 输入和输出全部有效；仍然可以使用邮箱通信 |

## 2.7 应用层协议

**图 2.28　EtherCAT 协议结构**（原书 p.40）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F030_p040.png" alt="图 2.28 EtherCAT 协议结构">

**应用层 AL**（Application Layer）是 EtherCAT 协议最高的功能层，**直接面向控制任务**：

* 为控制程序访问网络环境提供手段，同时为控制程序提供服务；
* **不包括控制程序**，只定义了**控制程序与网络交互的接口**，使符合此应用层协议的各种应用程序可以协同工作。

EtherCAT 包括以下几种应用层协议：

| 协议 | 全称 | 用途 |
| :--- | :--- | :--- |
| **CoE** | CANopen over EtherCAT | 支持 CANopen 协议及其对象字典 |
| **SoE** | Servo Drive over EtherCAT | 支持 SERCOS 伺服驱动行规 |
| **EoE** | Ethernet over EtherCAT | 传输标准以太网/IP 帧 |
| **FoE** | File Access over EtherCAT | 下载/上传固件和文件 |

### （1）CoE（CANopen over EtherCAT）

CANopen 最初是为 **CAN 总线**（Control Area Network）控制系统开发的应用层协议。EtherCAT 在应用层支持 CANopen 并做了扩充。主要功能：

* 使用**邮箱通信访问 CANopen 对象字典**及其对象，实现网络初始化；
* 使用 **CANopen 应急对象**和可选的事件驱动 PDO 消息，实现网络管理；
* 使用**对象字典映射过程数据**，周期性传输指令数据和状态数据。

> **为什么是 CANopen**：CANopen 在伺服和 I/O 领域已经积累了大量行规（尤其 **CiA402 伺服行规**）。EtherCAT 直接"继承"它，意味着**一个用 CANopen 的伺服驱动器，改个通信层就能上 EtherCAT**，厂商和工程师的既有资产全部复用。这是 EtherCAT 能迅速占领市场的关键决策之一。

### （2）SoE（Servo Drive over EtherCAT）

**IEC 61491** 是国际上第一个专门用于**伺服驱动器控制**的实时数据通信协议标准，商业名称为 **SERCOS**（Serial Real-time Communication Specification）。EtherCAT 的通信性能非常适合数字伺服驱动器的控制，应用层使用 SERCOS 应用层协议实现数据接口：

* 使用邮箱通信访问**伺服控制规范参数 IDN**，配置伺服系统参数；
* 使用 **SERCOS 数据电报格式**配置 EtherCAT 过程数据报文，周期性传输伺服指令数据和伺服状态数据。

### （3）EoE（Ethernet over EtherCAT）

除了主从站之间的寻址通信模式，EtherCAT 也支持 **IP 标准协议**，比如 TCP/UDP/IP 以及所有其他高层协议（HTTP、FTP 等）。

* EtherCAT 能**分段传输**标准以太网协议数据帧，并在相关设备**完成组装**；
* **好处**：避免为长数据帧预留时间片，**大大缩短周期性数据的通信周期**；
* 主站和从站需要相应的 **EoE 驱动程序**支持。

### （4）FoE（File Access over EtherCAT）

* 通过 EtherCAT **下载和上传固件程序和其他文件**；
* 使用类似 **TFTP**（简单文件传输协议）的协议，**不需要 TCP/IP 支持**，实现简单。

## 本章小结（把这张表记住就抓住了全章）

| 主题 | 一句话核心 |
| :--- | :--- |
| 帧结构 | EtherType = **0x88A4**，一帧里塞多个子报文，每个子报文服务一个从站 |
| 飞传机制 | 从站**不停顿**，就着经过的帧顺手读写，边传边处理 |
| 寻址 | MAC 定位网段 → 子报文 32 位地址定位设备/存储区 |
| 设备寻址 | **顺序寻址**（按位置，位置号减到 0 就是目标）、**设置寻址**（按站号） |
| 逻辑寻址 | **FMMU** 把从站本地存储映射到 4GB 逻辑空间，可多播、可按位 |
| 通信命令 | 15 个命令 = 3 种寻址 × 3 种读写 + NOP + ARMW/FRMW |
| WKC | 从站每正确处理一次就 +1，主站比对预期值即知是否有从站掉队 |
| 分布时钟 | 第一个 DC 从站为参考时钟；测传输延时 → 算初始偏移 → ARMW/FRMW 周期同步；**慢就每 10ns 加 11，快就加 9** |
| 通信模式 | 周期性 = **过程数据**（实时、PDO、FMMU 逻辑寻址）；非周期 = **邮箱**（参数、SDO） |
| 状态机 | **I → P → S → O**（逐级向上，可越级向下），Boot 只与 Init 互换 |
| 应用层 | **CoE**（CANopen 对象字典）、**SoE**（SERCOS 伺服）、**EoE**（IP）、**FoE**（文件） |
