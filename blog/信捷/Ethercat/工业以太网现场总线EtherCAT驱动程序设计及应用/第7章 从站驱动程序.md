# 第7章 从站驱动程序

> 上一章讲主站软件，这一章讲**从站那一颗单片机里的程序怎么写**。
>
> 一句话主线：**初始化 → 主循环死等事件 → 有状态变化就切状态（并启停对应的数据通道）→ 有周期数据就来一次"读输出、算一下、写输入"的循环。**

---

## 开篇：这一章在讲什么

本章介绍基于**第 4 章那块 Atmega128 单片机控制的 EtherCAT 从站**的驱动程序。

* **使用标准 C 语言开发**；
* **可以方便地移植到其他嵌入式控制平台**。

> ⚠️ **一个前提要先说清楚**：从站驱动里有一个**根本性的分工**——
>
> | 谁 | 负责什么 |
> | :--- | :--- |
> | **ESC 芯片** | EtherCAT **数据链路层**：帧的接收、发送、转发、错误处理、WKC 累加、FMMU 映射…… |
> | **从站微处理器** | **应用层**：读写 ESC 寄存器、跑状态机、处理周期数据、实现具体业务功能（A/D、D/A、电机控制） |
>
> **这条分工线决定了本章所有的代码长什么样**：微处理器从来不碰网线上的字节，它只是**通过一条并口（PDI）去读写 ESC 里那块 DPRAM**，就像读写一片外部 RAM 一样。**所有的协议复杂度都被 ESC 芯片"吃"掉了。**
>
> 所以你写从站程序时，**脑子里不该有"网络"这个词**，只有"**寄存器**"和"**存储区**"。

---

## 7.1 从站驱动程序头文件 `ec_def.h`

这个头文件定义了从站驱动所有重要的**常量、数据结构及全局变量**。

### （1）基本数据类型

```c
#define UINT8   unsigned char
#define UINT16  unsigned int
#define UINT32  unsigned long
#define INT8    char
#define INT16   int
#define INT32   long
#define UCHAR   unsigned char
#define BOOL    unsigned char
#define TRUE    1
#define FALSE   0
```

> **为什么一个嵌入式项目开头总要干这件事**：因为 C 语言的 `int` 大小是**平台相关的**（16 位单片机上 `int` 可能是 2 字节，32 位 ARM 上是 4 字节）。而 EtherCAT 协议里"**16 位寄存器**"必须是**恰好 2 字节**——差一字节，收发的帧就是错的。
>
> **把类型长度用宏钉死，是跨平台驱动的第一步**。这样换芯片（AVR → ARM）时，只需要改这几个宏，**协议代码一行都不用动**。
>
> 现代做法更好：直接用 `<stdint.h>` 的 `uint8_t` / `uint16_t`。但**思路是一样的，而且这个"自己定义一套类型"的写法在工业界非常普遍**（你会发现几乎所有 PLC 固件里都有 `UINT8` 这种类型）。

### （2）协议相关常量

| 常量 | 值 | 含义 |
| :--- | :--- | :--- |
| `MAX_RX_PDOS` / `MAX_TX_PDOS` | 0x0001 | 最大 RxPDO / TxPDO 数目 |
| `MIN_PD_WRITE_ADDRESS` / `MAX_PD_WRITE_ADDRESS` | 0x1000 / 0x2000 | 过程数据**输出**区地址范围 |
| `MIN_PD_READ_ADDRESS` / `MAX_PD_READ_ADDRESS` | 0x1000 / 0x2000 | 过程数据**输入**区地址范围 |
| `NO_OF_PD_INPUT_BUFFER` / `NO_OF_PD_OUTPUT_BUFFER` | 0x0003 | 过程数据输入/输出**缓存区个数**（3 个） |
| `MAX_PD_INPUT_SIZE` / `MAX_PD_OUTPUT_SIZE` | 0x0040 | 过程数据输入/输出**最大长度**（64 字节） |
| `MAX_MB_INPUT_SIZE` / `MAX_MB_OUTPUT_SIZE` | 0x0040 | 邮箱数据输入/输出最大长度（64 字节） |
| `MIN_MBX_SIZE` / `MAX_MBX_SIZE` | 0x0020 / 0x0400 | 邮箱最小/最大长度（32 ~ 1024 字节） |
| `MIN_MBX_WRITE_ADDRESS` / `MAX_MBX_WRITE_ADDRESS` | 0x1000 / 0x2000 | 邮箱**写**（主站→从站）地址范围 |
| `MIN_MBX_READ_ADDRESS` / `MAX_MBX_READ_ADDRESS` | 0x1000 / 0x2000 | 邮箱**读**（从站→主站）地址范围 |

> **这批常量在本章后面会反复出现**——因为第 7.6.2 节的"**检查 SM 设置**"就是拿**主站写下来的 SM 参数**和**这些常量**比大小。**这是从站驱动里最重要的一类防御性检查**：
>
> 主站可能配错（比如把 SM 长度写成 10000 字节），**从站必须自己发现并拒绝**，否则就会出现"**缓冲区溢出**"——写到别的 SM 甚至寄存器上去。
>
> **注意这里的"谁的地盘"划分**：地址范围是有**约定**的——**0x1000~0x2000 既给了过程数据，也给了邮箱**。所以光看地址范围还不够，**必须再检查"有没有互相重叠"**（7.6.4 节会看到这段代码）。**两个不同的 SM 用了同一块内存，是 EtherCAT 从站最典型的配置错误之一。**

### （3）状态机相关定义

```c
#define STATE_INIT      ((UINT8) 0x01)   // 初始化
#define STATE_PREOP     ((UINT8) 0x02)   // 预运行
#define STATE_BOOT      ((UINT8) 0x03)   // 引导
#define STATE_SAFEOP    ((UINT8) 0x04)   // 安全运行
#define STATE_OP        ((UINT8) 0x08)   // 运行
#define STATE_MASK      ((UINT8) 0x0F)   // 状态掩码（取低 4 位）
#define STATE_CHANGE    ((UINT8) 0x10)   // 状态改变位
#define STATE_ERRACK    ((UINT8) 0x10)   // 错误应答位
#define STATE_ERROR     ((UINT8) 0x10)   // 错误指示位
```

**转化组合**（`高 4 位 = 当前状态`，`低 4 位 = 目标状态`）：

```c
#define INIT_2_PREOP    ((STATE_INIT << 4)   | STATE_PREOP)
#define INIT_2_SAFEOP   ((STATE_INIT << 4)   | STATE_SAFEOP)
#define INIT_2_OP       ((STATE_INIT << 4)   | STATE_OP)
#define PREOP_2_INIT    ((STATE_PREOP << 4)  | STATE_INIT)
#define PREOP_2_PREOP   ((STATE_PREOP << 4)  | STATE_PREOP)
#define PREOP_2_SAFEOP  ((STATE_PREOP << 4)  | STATE_SAFEOP)
#define PREOP_2_OP      ((STATE_PREOP << 4)  | STATE_OP)
#define SAFEOP_2_INIT   ((STATE_SAFEOP << 4) | STATE_INIT)
#define SAFEOP_2_PREOP  ((STATE_SAFEOP << 4) | STATE_PREOP)
#define SAFEOP_2_SAFEOP ((STATE_SAFEOP << 4) | STATE_SAFEOP)
#define SAFEOP_2_OP     ((STATE_SAFEOP << 4) | STATE_OP)
```

> **这个"8 位打包一个状态转化"的技巧非常漂亮，值得好好体会。**
>
> **问题是**：状态机要判断"**从 A 到 B 该怎么处理**"，组合有 5×5 = 25 种。用 `if (from == INIT && to == PREOP) ... else if (from == PREOP && to == SAFEOP) ...` 写出来**又长又容易漏**。
>
> **解法**：把 `from` 和 `to` 各 4 位**拼成一个字节**——`(from << 4) | to`。于是 `INIT_2_PREOP = 0x12`、`PREOP_2_SAFEOP = 0x24`、`SAFEOP_2_OP = 0x48`，**一个 `switch` 就能干净利落地覆盖全部组合**：
>
> ```c
> statetrans = (nAlStatus << 4) + alcontrolvar;   // 这就是 7.6.1 的代码
> switch (statetrans) {
> case INIT_2_PREOP: ...
> case PREOP_2_SAFEOP: ...
> }
> ```
>
> **这个"把两个小数值打包进一个整数当查表键"的手法，在协议实现里到处都是**（比如 TCP 状态机、CANopen 状态机）。**比写一堆嵌套 if 清晰、快、不易错。** 记住它。

**注意一个容易混的地方**：`STATE_CHANGE`、`STATE_ERRACK`、`STATE_ERROR` **三个宏的值都是 0x10**——但它们**用途完全不同**：

* 读 AL 控制寄存器时，**位 4 = 错误应答**（主站在应答错误）；
* 读 AL 状态寄存器时，**位 4 = 错误指示**（从站在报错）；
* 判断"状态是否需要变化"时，位 4 有意义……

**同一个位在不同寄存器里含义不同**，代码里必须清楚自己在读哪个寄存器。

### （4）同步管理器（SM）通道编号

```c
#define MAILBOX_WRITE     0    // SM0：邮箱输出（主站 → 从站）
#define MAILBOX_READ      1    // SM1：邮箱输入（从站 → 主站）
#define PROCESS_DATA_OUT  2    // SM2：过程数据输出（主站 → 从站）
#define PROCESS_DATA_IN   3    // SM3：过程数据输入（从站 → 主站）
```

> **这四个名字是本章的"高频词"**，从站驱动里每一处配置和检查都用它们。**记住这个映射关系，整章的代码就通了**：
>
> **SM0/SM1 管"对话"（邮箱），SM2/SM3 管"干活"（过程数据）。**

#define AL_CONTROL_EVENT      ((UINT16) 0x0001)   // AL 控制事件（主站请求状态切换）

### （6）AL 状态码

```c
#define ALSTATUSCODE_NOERROR                 0x0000
#define ALSTATUSCODE_UNSPECIFIEDERROR        0x0001
#define ALSTATUSCODE_INVALIDALCONTROL        0x0011
#define ALSTATUSCODE_UNKNOWNALCONTROL        0x0012
#define ALSTATUSCODE_BOOTNOTSUPP             0x0013
#define ALSTATUSCODE_NOVALIDFIRMWARE         0x0014
#define ALSTATUSCODE_INVALIDMBXCFGINBOOT     0x0015
#define ALSTATUSCODE_INVALIDMBXCFGINPRE      0x0016
#define ALSTATUSCODE_INVALIDSMCFG            0x0017
#define ALSTATUSCODE_NOVALIDINPUTS           0x0018
#define ALSTATUSCODE_NOVALIDOUTPUTS          0x0019
#define ALSTATUSCODE_SYNCERROR               0x001A
#define ALSTATUSCODE_SMWATCHDOG              0x001B
#define ALSTATUSCODE_SYNCTYPESNOTCOMPATIBLE  0x001C
#define ALSTATUSCODE_INVALIDSMOUTCFG         0x001D
#define ALSTATUSCODE_INVALIDSMINCFG          0x001E
#define ALSTATUSCODE_WAITFORCOLDSTART        0x0020
#define ALSTATUSCODE_WAITFORINIT             0x0021
#define ALSTATUSCODE_WAITFORPREOP            0x0022
#define ALSTATUSCODE_WAITFORSAFEOP           0x0023
#define ALSTATUSCODE_DCINVALIDSYNCCFG        0x0030
#define NOERROR_NOSTATECHANGE                0xFE
#define NOERROR_INWORK                       0xFF
```

> **同一个错误码列表，主站那章（第 3 章）是"读出来分析"，从站这里是"写出去报告"**。**从站每拒绝一次状态切换，都要把对应的错误码写进 0x0134**——这是从站驱动最重要的"沟通行为"。
>
> **为什么必须写错误码**：如果从站只是"拒绝但不说原因"，主站看到的是"状态切不过去"，**完全不知道是地址配错了还是长度不对**。有了错误码，主站（或调试人员）**一眼就能定位**：
>
> | 状态码 | 从站想说什么 |
> | :--- | :--- |
> | `INVALIDMBXCFGINPRE` (0x0016) | "**你的邮箱配置不对**，我没法进 Pre-Op" |
> | `INVALIDSMCFG` (0x0017) | "**SM 通道配置有问题**" |
> | `INVALIDSMINCFG` (0x001E) | "**输入 SM 配置不对**" |
> | `INVALIDSMOUTCFG` (0x001D) | "**输出 SM 配置不对**" |
> | `NOERROR_INWORK` (0xFF) | "**我还在处理中，别急**"（注意这是"正常"的，不是错误！） |
>
> **最后那个 `NOERROR_INWORK = 0xFF` 特别值得注意**：它是"**暂时还不行，但没错**"。**能区分"失败"和"还没好"，是状态机设计成熟的标志**——很多初学者实现的协议只会返回"成功/失败"两态，导致主站误判、乱重试。

### （7）配置错误标志与 SM 寄存器位

```c
#define SYNCMANCHADDRESS   0x01   // SM 地址错误
#define SYNCMANCHSETTINGS  0x02   // SM 设置错误
#define SYNCMANCHSIZE      0x03   // SM 大小错误

// SM 寄存器位定义
#define SM_PDINITMASK     0x02
#define SM_TOGGLEMASTER   0x0F
#define SM_ECATENABLE     0x02
#define SM_INITMASK       0x0D
#define ONE_BUFFER        0x01
#define THREE_BUFFER      0x02
#define PD_OUT_BUFFER_TYPE  THREE_BUFFER
#define PD_IN_BUFFER_TYPE   THREE_BUFFER
#define SM_WRITESETTINGS  0x04
#define SM_READSETTINGS   0x00
#define SM_PDIDISABLE     0x01
#define WATCHDOG_TRIGGER  0x40
```

> **`SYNCMANCHADDRESS/SETTINGS/SIZE` 这三个值的用法很巧妙**：看 7.6.2 的代码，错误码会被算成 `SYNCMANCHSETTINGS + 1` 或 `SYNCMANCHADDRESS + 1`——
>
> 为什么 `+1`？因为 **`+0` 要留给"这个 SM 通道本身"**。例如输入通道（SM3）出错时用 `SYNCMANCHSETTINGS + 1`，而输出通道（SM2）出错时用 `SYNCMANCHSETTINGS + 0`——**用偏移量把"哪个通道错了"也编码进错误码里了**。
>
> **这是一种"手工位域"技巧**：在没有漂亮调试器的嵌入式环境里，**一个字节要尽量多带信息**。现在的做法一般是用 `enum` + 明确的错误结构体，但**原理一致：错误信息要够定位，不能只报"失败了"**。

### （8）关键数据结构

| 结构体 | 对应 ESC 内容 |
| :--- | :--- |
| `TESC_REG` | **整个 ESC 寄存器空间**（从 0x0000 到 0x0FFF），**变量与寄存器一一对应** |
| `UALEVENT` | AL 事件请求寄存器（0x220~0x223），4 字节数组 `Byte[4]` |
| `UALEVENTMASK` | AL 事件屏蔽寄存器（0x204~0x207），2 个字 `Word[2]` |
| `TSYNCMAN` | **SM 结构体**：`sm_physical_addr`（起始地址）、`sm_length`（长度）、`sm_register_control`（控制）、`sm_register_status`（状态）、`sm_register_activate`（激活）、`sm_register_pdictl`（PDI 控制） |
| `TEEPROM_DEF` | EEPROM 操作结构体：`eeprom_config`、`eeprom_pdi_acstate`、`eeprom_ctl_status`、`eeprom_addr`、`eeprom_data[2]` |
| `TMII` | MII 操作结构体 |
| `TFMMU` | FMMU 结构体：`logical_start_addr`、`length`、`logical_start_bit`、`logical_stop_bit`、`physical_start_adr`、`physical_start_bit`、`type`、`activate`、`res[3]` |
| `TDC` | 分布式时钟结构体：`receive_port[4]`、`sys_time[2]`、`receive_time_pu[8]`、`sys_time_offset[2]`、`sys_time_delay`、`sys_time_diff`、`speed_cnt_start`、`speed_cnt_diff`、`sys_filter_depth`、`cyclic_unit_ctl`、`activation`、`pulse_length`、`sync0_status`、`sync1_status`、`start_time_cyclic[2]`、`next_sync1_pulse[2]`、`sync0_cyclic_time`、`sync1_cyclic_time`、`latch0_ctl`、`latch1_ctl`、`latch0_status`、`latch1_status`、`latch0_time_pedge[2]` 等 |

#### `TESC_REG`：整个 ESC 寄存器空间的"镜像结构体"

```c
typedef struct {
    UINT8  type;                 // 0x0000
    UINT8  revision;             // 0x0001
    UINT16 build;                // 0x0002
    UINT8  fmmus_supported;      // 0x0004
    UINT8  sm_supported;         // 0x0005
    UINT8  ram_size;             // 0x0006
    UINT8  port_descriptor;      // 0x0007
    UINT16 esc_feature;          // 0x0008
    UINT16 res1[3];
    UINT16 station_addr;         // 0x0010
    UINT16 alias_addr;           // 0x0012
    ...
    UINT32 esc_dlctl;            // 0x0100
    UINT16 physical_rw_offset;   // 0x0108
    UINT16 esc_dlstatus;         // 0x0110
    UINT16 al_ctl;               // 0x0120
    UINT16 al_status;            // 0x0130
    UINT16 al_statuscode;        // 0x0134
    UINT16 pdi_ctl;              // 0x0140
    UINT32 pdi_config;           // 0x0150
    UINT16 ecat_interrupt_mask;  // 0x0200
    UALEVENTMASK al_event_mask;  // 0x0204
    UINT16 ecat_interrupt_request; // 0x0210
    UALEVENT AIEvent;            // 0x0220
    UINT16 rx_error_counter[4];  // 0x0300
    UINT8  rx_error_cntforwarded[4]; // 0x0308
    UINT8  ecat_pu_errorcnt;     // 0x030C
    UINT8  pdi_error_cnt;        // 0x030D
    UINT8  lost_link_cnt[4];     // 0x0310
    UINT16 watchdog_divider;     // 0x0400
    UINT16 watchdog_time_pdi;    // 0x0410
    UINT16 watchdog_time_pd;     // 0x0420
    UINT16 watchdog_status_pd;   // 0x0440
    UINT8  watchdog_cnt_pd;      // 0x0442
    UINT8  watchdog_cnt_pdi;     // 0x0443
    TEEPROM_DEF eeprom_interface; // 0x0500
    TMII mii_man;                // 0x0510
    TFMMU fmmu_register[16];     // 0x0600
    TSYNCMAN sm_register[8];     // 0x0800
    TDC dc_register;             // 0x0900
    UINT8  esc_specific_register; // 0x0E00
    UINT32 digital_io_outpd;     // 0x0F00
    UINT16 general_purp_outputs; // 0x0F10
    UINT16 general_purp_inputs;  // 0x0F18
    UINT8  user_ram[128];        // 0x0F80
} TESC_REG;
```

**注意每个成员后面注释的地址**（0x0000、0x0001、0x0002……）以及那些 `res1`、`res2`……**填充数组**。

> **这个结构体的写法是本章最值得学的技术点之一，务必理解清楚。**
>
> **问题**：ESC 寄存器空间是**按固定地址排布的**——`al_ctl` 在 0x0120，`al_status` 在 0x0130，中间隔着 16 个字节的保留空间。**如果你的结构体里不写东西补上这个空隙，编译器会紧挨着排列，`pEsc->al_status` 指向的地址就不是 0x0130 了**——所有寄存器访问全部错位。
>
> **解法**：**用 `res` 数组手工填充到正确的偏移量**。
>
> **为什么这么做**（对比另一种写法）：
>
> | 写法 | 优点 | 缺点 |
> | :--- | :--- | :--- |
> | **结构体 + 填充**（本章） | **读写就像访问变量**：`pEsc->al_status` | 偏移量算错就全错，**要靠编译器对齐规则正确**（所以还要 `#pragma pack` 或 `__attribute__((packed))`） |
> | 手写偏移宏：`#define AL_STATUS 0x0130` + `*(UINT16*)(base+0x0130)` | 绝对精确 | 代码又长又难读，容易打错数字 |
>
> **本章选结构体的关键理由是"可读性"**：整个驱动里要访问几十个寄存器，**`pEsc->al_ctl = x` 比 `*(UINT16*)(pEsc + 0x120) = x` 好读太多**。
>
> **⚠️ 但这里有个大坑必须提醒**：**用结构体映射硬件寄存器时，一定要确保编译器不会插入额外填充（padding）**。方法是加 `#pragma pack(1)` 或 `__attribute__((packed))`。**如果不加，编译器可能给 `UINT32 esc_dlctl` 前插入对齐填充，整个偏移就全乱了**——而且这种 bug 在**不同编译器/不同优化级别下表现不一样**，极其难查。
>
> **写硬件驱动时，这是最容易踩、也最致命的坑之一。** 实践中最保险的做法是：**加完 pack 后，用 `offsetof()` 或编译期静态断言，逐个核对关键寄存器的偏移量**。

| `nAlStatusFailed` | 状态变换出错时保存最后的状态；状态机重新初始化时该变量会复位 |
| `nAlStatusCode` | AL StatusCode 的值，**应写入 0x0134** |
| `nAlControl` | 保存 AL Control 的值 |
| `nPdInputSize` | 保存 **SM3 的输入长度**，由应用层设定 |
| `nPdOutputSize` | 保存 **SM2 的输出长度**，由应用层设定 |
| `nEscAddrOutputData` / `nEscAddrInputData` | 保存 SM2 / SM3 的地址 |
| `pPdOutputData` / `pPdInputData` | **SM2 输出数据指针 / SM3 输入数据指针** |
| `u16SendMbxSize` / `u16ReceiveMbxSize` | 非周期发送 / 接收 SM 通道字节数 |
| `u16EscAddrSendMbx` / `u16EscAddrReceiveMbx` | 非周期发送 / 接收 SM 通道地址 |
| `pMbxWriteData` / `pMbxReadData` | SM0 输出数据指针 / SM1 输入数据指针 |
| `m_maxsyncman` / `bEscIntEnabled` / `m_pdoinrun` / `m_pdooutrun` | ESC 支持的最大 SM 数 / 中断使能标志 / 周期性输入运行标志 / 周期性输出运行标志 |
| `b3BufferMode` | 输入输出是否运行在 **3 个缓存区模式** |
| `bWdTrigger` | 看门狗是否触发 |
| `bEcatOutputUpdateRunning` | 是否处于 Op 状态（**在 StartInputHandler 中设置，在 StopInputHandler 复位**） |
| `aPdOutputData[]` / `aPdInputData[]` | **周期性输出 / 输入数据**存储数组 |
| `aMbOutputData[]` / `aMbInputData[]` | **非周期性输出 / 输入数据**存储数组 |
| `mb_counter` / `pd_counter` | 通信计数 |

> **`pPdOutputData` / `pPdInputData` 这两个指针是本章的核心机制**，务必先理解它们指哪儿：
>
> ```
> ESC 内部 DPRAM
> ├── 0x1000  SM2 管理的存储区（64 字节）  ← pPdOutputData 指向这里（主站写的输出）
> └── 0x1100  SM3 管理的存储区（16 字节）  ← pPdInputData  指向这里（给主站读的输入）
> ```
>
> **它们是在 `pdo_startinputhandler()` 里算出来的**（`ESC_REG_ENTRY + pSyncMan->sm_physical_addr`），**地址不是写死的，而是从主站配置的 SM 参数里读出来的**。
>
> **这个设计非常关键**：主站可以把 SM2 配在 0x1000，也可以配在 0x1400——**从站不需要知道，它自动跟着配置走**。这就叫"**由主站决定，从站自适应**"，是 EtherCAT 配置灵活性的来源。
>
> **而那几个 `aPdXxxData[]` 数组是"应用层缓冲区"**：中断里把数据从 ESC 搬到数组（或反过来），**应用代码只跟数组打交道**，完全不碰 ESC 地址。**这就是驱动层和应用层之间的接口**。

## 7.2 从站基本操作

### （1）对 ESC 控制寄存器的访问

```c
TESC_REG_MEMTYPE *pEsc;                  // MEMTYPE 为平台相关宏定义
pEsc = (TESC_REG_MEMTYPE *)ESC_REG_ENTRY; // ESC_REG_ENTRY 为地址宏定义

// 例如读状态机控制寄存器 al_ctl 到变量 alcontrol：
UINT16 alcontrol;
alcontrol = pEsc->al_ctl;
```

**本质就是一句话**：给指针赋一个**平台相关的固定地址**（`ESC_REG_ENTRY`），之后所有寄存器访问都变成**结构体成员访问**。

> **`MEMTYPE` 和 `ESC_REG_ENTRY` 这两个宏，就是把"平台相关"全部关进两个宏里**：
>
> * AVR 上 `ESC_REG_ENTRY` 可能是 `0x8000`（外部存储区映射地址）；
> * STM32 上可能是 `0x60000000`（FSMC 映射地址）；
> * `MEMTYPE` 可能是 `volatile`。
>
> **移植到新平台时只改这两个宏**——这就是 7.1 节开头说的"可以方便地移植到其他嵌入式平台"的实现方式。
>
> **顺便注意 `MEMTYPE` 里很可能含 `volatile`，这一点绝不能漏**：这些地址背后是**硬件寄存器**，值会**被硬件自己改变**（比如主站刚写了 al_ctl，状态可能立刻变）。如果不用 `volatile`，编译器可能把 `while (pEsc->al_status == 0)` 优化成"读一次，然后死循环"——**因为你没在循环里改这个变量，编译器认为它不会变**。**这类 bug 的表现是"程序卡死但看代码完全没问题"，是嵌入式最经典的坑之一。**

### （2）设置应用层状态：`SetAlStatus()`

```c
void SetAlStatus(UINT16 alstatus, UINT16 alstatuscode) {
    pEsc->al_status = alstatus;                 // 写 AL 状态寄存器 0x130~0x131
    if (alstatuscode != 0xFF)
        pEsc->al_statuscode = alstatuscode;     // 写 AL 状态码寄存器 0x134~0x135
}
```

**注意 `0xFF` 这个特殊值**：传 `0xFF` 表示"**只更新状态，不动错误码**"（对应宏 `NOERROR_INWORK = 0xFF`，意思是"工作中，没有错误"，此时没必要去改错误码）。

> **一个小设计细节**：用一个"魔法值"（0xFF）来代表"这次不改错误码"。
>
> **好处**是函数签名简单（只有一个入口）；**坏处**是调用者必须知道这个约定。**更现代的做法**是拆成两个函数（`SetAlStatus` / `SetAlStatusWithCode`）或者用布尔参数。
>
> 但在**嵌入式里代码尺寸和寄存器操作次数都是宝贵的**，用一个魔数省一个函数调用是常见权衡。**关键是这个约定要在头文件里注释清楚**——实际工程中"魔数没有文档"才是真正的灾难。

### （3）设置/复位事件中断屏蔽寄存器

```c
void set_intmask(UINT16 intMask) {      // 设置事件屏蔽寄存器 0x204~0x205
    UINT16 mask;
    mask = pEsc->al_event_mask.Word[0];
    mask = mask | intMask;              // 按位置 1 → 使能对应事件
    pEsc->al_event_mask.Word[0] = mask;
}

void reset_intmask(UINT16 intMask) {    // 复位事件屏蔽寄存器 0x204~0x205
    UINT16 mask;
    mask = pEsc->al_event_mask.Word[0];
    mask = mask & intMask;              // 按位与 → 屏蔽对应事件
    pEsc->al_event_mask.Word[0] = mask;
}
```

**用法**：**读-改-写**。因为屏蔽寄存器里有很多位对应不同事件，**每次只想改动关心的那几位，不能整体覆盖**。

> **"读-改-写"是操作硬件寄存器最常用的模式**，但要注意：**它本身不是原子操作**。如果在这三步之间发生了中断，而中断服务程序也动了同一个寄存器，**你的修改就丢了**。
>
> 这里因为是在主循环/状态机里调用，且中断服务程序只**读**事件请求寄存器、不写屏蔽寄存器，所以安全。**但换一个场景（比如中断和主循环都写同一个寄存器）就必须加临界区保护**（关中断，或者用硬件提供的置位/清零寄存器）。
>
> **判断"要不要加保护"的方法**：列出所有可能修改这个寄存器的代码路径，**只要存在"两条路径可能并发"，就必须保护**。

### （4）SM 通道操作

```c
void enable_syncmanchannel(UINT8 channel) {    // 使能 SM 运行
    // 清除 SM_PDI_CTL 寄存器的 Bit0（SM_PDIDISABLE）以「使能」SM
    pEsc->sm_register[channel].sm_register_pdictl &= ~((UINT8)SM_PDIDISABLE);
}

void disable_syncmanchannel(UINT8 channel) {   // 禁止 SM 运行
    pEsc->sm_register[channel].sm_register_pdictl |= ((UINT8)SM_PDIDISABLE);
}

TSYNCMAN* get_sm(UINT8 channel) {              // 获取 SyncManager 寄存器指针
    return &(pEsc->sm_register[channel]);
}
```

> **注意"使能/禁止 SM"用的是 `sm_register_pdictl`（PDI 控制寄存器）的 Bit0**，而不是 SM 的"激活"寄存器——**这正好对应第 3 章 3.5.1 那句"使 SM 无效：读和写含义不同"**：
>
> * **读**：0 = 正常操作，1 = SM 无效并禁止对内存区的访问；
> * **写**：0 = **激活 SM**，1 = 请求 SM 无效（等到当时正在处理的数据帧结束）。
>
> **也就是说，从站（PDI 侧）是通过写 PDI 控制位来启停 SM 的**；而"SM 被主站使能"走的是另一条路（`sm_register_activate` 里的 `SM_ECATENABLE`）。
>
> **这两者必须都满足，SM 才真正工作**。看 7.6.2 的检查代码就很清楚：**主站必须在 `sm_register_activate` 里使能 ECAT 访问**（否则从站报错）；**而从站在启动时用 `enable_syncmanchannel()` 打开 PDI 侧的访问**。
>
> **为什么要两把钥匙**：ESC 的存储区是"主站和本地 CPU 共用"的。**主站配好参数并"使能 SM"是一整套动作**；**本地 CPU 什么时候准备好接收数据是另一件事**（它可能还在初始化，或者刚收到切回 Pre-Op 的命令）。**让两侧各自控制自己那一半，才能避免"主站已经在往里写数据了，本地 CPU 还没准备好"** —— 这正是同步管理器存在的意义。

## 7.3 从站驱动程序总体结构

**图 7.1　从站驱动程序总体流程图**（原书 p.212）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F104_p212.png" alt="图 7.1 从站驱动程序总体流程图">

**从站以 ESC 芯片为核心：ESC 实现数据链路层，完成数据接收/发送及错误处理；微处理器操作 ESC 实现应用层协议。**

### 微处理器的三项任务

| 任务 | 说明 |
| :--- | :--- |
| **① 初始化** | 微处理器初始化、**通信变量和 ESC 寄存器初始化** |
| **② 通信状态机处理** | 完成通信初始化：**查询主站的状态控制寄存器，读取相关配置寄存器，启动或终止从站相关通信服务** |
| **③ 周期性数据处理** | 实现过程数据通信：以**查询模式（自由运行模式）**或**同步模式（中断模式）**处理周期性数据和应用层任务 |

### 主程序结构（`main()`）

```c
void main(void) {
    HW_init();      // 初始化微处理器寄存器
    ECAT_init();    // 初始化通信变量和 ESC 寄存器

    while (1) {                                    // ===== 主循环 =====
        // 读应用层事件请求寄存器，EscAIEvent 为全局变量，在头文件中定义
        EscAIEvent = pEsc->A1Event;

        if (!bEscIntEnabled) {                     // 未使能中断，处于自由运行模式
            free_run();       // 自由运行模式，查询周期性数据，见 7.4.2
        }
        al_event();           // 应用层事件处理，包括状态机和非周期性通信等，见 7.5
    }
}
```

**`HW_init()` 初始化微处理器 Atmega128，并使能外部中断信号引脚响应**：

```c
void HW_init(void) {
    MCUCR = 0xC0;    // 使能外部存储空间访问功能
    EICRA = 0xFF;    // 配置中断信号为上升沿触发
    EICRB = 0xFF;
    EIMSK = 0x20;    // 使能外部中断 1 响应
}
```

**`ECAT_init()` 初始化通信控制变量和 ESC 寄存器**：

```c
void ECAT_init(void) {
    pEsc = (TESC_REG_MEMTYPE*)ESC_REG_ENTRY;   // 给指向 ESC 的指针变量赋值
    pEsc->al_event_mask.Word[0] = 0;           // 清除事件屏蔽寄存器 0x204~0x205
    pEsc->al_event_mask.Word[1] = 0;           // 清除事件请求寄存器 0x206~0x207

    m_maxsyncman = pEsc->sm_supported;         // 读取 ESC 所支持的 SM 通道数目
    nAlStatus = STATE_INIT;                    // 设置当前状态为「初始化」状态
    SetAlStatus(nAlStatus, 0);                 // 初始化通信变量

    nPdInputSize = 0;
    nPdOutputSize = 0;
    bEcatLocalError = 0;
    bEscIntEnabled = FALSE;
}
```

> **看 `main()` 这个主循环，就是整个从站驱动的骨架，只有四行有效代码。** 把它翻译成中文：
>
> ```
> 1. 硬件初始化
> 2. 通信变量和 ESC 初始化
> 3. 然后就无限循环：
>      a. 读一下"事件通知栏"（AL 事件请求寄存器 0x220）
>      b. 如果没开中断 → 主动查一下有没有新的周期数据（自由运行模式）
>      c. 处理应用层事件（状态机 + 邮箱通信）
> ```
>
> **三个关键点**：
>
> **① "读事件寄存器"放在循环最前面，而且是每轮都读。** 这个寄存器就是 ESC 给从站微处理器的"**事件通知栏**"——主站请求切状态、SM 收到新数据、SYNC 信号来了，都往这里贴一张条子。**微处理器不需要去猜发生了什么，读这个登记簿就行。**
>
> **② `bEscIntEnabled` 决定用哪种处理方式**：
> * **= 0（自由运行模式）**：主循环**主动查询**（`free_run()`）有没有新数据；
> * **= 1（同步模式）**：周期数据**在中断服务程序里处理**，主循环里就跳过了。
>
> **这个开关是在初始化阶段根据主站对 SM 的配置决定的**——即"**主站怎么配，从站就怎么跑**"。
>
> **③ `ECAT_init()` 里读了 `pEsc->sm_supported`**——这就是第 3 章说的"**能力发现**"：**先问 ESC 芯片"你支持几个 SM 通道"，把它们记到 `m_maxsyncman` 里，后面检查时就不会去访问不存在的通道。**
>
> **这是一个非常重要的习惯**：**永远不要假设硬件能力，要先去问它。** 这段代码因此可以直接跑在 ET1100（8 个 SM）和别的芯片（4 个 SM）上，不用改一行。

### 从站操作相关的基本寄存器

| 编号 | 地址（字节） | 名称 | 读写 | 作用 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **0x120 (2)** | 应用层状态控制 | 读 | **读取主站给出的状态改变命令** |
| 2 | **0x130 (6)** | 应用层状态及状态码 | 写 | **返回从站实际状态及状态码** |
| 3 | **0x204 (4)** | 事件请求屏蔽 | 写 | 设置事件中断信号 |
| 4 | **0x220 (4)** | 事件请求 | 读 | **运行时查询事件** |
| 5 | **0x800 (32)** | SM 配置数据 | 读 | **读取 SM 通道内存的起始地址和长度** |
| 6 | **0x098E** | SYNC0 信号状态 | 读 | 读取此寄存器将复位 SYNC0 中断 |

> **这张 6 行的表，就是从站驱动的"全部接口"。**
>
> 一个从站程序跟 ESC 打交道，**归根结底就是这 6 个寄存器**，其余全是应用逻辑：
>
> | 要干什么 | 碰哪个寄存器 |
> | :--- | :--- |
> | 知道主站想让我干什么 | **读 0x120** |
> | 告诉主站我在哪、有没有出错 | **写 0x130 / 0x134** |
> | 决定我关心哪些事件（用中断还是用查询） | **写 0x204** |
> | 知道"刚刚发生了什么" | **读 0x220** |
> | 知道我的数据该放哪、多长 | **读 0x800** |
> | 应答 SYNC0 中断 | **读 0x098E 或 0x098F** |
>
> **注意第 6 项（读 0x098E 复位 SYNC0）**：这是第 3 章讲的"**周期性应答模式**"——SYNC 信号在**被应答之前保持有效**，所以<u>**中断服务程序里必须去读这个状态寄存器**</u>。**忘了读会怎样？SYNC0 信号一直有效 → 中断一直被触发 → 程序卡死在中断里出不来。** 这是初次做 DC 同步从站最常见的死机原因。

## 7.4 从站周期性数据的处理

**从站设备可以运行在两种模式下**，用一个全局变量 `bEscIntEnabled` 控制：

| 值 | 模式 | 处理方式 |
| :--- | :--- | :--- |
| **0** | **自由运行模式** | **查询方式**处理周期性数据 |
| **1** | **同步运行模式** | 在**中断服务例程**中处理周期性过程数据 |

**这个变量在初始化阶段根据主站对 SM 的配置来初始化**，以决定当前的运行模式。

### 7.4.1 同步运行模式

**图 7.2　同步运行模式中断服务例程流程图**（原书 p.215）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F105_p215.png" alt="图 7.2 同步运行模式中断服务例程流程图">

**在中断服务例程中处理周期性过程数据。**

由于**其他应用事件也可能触发中断**，所以需要在中断服务例程中**判断中断源**以做相应处理。从站使用 **Atmega128 的外部中断引脚 1** 作为中断输入，并在 `HW_init()` 中初始化。

**中断服务例程流程**（图 7.2）：

1. **读取事件请求寄存器 0x220~0x223 到变量 `EscAIEvent`**；
2. 查询 **SM2 事件**，如果发生，则**从 ESC 的 SM2 管理的存储区读取周期性输出数据**；
3. **如果输出有效**，将输出数据映射到相应的输出变量，并**执行硬件输出操作**。
   * **在 Safe-Op 状态下，虽然有输出数据，但从站不执行硬件输出操作**；
   * 程序中使用全局变量 `bEcatOutputUpdateRunning` 表示输出是否有效；
4. **读取硬件输入操作**，将输入数据**写入 SM3 管理的存储区**，等待下个数据帧读取。

```c
interrupt [EXT_INT1] void exter_int1(void) {
    // 读应用层事件请求寄存器
    EscAIEvent = pEsc->AIEvent;

    if ((EscAIEvent.Byte[1]) & (PROCESS_OUTPUT_EVENT >> 8)) {   // 有 SM2 事件发生
        // 从 ESC SM2 管理的存储区读取周期性输出数据
        // aPdOutputData : ec_def.h 中定义的数组，保存输出数据
        // pPdOutputData : ec_def.h 中定义的指针，指向 SM2 管理的内存区
        // nPdOutputSize : ec_def.h 中定义的变量，表示 SM2 管理内存区的容量
        memcpy(aPdOutputData, pPdOutputData, nPdOutputSize);

        if (bEcatOutputUpdateRunning == TRUE) {   // 该变量的意义见 7.1
            memcpy(aPdInputData, aPdOutputData, min(nPdOutputSize, nPdInputSize));
            // 如果输出有效，则执行输出操作（本例中直接将输出数据映射到输入数据）
        }
        // 执行应用输出操作
        // 执行应用输入操作
        // 将输入数据写入 ESC SM3 管理存储区
        memcpy(pPdInputData, aPdInputData, nPdInputSize);
    }
}
```

> **这段中断服务代码里有三个必须学会的点：**
>
> **① 中断里必须先"辨明来意"**。`EscAIEvent` 里可能同时有多个事件位（SM2 数据到了、状态变了、SYNC 来了……）。**你不能假设"进了这个中断就是数据来了"**——因为多个事件源共用同一个 IRQ 引脚。**先读事件寄存器、再按位判断、只处理自己关心的**，这是所有"中断源复用"场景的标准做法。
>
> **② 中断里的工作要尽可能少、尽可能快**。看这段代码：读事件 → `memcpy` 搬数据 → 写回。**全是纯内存操作，没有循环等待、没有复杂的逻辑判断**。这是刻意的：
> * 中断期间**其他中断被阻塞**（或者至少优先级低于它的被阻塞）；
> * 中断里花的时间越长，**系统响应抖动越大**；
> * 在同步模式里，**中断处理时间直接影响你能不能在下个 SYNC 到来前干完活**。
>
> **原则：中断里只做"必须立刻做"的事（搬数据、清标志），复杂计算留给主循环。** 如果一定要算，用"中断置标志 + 主循环执行"的方式（**上半部/下半部**模型）。
>
> **③ `bEcatOutputUpdateRunning` 这个判断是安全逻辑，不能删**。它保证**只有在 Op 状态下才真正驱动输出**：
> * 在 **Safe-Op** 下，SM2 的**数据是有效的**（主站在写），但**从站不能真的去驱动输出**——因为 Safe-Op 的定义就是"**输入有效、输出无效**"；
> * 这个标志在 `pdo_startinputhandler()` 里设置，在 `pdo_stopoutputhandler()` 里复位。
>
> **漏掉这个判断的后果很严重**：从站在 Safe-Op 状态下就按主站给的数据去驱动电机/阀门了，**而主站此时可能还在试探性地发测试数据**——设备会乱动。**这是"安全运行"这个状态名里"安全"二字的实际含义。**

> **顺便注意那个"本例中直接将输出数据映射到输入数据"**：这是示例板子的简化处理——把收到的输出原样回读作为输入。**真实设备这里应该是"读 A/D、读编码器、读限位开关"之类**。示例这么写是为了**让你能用主站看到"数据绕了一圈回来了"**，从而验证通信链路通了。**调试新板子时这个"回环"设计非常实用。**

### 7.4.2 自由运行模式

**图 7.3　自由运行模式流程图**（原书 p.215）

```c
void free_run(void) {
    if ((EscAIEvent.Byte[1]) & (PROCESS_OUTPUT_EVENT >> 8)) {   // 有 SM2 事件发生
        // 从 ESC SM2 管理的存储区读取周期性输出数据
        memcpy(aPdOutputData, pPdOutputData, nPdOutputSize);

        if (bEcatOutputUpdateRunning == TRUE) {
            // 如果输出有效，则执行输出操作（本例中直接将输出数据映射到输入数据）
            memcpy(aPdInputData, aPdOutputData, min(nPdOutputSize, nPdInputSize));
        }
        // 执行应用输出操作
        // 执行应用输入操作

        memcpy(pPdInputData, aPdInputData, nPdInputSize);
    }

```

**对比一下 7.4.1 的中断版本**：**代码几乎一模一样**，唯一的区别是——

* **同步模式**：这段代码在**中断服务程序**里，由**外部中断引脚**触发（通常由主站的 SYNC 信号或 SM2 事件驱动）；
* **自由运行模式**：这段代码是**普通函数**，由**主循环反复调用**（`while(1)` 里每轮都查一次事件寄存器）。

> **同一份逻辑，两种触发方式——这个设计非常值得学，也是本章的一个亮点。**
>
> | | 自由运行模式 | 同步运行模式 |
> | :--- | :--- | :--- |
> | 触发 | **主循环轮询**事件寄存器 | **中断**触发 |
> | 时机 | 什么时候处理**取决于主循环转到哪了**（不确定，有抖动） | **精确**，由 SYNC 或 SM2 事件决定 |
> | 实时性 | 差 | **好** |
> | CPU 占用 | 空转也要查 | 没事不占 CPU |
> | 实现难度 | **简单** | 要配中断、要防重入 |
>
> **该怎么选**：
> * **调试阶段、非实时功能**（比如一个远程 IO 盒、温度采集模块）→ **自由运行模式**，简单、够用；
> * **伺服、多轴联动、需要精确同步的场合** → **必须同步模式**。
>
> **把这个判断做成一个全局变量（`bEscIntEnabled`）来切换，而不是写死**——这样**同一份固件能覆盖两种档次的从站产品**，也方便调试时先用简单模式把链路跑通、再切到同步模式验证时序。**这是非常实用的工程做法。**

## 7.5 从站非周期性事件的处理

**从站非周期性事件主要有两类**：

1. **状态改变事件**（主站请求切换状态）；
2. **邮箱通信事件**（主站读写参数）。

在**程序主函数的主循环**中**读取应用层事件请求寄存器**以查询事件的发生。

> **注意**：本章程序**只给出邮箱通信的接口，并未实现具体的应用层协议**（也就是没实现 CoE/SoE 的具体报文解析）。**状态机处理在 7.6 节详细介绍。**

```c
void al_event(void) {
    UINT16 alcontrol;
    // 读 ESC 中断事件请求寄存器
    EscAIEvent = pEsc->A1Event;

    // 判断是否 AL 控制变化事件发生
    if (EscAIEvent.Byte[0] & AL_CONTROL_EVENT) {
        // 是，则读 AL 控制寄存器 0x120 以响应事件
        alcontrol = pEsc->al_ctl;
        // 调用状态机处理函数
        al_statemachine(alcontrol);   // 见 7.6.1 节
    }

    // 如果非周期性通信在运行
    if (m_mbxrunning) {     // 全局变量，其定义见 7.1
        // 判断是否有「非周期性输出数据」（SM2 通道事件）到达
        if ((EscAIEvent.Byte[1]) & (MAILBOX_WRITE_EVENT >> 8)) {
            mbx_process();  // 处理邮箱通信的接口
        }
    }
}
```

> **`al_event()` 是对 `EscAIEvent` 的"分诊"**：它把"事件登记簿"里的每一项分给对应的处理函数。
>
> **注意两个细节**：
>
> **① 读 AL 控制寄存器（`pEsc->al_ctl`）这个动作本身就是"应答"**。第 3 章讲过：**"ECAT 帧写完 AL 控制寄存器后，PDI 必须执行一次（读一下），否则 ECAT 帧不能继续写操作。"** 所以这一行 `alcontrol = pEsc->al_ctl;` **不只是为了取值，它还是握手协议中"我收到了"的那个确认信号**。
>
> **忘了读会怎样？** 主站会发现"从站不确认"，**之后就再也切不了状态了**（只有复位才能恢复）。现象是"第一次状态切换成功，后面全部卡住"——**非常典型、也非常难查的 bug**。
>
> **② 状态机调用条件是 `AL_CONTROL_EVENT` 位**，而不是"每轮都调"。**这是"事件驱动"而不是"轮询"**：只有主站真的动了 AL 控制寄存器，才会触发这个事件位，从站才去跑状态机。**没有事件时什么也不做，省 CPU。**
>
> **顺带注意 `alcontrol` 这个变量只是把值传给了 `al_statemachine()`** ——**状态机是拿"主站请求的目标状态"作为参数**去判断该怎么走的（下一节第一行就用到它）。

## 7.6 从站状态机的处理

**从站在主函数的主循环中查询状态机改变事件请求位**，如果发生变化，则执行状态机管理机制。

**状态机管理流程**（图 7.4）：

1. 从站程序**首先检查当前状态转化必须的 SM 配置是否正确**；
2. **如果正确**，则根据转化要求**开始相应的通信数据处理**；
3. 从站从**高级别状态向低级别状态**变化时，则**停止相应的通信数据处理**。

> **把这四条翻译成一句话，就是状态机函数的两层结构**：
>
> ```
> al_statemachine(目标状态)
>   ├── 第一层：检查 SM 设置（checksmsettings）  ← 配置对不对？
>   │     └── 不对 → 返回错误码，状态不变
>   └── 第二层：启动/停止通信处理                  ← 配置对了才真正动
>         ├── Init → Pre-Op  : 启动邮箱
>         ├── Pre-Op → Safe-Op: 启动周期输入
>         ├── Safe-Op → Op   : 启动周期输出
>         └── xxx → 低状态   : 停止对应的东西
> ```
>
> **这个"先验证、后执行"的顺序是安全关键设计**：
>
> 想象一下如果反过来——**先启动了 SM 通道，再检查配置**。如果配置是错的（比如 SM3 地址和邮箱内存重叠），那么**在检查之前，主站就已经能往那块内存写数据了**，可能覆盖掉邮箱内容或者别的数据。**先检查、再开门，门一旦开了就是安全的**。
>
> **这个原则适用于所有"开放资源"的场景**：**打开端口前先校验参数，加载配置前先验证格式，启动服务前先检查依赖。** 永远不要在验证通过之前让任何东西生效。

### 7.6.1 状态机处理流程

**图 7.4　EtherCAT 从站状态机处理流程**（原书 p.217）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F107_p217.png" alt="图 7.4 EtherCAT 从站状态机处理流程">

```c
void al_statemachine(UINT16 alcontrolvar) {
    UINT8 result = 0;
    UINT8 statetrans;
    UINT8 val;
    UINT8 al;

    al = alcontrolvar;

    // ---- ① 错误状态的处理 ----
    if (alcontrolvar & STATE_ERRACK)                      // 主站请求"错误应答"
        nAlStatus &= ~STATE_ERROR;                        // 清除错误指示位
    else if ((nAlStatus & STATE_ERROR) &&
             (((UINT8)alcontrolvar & STATE_MASK) >
              (nAlStatus & STATE_MASK)))                  // 有错误时不允许往上切
        return;

    alcontrolvar &= STATE_MASK;                           // 取低 4 位 = 目标状态
    statetrans = nAlStatus;                               // 得到目前的状态
    statetrans <<= 4;
    statetrans += alcontrolvar;                           // 得到转换状态变量（高 4 位当前 + 低 4 位目标）

    // ---- ② 第一层：检查 SM 设置 ----
    switch (statetrans) {
    case INIT_2_PREOP:
    case OP_2_PREOP:
    case SAFEOP_2_PREOP:
    case PREOP_2_PREOP:
        val = MAILBOX_READ + 1;                  // = 2，只检查 SM0/SM1
        result = checksmsettings(val);           // 在此状态检查 SM0/SM1 的设置
        break;

    case PREOP_2_SAFEOP:
    case SAFEOP_2_OP:
    case OP_2_SAFEOP:
    case SAFEOP_2_SAFEOP:
    case OP_2_OP:
        result = checksmsettings(m_maxsyncman);  // 在此状态检查所有的 SM
        break;
    }

    // ---- ③ 第二层：如果 SM 设置正确，则进行下一步处理 ----
    if (result == 0) {
        switch (statetrans) {
        case INIT_2_PREOP:
            result = mbx_startmailboxhandler();   // 见 7.6.3 启动邮箱
            break;
        case PREOP_2_SAFEOP:
            result = pdo_startinputhandler();     // 见 7.6.4 启动周期输入
            // 设置过程数据中断，使能 SM2、SM3
            break;
        case SAFEOP_2_OP:
            result = pdo_startoutputhandler();    // 见 7.6.5 启动周期输出
            break;
        case OP_2_INIT:
        case SAFEOP_2_INIT:
        case PREOP_2_INIT:
            mbx_stopmailboxhandler();             // 停止邮箱应用程序，见 7.6.6
        case OP_2_PREOP:
        case SAFEOP_2_PREOP:
            result = pdo_stopinputhandler();      // 见 7.6.6
            if (result != 0) break;
        case OP_2_SAFEOP:
            result = pdo_stopoutputhandler();     // 见 7.6.6
            break;
        }
    }

    // ---- ④ 检查 SM 设置不正确时的错误处理 ----
    else {
        switch (nAlStatus) {
        case STATE_OP:
            pdo_stopoutputhandler();              // 见 7.6.6
            break;
        case STATE_PREOP:
            if (result == ALSTATUSCODE_INVALIDMBXCFGINPRE) { ... }
            else nAlStatus = STATE_PREOP;
            break;
        }
    }

    // ---- ⑤ 设置 alStatus 和 alStatusCode ----
    if ((UINT8)alcontrolvar != (nAlStatus & STATE_MASK)) {
        if (result != 0) {
            nAlStatusFailed = nAlStatus;
            nAlStatus |= STATE_CHANGE;            // 没有成功，状态机状态不变
        } else {
            if (nAlStatusCode != 0)
                result = nAlStatusCode;
            nAlStatusFailed = alcontrolvar;
            alcontrolvar |= STATE_CHANGE;
        }
    } else if (alcontrolvar <= nAlStatusFailed) {
        result = 0xFF;
    } else {
        nAlStatusFailed = 0;
        nAlStatus = alcontrolvar;
    }

    // 为 AlStatus 寄存器赋值（该函数在 7.2 中介绍）
    SetAlStatus(nAlStatus, result);
    nAlStatusCode = 0;
}
```

> **这是全章最绕的一段代码，但把它拆成 5 个阶段就很清楚了：**
>
> | 阶段 | 干什么 |
> | :--- | :--- |
> | **① 错误处理** | 主站请求"错误应答"就清错误位；**有错误时不允许往高状态切** |
> | **② 检查 SM** | 按转化的类型决定检查哪些 SM：**去 Pre-Op 只查 SM0/SM1（邮箱），去 Safe-Op/Op 要查全部 SM** |
> | **③ 执行** | SM 全对才启动/停止对应的通信处理 |
> | **④ 错误分支** | SM 不对时，还要**回退已经启动的东西**（比如在 Op 状态下发现配置坏了，先停输出） |
> | **⑤ 汇报** | 把最终状态和错误码**写进 AL 状态寄存器**，告诉主站结果 |
>
> **几个必须理解的要点：**
>
> **（a）为什么"去 Pre-Op 只查 SM0/SM1"？** 因为按第 2 章的状态定义：
> * **Pre-Op 只需要邮箱通信**（这时过程数据的 SM 可能**还没配置**，是主站进 Pre-Op 之后才配的）；
> * **Safe-Op 开始才需要过程数据 SM**。
>
> **所以如果在 Init→Pre-Op 时就去检查 SM2/SM3，会全部失败**——因为主站还没来得及配它们。**检查的严格程度必须匹配当前阶段的需求**，这是很精细的设计。
>
> **（b）`statetrans` 这个"打包"技巧在 7.1 节解释过了**：`(当前状态 << 4) + 目标状态`，一个 `switch` 覆盖所有组合。**注意两层 `switch (statetrans)` 用了同一把钥匙**——第一层决定"检查什么"，第二层决定"执行什么"。**同样的键，两轮查表**，结构非常干净。
>
> **（c）`nAlStatus |= STATE_CHANGE`（0x10）是什么？** 这是**"状态改变位"**。第 3 章讲过 AL 状态寄存器的位 4：**位 0~3 是实际状态，位 4 是"是否处在请求的状态/错误标志"**。置位 0x10 相当于告诉主站："**我收到了你的请求，但我不在那个状态**"（即切换未完成）。
>
> **（d）`nAlStatusFailed` 的用途**：记录"上一次失败的目标状态"。配合那句 `else if (alcontrolvar <= nAlStatusFailed) result = 0xFF;` ——**`0xFF = NOERROR_INWORK`（还在处理中）**。
>
> **这段是在处理"重复请求"的情况**：
> * 主站可能**反复请求同一个目标状态**（因为它还没看到从站确认）；
> * 从站第二次收到**同样的请求**时，**不应该再报错**（配置上次已经检查过了，是好的）；
> * 所以返回 `0xFF`（**工作中，无错误**），表示"**我知道你要什么了，正在做，别急**"。
>
> **这个细节很能说明协议实现的成熟度**。如果没有它，主站的重试会被从站当成"新错误"处理，**两边反复来回、状态机永远收敛不了**。**在分布式协议里，"幂等地处理重复请求"是必须的**（还记得第 3 章邮箱通信的 `Ctr` 计数器吗？那是同一个思想的另一种实现）。
>
> **（e）最后 `SetAlStatus(nAlStatus, result)`** 把结果写进 0x130/0x134——**这就是从站向主站"汇报工作"的唯一出口**。主站读这两个寄存器，就知道"切成功没有、失败原因是什么"。

### 7.6.2 检查 SM 通道设置：`checksmsettings()`

**检查时机**：

* 进入 **Pre-Op** 之前 → 检查**邮箱通信**相关的 **SM0 和 SM1**；
* 进入 **Safe-Op** 之前 → 检查**周期性过程数据通信**使用的 **SM2 和 SM3**。

**要检查的 4 项内容**：

1. **SM 通道的大小**；
2. **SM 通道的设置是否重叠**——**特别注意三个缓存区时应该预留配置长度 3 倍大小的空间**；
3. **SM 通道起始地址应该为偶数**；
4. **SM 通道应该被使能**。

```c
UINT8 checksmsettings(UINT8 maxChannel) {
    UINT8 i;
    UINT8 result = 0;
    UINT8 smFailed = 0;
    TSYNCMAN_MEMTYPE* pSyncMan;

    // ===== 检查接收 Mailbox（SyncManager 通道 0）的 SyncManager 参数 =====
    pSyncMan = get_sm(MAILBOX_WRITE);
    if ((pSyncMan->sm_register_activate & SM_ECATENABLE) != SM_ECATENABLE)
        // 接收 Mailbox 没有使能
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if ((pSyncMan->sm_register_control & SM_INITMASK) != (ONE_BUFFER | SM_WRITESETTINGS))
        // 接收 Mailbox 不可被主站写，或 SM 不是一个缓存区的模式
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if (pSyncMan->sm_length < MIN_MBX_SIZE)
        // 接收 Mailbox 长度过小
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if (pSyncMan->sm_length > MAX_MBX_SIZE)
        // 接收 Mailbox 长度过大
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if (pSyncMan->sm_physical_addr < MIN_MBX_WRITE_ADDRESS)
        // 接收 Mailbox 地址过小
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if (pSyncMan->sm_physical_addr > MAX_MBX_WRITE_ADDRESS)
        // 接收 Mailbox 地址过大
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    else if ((pSyncMan->sm_physical_addr & 0x0001) != 0)
        // 接收 Mailbox 地址不是偶数
        result = ALSTATUSCODE_INVALIDMBXCFGINPRE;

    // 如果 SyncManager 长度为零，则返回
    if (pSyncMan->sm_length == 0)
        result = ALSTATUSCODE_NOERROR;

    if (result == 0) {
        // ===== 检查发送 Mailbox（SM1）的 SyncManager 参数（同上，略）=====
        ...
        else if ((pSyncMan->sm_register_control & SM_INITMASK) != (ONE_BUFFER | SM_READSETTINGS))
            // 发送 Mailbox 不可被主站读，或 SM 不是一个缓存区的模式
            result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
        ...
        else if ((pSyncMan->sm_physical_addr & 0x0001) != 0)
            // 发送 Mailbox 地址不是偶数
            result = ALSTATUSCODE_INVALIDMBXCFGINPRE;
    }

    if (result != 0) smFailed = MAILBOX_READ;
    else             smFailed = MAILBOX_WRITE;

    // ===== 检查输入（SM3）的 SyncManager 参数 =====
    if (result == 0 && maxChannel > PROCESS_DATA_IN) {
        b3BufferMode = TRUE;
        pSyncMan = get_sm(PROCESS_DATA_IN);
        if ((pSyncMan->sm_register_activate & SM_ECATENABLE) != 0 && pSyncMan->sm_length == 0)
            // SM3 长度为 0 且 SM3 没有激活
            result = SYNCMANCHSETTINGS + 1;
        else if ((pSyncMan->sm_register_activate & SM_ECATENABLE) == SM_ECATENABLE) {
            // SM 通道激活，输入大小必须大于 0
            if (nPdInputSize != 0) {
                if ((pSyncMan->sm_register_control & SM_PDINITMASK) == SM_READSETTINGS) {
                    if (((nAlStatus == STATE_PREOP) &&
                         (pSyncMan->sm_physical_addr >= MIN_PD_READ_ADDRESS) &&
                         (pSyncMan->sm_physical_addr <= MAX_PD_READ_ADDRESS)) ||
                        ((nAlStatus != STATE_PREOP) &&
                         (pSyncMan->sm_physical_addr == nEscAddrInputData))) {
                        // 地址匹配
                        if ((pSyncMan->sm_register_control & SM_INITMASK) == (ONE_BUFFER | SM_READSETTINGS)) {
                            // 输入为 1 个缓存的模式，复位标识 b3BufferMode
                            b3BufferMode = FALSE;
                        }
                    } else {
                        // 输入地址超出允许范围，或者在 SAFEOP 或 OP 状态被改变
                        result = SYNCMANCHADDRESS + 1;
                    }
                } else {
                    // 输入设置不匹配
                    result = SYNCMANCHSETTINGS + 1;
                }
            }
        } else if (pSyncMan->sm_length != 0 || nPdInputSize != 0) {
            // SM3 输入大小不为零而 SM3 没有激活
            result = SYNCMANCHSIZE + 1;
        }

        // 如果长度为零，则返回
        if (pSyncMan->sm_length == 0) {
            nPdInputSize = 0x0;
            nPdOutputSize = 0x0;
            result = ALSTATUSCODE_NOERROR;
        }

        if (result != 0) {
            result = ALSTATUSCODE_INVALIDSMINCFG;
            smFailed = PROCESS_DATA_IN;
        }
    }

    // ===== 检查输出（SM2）的 SyncManager 参数 =====
    if (result == 0 && maxChannel > PROCESS_DATA_OUT) {
        pSyncMan = get_sm(PROCESS_DATA_OUT);
        nPdOutputSize = pSyncMan->sm_length;
        ...
        // 检查激活、大小、设置（必须是 SM_WRITESETTINGS）、地址范围
        ...
        // 检查看门狗触发位是否使能
        if (pSyncMan->sm_register_control & WATCHDOG_TRIGGER)
            bWdTrigger = TRUE;
        ...
        if (result != 0) {
            result = ALSTATUSCODE_INVALIDSMOUTCFG;
            smFailed = PROCESS_DATA_OUT;
        }
    }

    // ===== 使能剩余的 SM 通道的使能字节，以应答 SM 变换的中断 =====
    if (result == 0) {
        for (i = maxChannel; i < m_maxsyncman; i++) {
            pSyncMan = get_sm(i);
            ...
        }
    }
    return result;
}
```

> **这段代码看着长，其实结构极其简单——它是同一种检查的 4 次重复（SM0 / SM1 / SM3 / SM2），每次检查 6 件事**：
>
> | 检查项 | 对应代码 | 不通过会怎样 |
> | :--- | :--- | :--- |
> | **① 是否被使能** | `sm_register_activate & SM_ECATENABLE` | 主站没给这个通道开权限 |
> | **② 缓存区模式** | `SM_INITMASK` 与 `ONE_BUFFER \| SM_WRITESETTINGS`（或 `READSETTINGS`）比较 | **邮箱必须是 1 个缓存区**；过程数据可以是 1 或 3 个 |
> | **③ 长度范围** | `sm_length` 与 `MIN/MAX_MBX_SIZE` 比较 | 太大 → 溢出；太小 → 装不下报文 |
> | **④ 地址范围** | `sm_physical_addr` 与 `MIN/MAX_XXX_ADDRESS` 比较 | 指到了不该指的地方 |
> | **⑤ 地址奇偶** | `sm_physical_addr & 0x0001` | **必须是偶数** |
> | **⑥ 是否重叠** | （在 start handler 里，见 7.6.4） | 两个 SM 抢同一块内存 |
>
> **几个值得单独说的点：**
>
> **（a）"地址必须是偶数"这条看着奇怪，但很有道理。** ESC 访问内存是**按字（16 位）**组织的，**奇地址会导致跨字访问**——要么硬件不支持，要么效率减半还可能出错。**所以从站必须主动拒绝奇地址。**
>
> **类比**：就像停车位是按"两个车位一组"划的（一个字 = 2 字节），**你非要把车停在"跨两个车位"的位置上，那谁也停不进去了**。所以规则是"**只能停在整格上**"。
>
> **（b）注意 `nAlStatus == STATE_PREOP` 这个条件**，非常有讲究：
> ```c
> if (((nAlStatus == STATE_PREOP) &&   // 还在 Pre-Op 阶段
>      (addr >= MIN_PD_READ_ADDRESS) && (addr <= MAX_PD_READ_ADDRESS))
>     ||                                // 或者
>     ((nAlStatus != STATE_PREOP) &&    // 已经离开 Pre-Op
>      (addr == nEscAddrInputData)))     // 地址必须和之前的一致
> ```
> **翻译成人话**：
> * **在 Pre-Op 阶段**（第一次配置过程数据 SM）→ **地址只要在合法范围内就行**，因为这是**首次配置**，主站还没定下来；
> * **一旦离开 Pre-Op**（进到 Safe-Op / Op）→ **地址必须和之前一模一样**！
>
> **为什么**：因为**已经在跑周期数据了**。这时候主站**偷偷改了 SM 地址**，从站还在往老地方搬数据、主站已经从新地方读——**数据就错位了，而且不会有任何报错**。
>
> **所以从站的态度是："第一次你随便定，定了就不能改。"** 要改？**先退回 Pre-Op 再说。** 这就是为什么那句注释写着"**输入地址超出允许范围，或者在 SAFEOP 或 OP 状态被改变**"会报错——**两个错误原因合并在一行里，但含义完全不同**。
>
> **这个"配置冻结"概念在工业协议里很常见**：**运行期不允许改配置**，因为改配置的一致性无法保证。想想 PLC 里"改硬件组态必须停机下载"——**是同一个道理**。
>
> **（c）`b3BufferMode` 和"预留 3 倍空间"**。检查项 2 特别强调："**三个缓存区时应该预留配置长度 3 倍大小的空间**"。
>
> 原因在第 3 章 3.5.2 讲过：**3 个缓存区模式下，SM 只配置第一个缓存区的地址，但实际会用到 3 块连续内存**（比如起始 0x1000、长度 0x100 → 实际占用 0x1000~0x12FF）。
>
> **所以代码里要检查的是"3 倍长度范围内有没有和别的 SM 重叠"**（7.6.4 里那个 `nPdInputSize * nPdInputBuffer` 就是在算这个）。
>
> **这是最容易配错、也最容易被忽略的一点**：如果你按"长度 0x100"去规划内存，只留了 0x100 的空间，**实际会溢出到后面 0x200 字节**——**写到别的 SM 或者邮箱上去了，而且平时看不出来，只在数据多的时候偶发**。
>
> **（d）最后那个 `for (i = maxChannel; i < m_maxsyncman; i++)` 循环**，目的是"**使能剩余 SM 通道的使能字节，以应答 SM 变换的中断**"。
>
> **为什么要把没用到的 SM 也"应答"一遍**：因为 ESC 会产生 **SM 变化事件**，如果**不给每个 SM 一个应答**，这个事件位就一直挂着、中断一直触发。**把没用的通道也"点一遍名"，是为了把中断标志清干净。**
>
> **这是一种典型的"防御性清理"**：**硬件报了个事件，你不确定是谁报的，那就把所有可能的来源都确认一遍。** 代价很小（几个寄存器读），换来的是"不会有幽灵中断"。

### 7.6.3 启动邮箱数据通信：`mbx_startmailboxhandler()`

**在设置从站为 Pre-Op 状态之前，如果邮箱通信 SM 配置正确，则启动邮箱通信处理。**

```c
UINT8 mbx_startmailboxhandler(void) {
    TSYNCMAN_MEMTYPE* pSyncMan;

    // 获取 Mailbox 接收 SyncManager
    pSyncMan = get_sm(MAILBOX_WRITE);
    u16ReceiveMbxSize = pSyncMan->sm_length;                        // 保存接收 Mailbox 数据长度
    u16EscAddrReceiveMbx = pSyncMan->sm_physical_addr;              // 保存接收 Mailbox 地址
    pMbxWriteData = (UINT8_MEMTYPE*)(ESC_REG_ENTRY + u16EscAddrReceiveMbx);

    // 获取 Mailbox 发送 SyncManager
    pSyncMan = get_sm(MAILBOX_READ);
    u16SendMbxSize = pSyncMan->sm_length;                           // 保存发送 Mailbox 数据长度
    u16EscAddrSendMbx = pSyncMan->sm_physical_addr;                 // 保存发送 Mailbox 地址
    pMbxReadData = (UINT8_MEMTYPE*)(ESC_REG_ENTRY + u16EscAddrSendMbx);

    // ★ 检查 Mailbox 是否有内存重叠设置
    if ((u16EscAddrReceiveMbx + u16ReceiveMbxSize) > u16EscAddrSendMbx &&
        (u16EscAddrReceiveMbx < (u16EscAddrSendMbx + u16SendMbxSize))) {
        return ALSTATUSCODE_INVALIDMBXCFGINPRE;     // 返回错误码
    }

    enable_syncmanchannel(MAILBOX_WRITE);   // 使能 Mailbox 接收 SyncManager 通道
    enable_syncmanchannel(MAILBOX_READ);    // 使能 Mailbox 发送 SyncManager 通道

    m_mbxrunning = TRUE;                    // 表明 Mailbox 已经开始运行
    return 0;
}
```

**这个函数做了三件事**：

| 步骤 | 动作 |
| :--- | :--- |
| **① 取参数** | 从 SM0/SM1 读出**地址和长度**，算出数据指针 `pMbxWriteData` / `pMbxReadData` |
| **② 检查重叠** | **两个邮箱的地址区间不能有交集** |
| **③ 使能通道** | 打开 SM0/SM1，置 `m_mbxrunning = TRUE` |

> **重点看那个"重叠检查"的写法，这是一个标准的"区间相交"判断，值得记住：**
>
> ```c
> // 两个区间 [A, A+lenA) 和 [B, B+lenB) 相交 ⟺
> //   A + lenA > B  且  A < B + lenB
> ```
>
> **它的直觉是"两个区间不可能同时满足"**：
> * `A + lenA > B` 表示"A 的尾巴越过了 B 的头"；
> * `A < B + lenB` 表示"A 的头在 B 的尾巴之前"；
> * **两个条件同时成立**，说明**它们一定有重叠部分**。
>
> **反过来想更容易记**：两个区间**不相交**只有两种可能——**A 完全在 B 前面**（`A+lenA <= B`）或者**A 完全在 B 后面**（`A >= B+lenB`）。**所以"相交"就是这两个都不成立**。
>
> **这是区间判断的标准公式，写代码时直接套，不要自己想。** 手写 `if` 判断重叠是最容易漏边界（`>` 还是 `>=`）的地方。
>
> **为什么邮箱特别要查重叠**：邮箱是**双向的**——SM0 是"主站→从站"，SM1 是"从站→主站"。如果**两者的内存有重叠**，就会出现"**我在写的数据正好是你正在读的区域**"，**邮箱内容被破坏，而且握手状态机会直接乱掉**（读到的数据不属于这轮的）。**这是最难查的一类 bug，因为数据"有时候对有时候错"**。所以必须**在启动时就拦住**。

### 7.6.4 启动周期性输入数据通信：`pdo_startinputhandler()`

**图 7.5　从站状态机中 PDO 输入处理流程**（原书 p.219）

<img src="https://cdn.jsdelivr.net/gh/lcekold/lcekold.github.io/img/ethercat/ethercat-book/F108_p219.png" alt="图 7.5 从站状态机中 PDO 输入处理流程">

**进入 Safe-Op 状态时**，如果过程数据 SM 通道设置正确，则：

1. **使能输入数据通道 SM3**；
2. **设置中断屏蔽寄存器，使输出数据 SM2 触发中断**；
3. **如果支持分布时钟，则使 SYNC0 事件触发中断**，启动周期性输入数据通信。
4. **此时输出数据通道 SM2 并不使能，输出数据无效**。

```c
UINT8 pdo_startinputhandler(void) {
    UINT16 nPdInputBuffer = 3;
    UINT16 nPdOutputBuffer = 3;
    TSYNCMAN_MEMTYPE* pSyncMan;
    UINT16 intMask = 0;         // 用于设置 AL-Event-Mask 寄存器
    UINT8 dcControl;
    UINT32 cycleTime;

    // ===== ① 从 SM2/SM3 读出地址、长度、缓存区数，算出数据指针 =====
    pSyncMan = get_sm(PROCESS_DATA_OUT);
    nEscAddrOutputData = pSyncMan->sm_physical_addr;
    nPdOutputSize = pSyncMan->sm_length;
    pPdOutputData = (UINT8_MEMTYPE*)(ESC_REG_ENTRY + pSyncMan->sm_physical_addr);
    if (pSyncMan->sm_register_control & ONE_BUFFER) nPdOutputBuffer = 1;

    pSyncMan = get_sm(PROCESS_DATA_IN);
    nEscAddrInputData = pSyncMan->sm_physical_addr;
    nPdInputSize = pSyncMan->sm_length;
    pPdInputData = (UINT8_MEMTYPE*)(ESC_REG_ENTRY + pSyncMan->sm_physical_addr);
    if (pSyncMan->sm_register_control & ONE_BUFFER) nPdInputBuffer = 1;

    // ===== ② 检查内存重叠 =====
    // 输入 SM 区域与 Mailbox 区域重叠？
    if (((nEscAddrInputData + nPdInputSize * nPdInputBuffer) > u16EscAddrSendMbx &&
         (nEscAddrInputData < (u16EscAddrSendMbx + u16SendMbxSize))) ||
        ((nEscAddrInputData + nPdInputSize * nPdInputBuffer) > u16EscAddrReceiveMbx &&
         (nEscAddrInputData < (u16EscAddrReceiveMbx + u16ReceiveMbxSize))))
        return ALSTATUSCODE_INVALIDSMINCFG;

    // 输出 SM 区域与 Mailbox、与输入 SM 区域重叠？
    if (((nEscAddrOutputData + nPdOutputSize * nPdOutputBuffer) > u16EscAddrSendMbx && ...) ||
        ((nEscAddrOutputData + nPdOutputSize * nPdOutputBuffer) > u16EscAddrReceiveMbx && ...) ||
        ((nEscAddrOutputData + nPdOutputSize * nPdOutputBuffer) > nEscAddrInputData &&
         (nEscAddrOutputData < (nEscAddrInputData + nPdInputSize))))
        return ALSTATUSCODE_INVALIDSMOUTCFG;

    // ===== ③ 分布式时钟检查 =====
    dcControl = pEsc->dc_register.activation;
    if (dcControl & (DC_SYNC0_ACTIVE | DC_SYNC1_ACTIVE)) {
        // 分布式时钟启用，检查 SYNC0/SYNC1 设置
        if (dcControl != (DC_CYCLIC_ACTIVE | DC_SYNC_ACTIVE))
            return ALSTATUSCODE_DCINVALIDSYNCCFG;
        intMask = DC_EVENT_MASK;               // 激活 DC 事件
        bDcSyncActive = TRUE;                  // 表明从站运行在分布式时钟模式
        cycleTime = pEsc->dc_register.sync0_cyclic_time;
    }

    // ===== ④ 设置中断屏蔽 =====
    if (nPdOutputSize != 0)
        intMask |= PROCESS_OUTPUT_EVENT;       // 激活 SM 通道 2（输出）中断事件
    else
        intMask |= PROCESS_INPUT_EVENT;        // 激活 SM 通道 3（输入）中断事件

    // ===== ⑤ 使能 SM 通道 =====
    if (nPdInputSize > 0) {
        enable_syncmanchannel(PROCESS_DATA_IN);   // 使能 SyncManager 通道（输入）
        m_pdoinrun = TRUE;
    }
    if (nPdOutputSize > 0) {
        if (!bEcatLocalError) {
            enable_syncmanchannel(PROCESS_DATA_OUT);   // 使能 SyncManager 通道
            m_pdooutrun = TRUE;
        }
    }

    set_intmask(intMask);
    return 0;
}
```

**这个函数做了 5 件事**：

| 步骤 | 干什么 |
| :--- | :--- |
| **①** | 从 SM2/SM3 读出参数，**算出 `pPdOutputData` / `pPdInputData` 指针**（**这就是"从站自适应主站配置"的实现**） |
| **②** | **检查内存重叠**——输入 SM vs 邮箱、输出 SM vs 邮箱、**输出 SM vs 输入 SM** |
| **③** | **检查 DC 配置**（如果启用了 SYNC0/SYNC1） |
| **④** | **设置中断屏蔽**（有输出 → 用 SM2 事件；没输出 → 用 SM3 事件） |
| **⑤** | **使能 SM3（和 SM2）**，置运行标志 |

> **这段代码里有三个非常值得理解的细节：**
>
> **（a）第 ① 步就是"自适应"的落地。** 开头 7.1 节提到过 `pPdOutputData` / `pPdInputData`，**它们就是在这里被算出来的**：
>
> ```c
> pPdOutputData = (UINT8_MEMTYPE*)(ESC_REG_ENTRY + pSyncMan->sm_physical_addr);
> ```
>
> **`ESC_REG_ENTRY` 是"ESC 寄存器空间的基地址"，加上"主站配置的 SM 物理地址"，就得到了数据区指针。** 主站把 SM2 配在 0x1000 还是 0x1400，从站代码完全不用管——**指针自己会算对**。
>
> **这个设计让同一份从站固件可以适配无数种主站配置**。如果是写死地址（`#define PD_OUT 0x1000`），那么换个主站软件、改个配置就崩了。**"从配置里读，不要写死"是驱动开发的第一原则。**
>
> **（b）注意第 ② 步检查了三组重叠，其中最后一组特别重要**：
>
> ```c
> // 输出 SM 区域 与 输入 SM 区域 重叠？
> ((nEscAddrOutputData + nPdOutputSize * nPdOutputBuffer) > nEscAddrInputData &&
>  (nEscAddrOutputData < (nEscAddrInputData + nPdInputSize)))
> ```
>
> **输出和输入是两块不同的数据区**：输出去从站（主站写），输入回主站（主站读）。**如果它们重叠了**：
> * 主站写输出 → **覆盖了从站刚写好的输入**；
> * 或者从站写输入 → **覆盖了主站刚写下来的输出**。
>
> 结果就是"**数据看起来对，但偶尔错一个值**"——**这种偶发数据错误在调试时最难查**，因为链路是通的、WKC 是对的、状态机也是好的。
>
> **所以从站必须自己拦住它。** 这也是为什么这个函数开头要先算 `nPdInputBuffer` / `nPdOutputBuffer`：***如果是 3 缓存区模式，要按 3 倍长度去算重叠范围***（前面 7.6.2 提过的那句"三个缓存区时应预留 3 倍空间"在这里落地）。
>
> **（c）第 ④ 步那个"有输出用 SM2 事件、没输出用 SM3 事件"的切换很讲究**：
> ```c
> if (nPdOutputSize != 0) intMask |= PROCESS_OUTPUT_EVENT;   // 用 SM2 事件
> else                    intMask |= PROCESS_INPUT_EVENT;    // 用 SM3 事件
> ```
>
> **为什么要分情况**：中断的触发源是"**有新数据要处理**"。
> * 如果**从站有输出**（是执行器，比如伺服）：主站每次写新数据 → **SM2 事件**，从站在这个事件上去取输出、算完写输入。**所以监听 SM2**。
> * 如果**从站只有输入**（是传感器，比如编码器模块）：主站没有数据要给它，**没有 SM2 事件**。这时从站应该在"**主站把我的输入读走了**"（SM3 事件）之后，去准备下一轮输入。**所以监听 SM3**。
>
> **这个细节很能说明"从站是有类型差异的"**：纯输入从站和带输出从站的**节拍来源不一样**。**如果一律监听 SM2，纯输入从站就永远收不到中断**——现象是"能扫到设备、能进 Op，但输入数据永远是 0"。**这是一个非常典型的、只发生在特定类型从站上的 bug。**
>
> **顺便注意第 ⑤ 步那句 `if (!bEcatLocalError)`**：**只有本地没有错误时才使能输出 SM2**。**这是又一道安全闸门**——本地应用自检出错（比如传感器故障）时，**宁可不开输出通道，也不让设备在不健康的状态下被驱动**。

### 7.6.5 启动周期性输出数据通信：`pdo_startoutputhandler()`

**进入 Op 状态时，使能输出数据 SM2，启动周期性输出数据通信。**

```c
UINT8 pdo_startoutputhandler(void) {
    UINT16 result = 0;
    if (nPdOutputSize > 0) {
        if (bEcatLocalError && (result == 0 || NOERROR_INWORK)) {
            enable_syncmanchannel(PROCESS_DATA_OUT);   // 没有错误，使能 SyncManager 2 通道
            bEcatLocalError = FALSE;
        }
        if (result != 0) {
            if (result != NOERROR_INWORK)
                bEcatLocalError = TRUE;
            return result;
        }
        m_pdooutrun = TRUE;                        // 表明输出已经运行
        bEcatOutputUpdateRunning = TRUE;
    }
    return 0;
}
```

**这个函数很短，但它是状态机里"最后一个安全开关"**：

* 只有到了 **Op** 状态才调用它；
* 调用它之后，**`bEcatOutputUpdateRunning = TRUE`**；
* 而 7.4.1/7.4.2 里那个 `if (bEcatOutputUpdateRunning == TRUE)` 判断，**正是用这个标志来决定"要不要真去驱动输出"**。

> **把这条链串起来看**，就是完整的"三层放行"：
>
> ```
> ① 主站请求 Op
>      ↓ al_statemachine 检查 SM 全部通过
> ② pdo_startoutputhandler() 被调用
>      ↓ 本地无错误（bEcatLocalError == FALSE）
> ③ 使能 SM2 通道 + bEcatOutputUpdateRunning = TRUE
>      ↓
> ④ 中断/主循环里：if (bEcatOutputUpdateRunning) { 真正驱动输出 }
> ```
>
> **注意第 ⑤ 步那个 `return result` 提前返回的分支**：
> ```c
> if (result != 0) {
>     if (result != NOERROR_INWORK) bEcatLocalError = TRUE;
>     return result;                    // ★ 这里就直接返回了
> }
> m_pdooutrun = TRUE;
> bEcatOutputUpdateRunning = TRUE;      // ★ 出错时不会执行到这里
> ```
> **意思是"有错误就不设置输出运行标志"**——**这样即使状态机把从站切到了 Op，实际的硬件输出仍然是关着的**。
>
> **这是"纵深防御"的体现**：状态机能进 Op 是一层，本地自检通过是第二层，**输出标志置位是第三层**。**任何一层拦住了，设备都不会动。** 做安全相关功能时，**这种"多层独立判断"是必须的**——因为任何单点判断都可能被绕过或有 bug。

### 7.6.6 停止 EtherCAT 数据通信

**在 EtherCAT 通信状态回退时停止相应的数据通信 SM 通道，有 3 种方式**：

| 方式 | 从什么状态退回 | 停止什么 | 调用函数 |
| :--- | :--- | :--- | :--- |
| **①** | 高状态 → **Safe-Op** | 停止**周期性过程数据输出**处理 | `pdo_stopoutputhandler()` |
| **②** | 高状态 → **Pre-Op** | 停止**所有周期性过程数据**处理 | `pdo_stopinputhandler()` |
| **③** | 高状态 → **Init** | 停止**所有应用层数据处理** | `mbx_stopmailboxhandler()` |

**（1）停止邮箱通信**

```c
void mbx_stopmailboxhandler(void) {
    m_mbxrunning = FALSE;                        // 表明 Mailbox 已经停止
    disable_syncmanchannel(MAILBOX_WRITE);       // 禁用 SyncManager 通道（接收）
    disable_syncmanchannel(MAILBOX_READ);        // 禁用 SyncManager 通道（发送）
}
```

**（2）停止周期性输入通信**

```c
UINT8 pdo_stopinputhandler(void) {
    disable_syncmanchannel(PROCESS_DATA_OUT);    // 禁用 SyncManager 通道
    // 复位 AL-Event 屏蔽寄存器
    reset_intmask(~(SYNC0_EVENT | SYNC1_EVENT | PROCESS_INPUT_EVENT | PROCESS_OUTPUT_EVENT));
    bEscIntEnabled = FALSE;
    m_pdoinrun = FALSE;
    disable_syncmanchannel(PROCESS_DATA_IN);     // 禁用 SyncManager 通道（输入）
    return 0;
}
```

**（3）停止周期性输出通信**

```c
UINT8 pdo_stopoutputhandler(void) {
    bEcatOutputUpdateRunning = FALSE;   // 输出标志复位 → 不再驱动输出
    return 0;
}
```

> **注意 `pdo_stopoutputhandler()` 只做了一件事——清掉那个输出标志**，连 SM 通道都没关。
>
> **这是刻意的、也是正确的**：**电机停下比"少占一个 SM 通道"重要一万倍**。
>
> ```c
> bEcatOutputUpdateRunning = FALSE;
> ```
> **这一行执行之后，7.4 节的中断/主循环里那个 `if` 判断就会失败，硬件输出立刻不再被驱动。**
>
> **对比一下如果按"教科书逻辑"写会怎样**：先关 SM2 通道、再清标志。那么在"关通道"和"清标志"之间有一个时间窗口——**这期间 SM2 可能正好来了一帧新数据**（因为有中断清标志的延迟），程序看到 `bEcatOutputUpdateRunning` 还是 TRUE，**照样驱动一次输出**。**在急停场景下，这"一次多余的动作"就可能导致事故。**
>
> **所以安全相关代码的第一原则是：先把"安全标志"清掉（让后续逻辑失效），再去收拾其他资源。** 顺序反了就有窗口。
>
> **另外注意 `reset_intmask` 的参数**：
> ```c
> reset_intmask(~(SYNC0_EVENT | SYNC1_EVENT | PROCESS_INPUT_EVENT | PROCESS_OUTPUT_EVENT));
> ```
> **取反之后按位与**，等价于"**把这四个事件位清掉，其他位保留**"。
>
> **为什么不能直接 `reset_intmask(0)`**？因为**屏蔽寄存器里可能还有别的位是别的模块在用的**，直接清 0 会把它们的设置也弄丢。**用"掩码取反"只动自己关心的位，是操作共享寄存器的标准做法**（还记得 7.2 节 `set_intmask`/`reset_intmask` 的读-改-写吗？这就是它的用途）。
>
> **规则记住**：**操作共享寄存器时，永远"只改我关心的位"，绝不整体覆盖。**

## 本章小结

| 主题 | 一句话核心 |
| :--- | :--- |
| **根本分工** | **ESC 干数据链路层，微处理器干应用层**；微处理器只是"读写一片外部 RAM"，不碰网线上的字节 |
| **头文件四件事** | 钉死类型长度（跨平台）、协议常量、状态机宏、结构体映射寄存器 |
| **状态转化打包** | `(当前状态 << 4) + 目标状态` 拼成一个字节，**一个 `switch` 覆盖所有组合** |
| **`NOERROR_INWORK = 0xFF`** | "还没好，但没错"——**能区分"失败"和"进行中"是状态机成熟的标志** |
| **`TESC_REG` 结构体** | 用 `res[]` 数组**手工填充到正确偏移**来映射寄存器；**必须加 pack，否则编译器的对齐填充会让整个偏移表崩掉** |
| **`MEMTYPE` / `ESC_REG_ENTRY`** | 把"平台相关"关进两个宏里；**`MEMTYPE` 必须含 `volatile`**，否则编译器会把"等硬件改值"优化成死循环 |
| **只读/写 6 个寄存器** | 0x120（主站要我干什么）、0x130/0x134（我在哪、错了什么）、0x204（我关心啥）、0x220（刚发生了啥）、0x800（我的数据在哪）、0x098E（应答 SYNC0） |
| **main() 骨架** | `HW_init` → `ECAT_init` → `while(1){ 读事件; 自由运行处理; al_event 处理 }` |
| **能力发现** | `ECAT_init` 里读 `sm_supported` 得到 `m_maxsyncman`——**永远先问硬件能力，不要假设** |
| **两种运行模式** | `bEscIntEnabled = 0` → **主循环轮询**（自由运行，简单但抖动大）；`= 1` → **中断处理**（同步，精确） |
| **一份逻辑两种触发** | `free_run()` 和 `exter_int1()` 内容几乎相同——**做成开关，同一固件覆盖两种档次的产品** |
| **中断三原则** | **先辨明来意**（读事件寄存器按位判断）、**只做必要的事**（搬数据+清标志）、**复杂计算留给主循环** |
| **Safe-Op 不输出** | `if (bEcatOutputUpdateRunning)` 这个判断**必须留着**——Safe-Op 的定义就是"输入有效、输出无效" |
| **`al_event()` 分诊** | AL 控制事件 → 跑状态机；邮箱事件 → `mbx_process()` |
| **读 0x120 即应答** | 那一行 `alcontrol = pEsc->al_ctl` **同时是取值和握手确认**；不读 → **主站第二次就再也切不了状态** |
| **状态机两层结构** | **先 `checksmsettings` 验证配置，通过了才启动/停止通信处理**（先检查、后开门） |
| **检查严格度分阶段** | **进 Pre-Op 只查 SM0/SM1（邮箱）**；**进 Safe-Op/Op 才查全部 SM**（此时过程数据 SM 才配好） |
| **SM 六项检查** | 是否使能、缓存区模式、长度范围、地址范围、**地址必须是偶数**、不与其它 SM 重叠 |
| **邮箱必须 1 缓存区** | 校验 `ONE_BUFFER \| SM_WRITESETTINGS`（或 `READSETTINGS`） |
| **3 缓存区要按 3 倍算** | **必须预留配置长度 3 倍的空间**，否则溢出到别的 SM（平时看不出、数据多时偶发） |
| **配置冻结** | Pre-Op 阶段地址在范围内即可；**离开 Pre-Op 后地址必须和之前完全一致**——运行期不许改配置 |
| **区间重叠判断** | `A+lenA > B && A < B+lenB` 即相交——**标准公式，直接套，别自己推** |
| **启动顺序** | `mbx_startmailboxhandler`（Init→Pre-Op）→ `pdo_startinputhandler`（Pre-Op→Safe-Op）→ `pdo_startoutputhandler`（Safe-Op→Op） |
| **中断源分类型** | **有输出的从站监听 SM2 事件；只有输入的从站监听 SM3 事件**——一律用 SM2 会让纯输入从站永远收不到中断 |
| **DC 检查** | `activation` 必须等于 `DC_CYCLIC_ACTIVE \| DC_SYNC_ACTIVE`，否则报 `DCINVALIDSYNCCFG` |
| **三层放行输出** | 状态机进 Op + 本地自检通过（`bEcatLocalError`）+ `bEcatOutputUpdateRunning` 置位——**任何一层拦住，设备都不会动** |
| **停机顺序** | **先清安全标志再收拾资源**（`bEcatOutputUpdateRunning = FALSE` 放最前），否则有"多余动作"的时间窗口 |
| **掩码取反清中断** | `reset_intmask(~(要清的位))`——**操作共享寄存器只改自己关心的位，绝不整体覆盖** |
| **自适应而非写死** | `pPdOutputData = ESC基址 + SM配置的地址`——**从配置里读，主站怎么配都能跑** |
