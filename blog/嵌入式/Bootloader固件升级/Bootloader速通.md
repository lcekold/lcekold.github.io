# Bootloader速通

（本文适合太长时间没使用过 Bootloader，导致相关流程有些生疏的开发者快速复习）

    OTA_Task（负责“下载和准备升级”）
    1. 监听升级指令
    2. 下载固件到非活动分区
    3. 校验固件完整性
    4. 设置升级标志位
    5. 重启设备

    Bootloader（负责“启动决策和回滚兜底”）
    1. 读取升级标志
    2. 校验待启动分区镜像
    3. 切换到新分区试运行
    4. 根据确认结果决定正式切换或回滚

## 一个设备中通常有两个程序

在支持 OTA 的单片机系统里，通常会有两个程序：Bootloader 和 Application。

- Bootloader：负责上电引导、镜像校验、分区切换、试运行判断、失败回滚。
- Application：负责设备的业务功能，同时负责接收升级指令、下载新固件、写入备用分区并触发升级。

可以简单理解为：

- Application 负责升级流程的前半段：把新固件安全地下载好。
- Bootloader 负责升级流程的后半段：决定能不能启动新固件，以及失败时怎么退回旧固件。

## 本文讨论的是标准 A/B 双分区 OTA

这里先明确一下本文讨论的方案：**标准 A/B 双分区 OTA**。

它的特点是：

- A 和 B 都是**可启动分区**。
- 当前正在运行的分区，叫**活动分区（Active Slot）**。
- 另一个暂时不用来运行、专门接收新固件的分区，叫**非活动分区（Inactive Slot）**。
- 升级时，新固件总是写入**非活动分区**。
- 升级成功后，新分区会变成新的活动分区。
- 下一次升级时，再把固件写回另一个分区。

所以在标准 A/B 方案里，并不是“A 永远是主分区，B 永远是备份分区”，而是：

- 这次 A 在运行，升级包就写到 B。
- 下次 B 在运行，升级包就写到 A。

两个分区会轮流承担“当前运行”和“下次升级写入”的角色。

## Bootloader 和 Application 各自负责什么

### Bootloader 的主要职责

1. 上电后读取升级标志、启动标志、确认标志等元数据。
2. 判断当前应该从 A 还是 B 启动。
3. 校验目标分区中的镜像是否合法，例如镜像头、长度、CRC/SHA256、签名等。
4. 如果目标镜像合法，则进入新固件试运行。
5. 如果新固件没有在规定时间内确认成功，或者反复异常重启，则回滚到旧固件。
6. 如果新固件确认成功，则将该分区标记为新的正式运行分区。

### Application 的主要职责

1. 完成设备本身的业务功能。
2. 监听升级指令。
3. 判断版本是否需要更新。
4. 将新固件下载到**非活动分区**。
5. 对下载后的固件做一次基础完整性校验。
6. 设置“待升级/待试运行”标志位。
7. 重启设备，交给 Bootloader 做最后的启动决策。

这里要注意：

- **Application 校验**，是为了尽早发现下载损坏。
- **Bootloader 校验**，是上电启动前的最终裁决，不能省。

## A/B 双分区 OTA 的核心流程

下面按一次完整升级来梳理。

假设当前状态如下：

- A 分区：当前稳定运行版本 v1
- B 分区：非活动分区
- 当前活动分区：A

那么升级到 v2 时，流程一般如下。

### 第 1 阶段：Application 下载并准备升级

    1. 后台循环监听 MQTT / HTTP / 串口等升级指令
    2. 收到升级指令后，先比较版本号，判断是否需要更新
    3. 确定当前活动分区是 A，因此本次写入目标为 B
    4. 申请互斥资源（独占 Flash，防止读写冲突）
    5. 开始下载固件包，并写入 B 分区
    6. 下载完成后，校验镜像完整性（如 SHA256 / CRC）
    7. 校验成功后，设置 OTA 升级标志和待启动分区标志（pending slot = B）
    8. 释放互斥资源
    9. 上报云端“固件下载完成，等待重启生效”
    10. 安全重启设备

### 第 2 阶段：Bootloader 决定是否切换到新分区

设备重启后，Bootloader 开始工作：

    1. 读取升级元数据
    2. 发现 pending slot = B
    3. 校验 B 分区镜像是否合法
    4. 若合法，则尝试从 B 分区启动
    5. 此时 B 进入“试运行”状态，而不是立刻算正式成功

### 第 3 阶段：新固件试运行并确认

新固件第一次启动后，通常还需要完成一次“确认成功”动作。

例如：

- 系统启动完成
- 关键任务正常运行
- 看门狗没有频繁复位
- 自检通过
- 在规定时间内写入“启动确认成功”标志

如果这些条件满足，那么可以将 B 分区标记为：

- 已确认（confirmed）
- 当前正式活动分区（active slot = B）

此时，B 就从“试运行的新分区”变成了“新的稳定分区”。

### 第 4 阶段：下一次升级写到另一个分区

当 B 已经成为稳定运行分区后：

- 当前活动分区 = B
- 非活动分区 = A

那么下一次 OTA 升级时，新固件就应该写入 **A 分区**。

也就是说，标准 A/B 双分区的写入规则始终是：

> **新固件永远写入非活动分区。**

所以升级过程会在 A/B 之间来回切换：

- v1 稳定运行在 A，升级包写到 B
- v2 稳定运行在 B，升级包写到 A
- v3 稳定运行在 A，升级包写到 B

## 为什么 A/B 双分区不怕升级失败

A/B 方案最大的价值就是：**始终保留一个旧的可启动版本**。

比如：

- 下载过程中断电
- 新固件镜像损坏
- 新固件启动后死机
- 新固件反复触发 watchdog 复位
- 新固件没有在规定时间内写入确认标志

在这些情况下，Bootloader 都可以选择：

- 放弃新分区
- 回滚到旧分区
- 继续从旧的稳定版本启动

这也是 A/B 双分区比“直接覆盖当前运行分区”更安全的根本原因。

## Bootloader 常见判断逻辑

为了方便快速回忆，可以把 Bootloader 的决策理解成下面这张表。

| 条件 | Bootloader 动作 |
|---|---|
| 没有升级标志 | 启动当前已确认分区 |
| 有 pending slot，且镜像合法 | 切换到新分区试运行 |
| 新分区试运行后已确认成功 | 将该分区设为新的活动分区 |
| 新分区未确认成功 / 启动异常 | 回滚到旧分区 |

## 一个容易混淆的点

本文讲的是**标准 A/B 双启动分区方案**。

还有一种常见实现是：

- A：主运行区
- B：下载暂存区

这种方案下：

- 新固件总是先下载到 B
- 然后 Bootloader 再把 B 拷贝到 A
- 最终仍然从 A 启动

它和标准 A/B 双分区的区别在于：

- 标准 A/B：A 和 B 都能直接启动，成功后活动分区在 A/B 间切换。
- 下载暂存区方案：B 只是中转区，最终运行区通常还是 A。

这两个方案的思路很像，但实现细节并不一样，不能混为一谈。

## 总结

如果只记一句话，那么标准 A/B 双分区 OTA 可以概括为：

> Application 负责把新固件下载到非活动分区，Bootloader 负责校验、试运行、确认和回滚；升级成功后，新分区成为新的活动分区，下一次升级再写到另一个分区。

这样设计的核心目的，就是在升级失败、异常重启、甚至掉电时，仍然保留一个可正常启动的旧版本。
